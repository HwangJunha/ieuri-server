# SPEC-0014 — 서버 설계

요구사항·수용 기준·계약 초안은 spec에 있다. 여기에는 서버 쪽 설계 판단만 적는다.

---

## 구현 이력 (2026-08-10)

구현하면서 이 문서의 판단이 사실과 달랐던 곳과, 실측으로 확정한 것을 적는다.

**① §5.1 "전부 `Polygon`(멀티폴리곤·홀 없음)"은 틀렸다.**
원본 GeoJSON 121건 중 **POI096(북서울꿈의숲)에 내부 링이 1개 있다**(외곽 507점 + 내부 47점).
계약도 이 전제 위에 단일 링으로 되어 있었다. **외곽 링만 적재**하기로 했다 — 폴리곤 채색이
용도라 공원 안 작은 구멍은 표현할 필요가 없고, 링 배열로 계약을 넓히면 클라이언트가 121곳
전부에 대해 다중 링 렌더링을 다뤄야 한다(사용자 결정).

**② EN 이름의 출처는 CSV가 아니라 xlsx다.**
§5.1은 `서울시_121장소_목록.csv`에 `AREA_CD·CATEGORY·AREA_NM`이 있다고 적었고 실제로 그렇다 —
**`ENG_NM`이 없다.** 영문명은 `서울시 주요 121장소 목록.xlsx`에만 있다. 세 원본(xlsx ·
area-names.md · geojson)을 `AREA_CD`로 조인해 마이그레이션을 생성했고, 121건이 결측 없이
맞물리는 것을 확인했다.

**③ §2.1의 캐스팅 우려가 실제로 발생했다 — `&&` + geography 캐스팅이라야 인덱스를 탄다.**
`ST_Intersects(location::geometry, ST_MakeEnvelope(...))`로 쓰면 **컬럼 쪽 캐스팅이
`idx_spot_location`(geography GiST)을 무력화해 전 행 필터가 된다.** 실행 계획으로 확인한
비용은 **291,650 → 1,112**(약 260배)이다. 확정 형태는 이렇다:

```sql
location && ST_MakeEnvelope(?, ?, ?, ?, 4326)::geography
```

점 데이터에서는 `&&`(바운딩박스 겹침)와 `ST_Intersects`의 결과가 같다 — 점의 바운딩박스가
점 자신이라 경계 포함(R1)도 그대로 지켜진다. §8 4번은 이로써 해소됐다.

**④ 클러스터링 집계를 전부 SQL에서 한다 — 카테고리 목록을 올리지 않는다.**
§2.3은 "집계는 DB에서"라고만 적었는데, 우세 카테고리 판정을 애플리케이션에 두면
`ARRAY_AGG(category)`로 셀 하나에 **수천 건**이 실려 온다(실측: 저줌 한 셀 1,769건).
과반 판정에 필요한 것은 최빈 카테고리와 그 개수뿐이라 CTE 둘로 셀 집계와 최빈값을 각각
내고 `top_cat.c * 2 > cell.cnt`로 판정한다. `mode()`를 쓰지 않는 것은 개수를 함께 주지
않아 과반인지 알 수 없기 때문이다.

**⑤ 업스트림은 구역 코드가 아니라 국문명으로 조회한다.**
포트가 `fetch(areaCode, areaName)` 둘을 받는다 — 이름은 요청에, 코드는 응답 검증(R15)에
쓴다. 활성 언어와 무관하게 항상 국문명을 넘긴다.

**⑥ R15 검증이 실제로 필요하다는 것을 확인했다.**
샘플 키로 `강남역`·`홍대 관광특구`를 요청해도 **전부 POI009(광화문·덕수궁)가 돌아왔다.**
설계가 예상한 동작 그대로이며, 이 검증이 없으면 잘못된 구역 데이터가 올바른 키로 캐시된다.

**⑦ 상권 단계 문자열과 시각 형식이 spec과 다르다.**
`AREA_CMRCL_LVL`은 `한산한 시간대`가 아니라 **`한산한`**(어간만)으로 오고, `CMRCL_TIME`은
`"20260810 0600"`으로 `PPLTN_TIME`(`"2026-08-10 05:45"`)과 **형식이 다르다.** 매핑은 어간
기준(접미사·영문 병기 제거)으로, 시각 파싱은 두 형식 모두 시도하도록 구현했다.

**⑧ 계약 변경 2건.** `MapViewportResult.spots`를 `Spot` 재사용에서 **`MapSpot` 신규 타입**으로
바꿨고(기존 `Spot.distanceMeters`가 non-null인데 bbox에는 중심점이 없다 — nullable로 바꾸면
BREAKING), 구역·행사 식별자를 `ID!` → **`String!`**으로 바꿨다(codegen이 `ID`를 `Long`으로
매핑하는데 `POI001`은 문자열이다). 근거는 `contract.graphql` 상단 AMEND에 적었다.

**⑨ `[TBD]` 수치 7종은 설정값으로 뺐다.** `ieuri.map-viewport.*`와
`ieuri.seoul-citydata.*`이며 기본값은 spec §8 표에 적었다. 실측 후 값만 바꾸면 된다.

**⑩ 문화행사는 캐시에서만 모은다.** §6은 부분 실패만 다루고 행사 조회 경로를 정하지
않았는데, `mapViewport`가 행사를 위해 업스트림을 부르면 지도를 움직일 때마다 쿼터가 탄다.
혼잡도 조회가 `citydata` 1콜로 세 블록을 함께 받아 두므로, 행사는 그 캐시에서만 읽는다 —
캐시가 없는 구역은 행사가 비고 그것은 오류가 아니다.

**⑪ 리뷰 지적 중 받아들이지 않은 것: `events`를 지연 필드로 분리하지 않는다.**
아키텍처 리뷰가 `mapViewport.events`를 `@DgsData`로 빼라고 지적했다 — 별도 I/O(구역 bbox
질의 + 구역당 캐시 읽기)를 선택 여부와 무관하게 치른다는 점에서 맞는 지적이다. 그럼에도
두지 않는 이유는 **R21이 "spot 마커와 문화행사 마커를 항상 함께 표시한다. 토글 필터를 두지
않는다"**로 못 박고 있어서다. 클라이언트가 `events`를 빼고 물을 일이 계약상 없으므로,
지연 필드는 실제 호출을 줄이지 못한 채 포트만 쪼갠다. 요건이 바뀌어 토글이 생기면 그때
분리한다.

**미검증으로 남긴 것**: 실키 호출(환경변수 미보유 — 샘플 키로만 검증), 마이그레이션의
실제 적용과 앱 기동(로컬 DB 비밀번호 미보유), Valkey 직렬화 왕복. 앞의 둘은 사용자 확인이
필요하다. 단 마이그레이션 SQL의 폴리곤은 PostGIS에 직접 넣어 `ST_IsValid` · 내부 링 0개를
확인했고, bbox·클러스터링 질의는 실 DB에서 실행해 결과와 실행 계획을 확인했다.

## 1. 기존 자산 — 새로 만들지 않아도 되는 것

조사 결과 이미 있는 것들이다. 중복 구축하지 않는다.

| 자산 | 위치 | 본 spec에서의 쓰임 |
|---|---|---|
| PostGIS `geography(Point,4326)` + GiST 인덱스 | `spot.location` (V15) | bbox 조회를 그대로 얹는다. 신규 공간 인프라 불필요 |
| `map_x`/`map_y` → `location` 동기화 트리거 | V15 | 그대로 유효 |
| `SpotCachePort` / `ValkeySpotCache` | `tourism/…/out/cache` | 실시간 캐시 포트를 같은 패턴으로 추가 |
| Valkey 인스턴스 | auth refresh 토큰과 공용 | 신규 인프라 아님 |
| `SpotQueryPort.findSpotIdsWithin` | `tourism/…/port/out/query` | 원형 조회. **유지**하고 bbox 조회를 별도 메서드로 추가 |

**`spots()` 원형 조회를 없애지 않는다.** 목록 화면에서 여전히 쓴다. bbox는 지도 전용 경로다.

## 2. bbox 조회

### 2.1 질의 방식

`ST_Intersects(location, ST_MakeEnvelope(minLng, minLat, maxLng, maxLat, 4326))`로 좁힌다.
`location`이 `geography`이므로 envelope 비교 시 캐스팅 방향을 명시해야 한다 — `geography`와
`geometry`를 암묵 캐스팅에 맡기면 인덱스를 타지 않는 계획이 나올 수 있다. 실행 계획을 확인해
GiST 인덱스가 실제로 쓰이는지 검증한다.

**경계 포함**(R1)이므로 `ST_Intersects`를 쓴다. `ST_Within`은 경계선상 점을 제외한다.

### 2.2 날짜변경선

bbox의 `minLng > maxLng`인 경우(태평양 횡단)는 **거절한다**(`INVALID_BBOX`). 서비스 대상이
한국이라 정상 사용에서 발생하지 않으며, 지원하면 질의가 두 개로 쪼개진다.

### 2.3 클러스터링

저줌에서 그리드 기반으로 묶는다. 줌 레벨에서 그리드 셀 크기를 유도하고, 셀별로
`count` · 중심 좌표 · 우세 카테고리를 집계한다.

- **우세 카테고리**의 판정 규칙(과반 초과, 없으면 부재)은 spec R2가 정한다. 여기서는
  집계를 DB에서 수행한다는 점만 덧붙인다.
- 중심 좌표는 셀 중심이 아니라 **포함된 spot 좌표의 평균**을 쓴다. 셀 중심을 쓰면 마커가
  실제 밀집 위치에서 벗어난다.
- 집계는 DB에서 수행한다. 전체를 애플리케이션으로 끌어와 묶으면 저줌에서 상한의 의미가
  사라진다.

### 2.4 상한과 잘림

상한 + 1건을 조회해 초과 여부를 판정하고, 반환은 상한까지만 한다. `COUNT(*)` 별도 질의는
하지 않는다 — 정확한 총계가 필요 없고 "더 있다"만 알면 된다.

## 3. 서울 실시간 데이터 어댑터

### 3.1 위치

`tourism/application/port/out/client`에 포트를, `tourism/infrastructure/adapter/out/client`에
어댑터를 둔다. community·auth의 기존 외부 클라이언트와 같은 구조다.

REST 호출은 여기서만 일어난다. POL-021은 **우리가 REST를 제공하지 않는다**는 뜻이지 외부
REST를 소비하지 않는다는 뜻이 아니다.

### 3.2 엔드포인트 선택

혼잡도만 필요한 경로에서는 `citydata_ppltn`(경량)을, 문화행사·상권까지 필요하면
`citydata`(전체, ~170KB)를 쓴다. 인구 필드는 양쪽이 동일함이 확인됐다.

호출 1회에 세 블록이 다 오므로, **본 spec 범위에서는 `citydata` 한 번으로 세 블록을 모두
채우는 편이 호출 수 측면에서 유리하다.** 블록별로 나눠 호출하면 같은 구역에 대해 호출이
배가된다 — 일일 1000건 제약에서 치명적이다.

### 3.3 응답 구역 코드 검증 (R15)

샘플 키에서 **존재하지 않는 구역명을 요청해도 오류 없이 POI009 데이터가 반환되는** 동작이
관측됐다. 요청한 구역 코드와 응답의 `AREA_CD`가 다르면 캐시에 쓰지 않고 실패로 처리한다.
이 검증이 없으면 잘못된 구역 데이터가 올바른 키로 캐시된다.

### 3.4 파싱 방어

- 인구 관련 필드는 **문자열로 온다**(`"3000"`). 정수 파싱 실패를 예외로 전파하지 말고 해당
  구역을 건너뛴다.
- `AREA_SH_PAYMENT_CNT`는 문자열인데 `AREA_SH_PAYMENT_AMT_MIN/MAX`는 숫자로 오는 등
  **타입이 일관되지 않다.** 필드별로 관대하게 파싱한다.
- 혼잡도 단계가 정의된 4값 중 어느 것도 아니면 **임의 단계로 넘기지 않는다**(R7). 매핑
  실패로 처리한다. 업스트림이 5번째 값을 도입했을 때 조용히 잘못된 색을 칠하는 것보다,
  표시하지 않는 편이 낫다.

## 4. 캐시 설계

### 4.1 키 구조

기존 `ieuri:tourism:spot:{op}:...` 관행을 따라 `ieuri:tourism:citydata:{block}:{areaCd}` 형태로
둔다.

**캐시된 값 안에 업스트림 타임스탬프를 함께 저장한다**(R13). 키에 타임스탬프를 넣지 않는
이유: 넣으면 이전 시각의 키가 TTL까지 남아 메모리를 갉아먹고, "현재 값"을 찾으려면 키를
스캔해야 한다. 값 안에 두면 조회 즉시 신선도를 판정할 수 있다.

### 4.2 재호출 판정

데이터가 **약 30분 지연되어 도착**하므로(spec §4.2), "5분 경계까지 TTL"은 동일 데이터를
반복 호출한다. 판정 기준은 이렇게 둔다:

```
캐시에 값이 있고, (지금 - 저장시각) < 최소재호출간격  →  캐시 반환
그 외                                                →  업스트림 호출
호출 결과의 PPLTN_TIME이 캐시된 것과 같으면          →  저장시각만 갱신
```

최소재호출간격은 `[TBD]`이며 실측으로 정한다. 5분보다 크게 잡아야 호출량이 준다.

### 4.3 블록별 독립 (R14)

인구·상권·문화행사를 **별개 키로** 저장하고 각자의 타임스탬프로 판정한다. `CMRCL_TIME`이
야간 내내 정지하는 것이 관측됐으므로, 단일 TTL이면 상권이 멈춘 동안 인구까지 낡은 채로
남거나 그 반대가 된다.

문화행사는 일 1회 갱신이므로 TTL을 훨씬 길게 잡는다.

### 4.4 장애 처리

기존 `ValkeySpotCache`는 Valkey 장애를 **삼킨다**(캐시는 정합성 소스가 아님). 같은 방침을
유지한다. 단 **auth의 refresh 토큰 저장소는 fail-closed**(POL-008)이며 같은 인스턴스를
쓰므로, 여기서 예외를 삼키는 것이 그쪽 동작에 영향을 주지 않는지만 확인한다.

업스트림 장애 시에는 만료된 캐시라도 반환하고 `degraded`를 세운다(R11). 이때 `staleSince`에
그 데이터의 시각을 담는다.

## 5. 정적 데이터 적재 (R16·R17)

### 5.1 대상

- `서울시_121장소_목록.csv` — `AREA_CD` · `CATEGORY` · `AREA_NM` (122행 = 헤더 + 121)
- `서울시_주요_121장소_영역.geojson` — 121 feature, **전부 `Polygon`** (멀티폴리곤·홀 없음)

두 파일의 `AREA_CD`가 조인 키다.

### 5.2 저장 방식

`congestion_area` 테이블에 코드·분류·경계와 **4개 언어 이름**을 함께 둔다. 경계는 PostGIS
`geography(Polygon,4326)`로 저장한다 — bbox로 구역을 좁히는 질의(R6)에 그대로 쓰인다.

```
congestion_area
  area_cd     varchar  PK      -- POI001. 연속하지 않는다(§5.5)
  category    varchar          -- 관광특구 · 고궁·문화유산 · 인구밀집지역 · 발달상권 · 공원
  name_ko     varchar  not null
  name_en     varchar  not null   -- 서울시 원본 ENG_NM
  name_ja     varchar
  name_zh     varchar             -- 번체
  boundary    geography(Polygon,4326) not null
```

**이름을 별도 테이블로 분리하지 않는다.** 언어가 4개로 고정이고 구역이 121건뿐이라 정규화
이득이 없고, 조회마다 조인이 붙는다.

`name_ja`/`name_zh`를 nullable로 두는 것은 폴백(R31)을 위해서다 — 서울시가 구역을 추가하면
번역이 없는 상태로 먼저 들어올 수 있다. `name_ko`/`name_en`은 원본이 항상 주므로 not null이다.

**실시간 값은 이 테이블에 저장하지 않는다.** 정적 메타데이터만 담는다.

### 5.3 적재 시점

Flyway 마이그레이션으로 적재한다. 121행이고 사실상 불변이라 배치 잡을 만들 이유가 없다.
CSV·GeoJSON 원본을 리소스로 두고 마이그레이션에서 읽거나, 변환된 SQL을 커밋한다 —
**멱등해야 한다**(R16). 재실행 시 중복이 생기면 안 된다.

CSV 첫 바이트에 **BOM이 있다**(`﻿`). 헤더 파싱 시 제거한다.

### 5.4 경계 제공

`seoulCongestionAreas`는 실시간 의존이 없는 순수 DB 조회다. 폴리곤 좌표가 크므로 응답 자체를
캐시하는 것을 고려한다 — 값이 바뀌지 않으므로 TTL을 길게 둘 수 있다.

폴리곤은 **닫힌 다각형**으로 반환한다(첫 점 = 끝 점, R17).

### 5.5 코드가 연속하지 않는다

`AREA_CD`는 POI001~POI131 범위에 121건이며 **열 개가 결번**이다 — POI022 · 028 · 057 · 062 ·
065 · 069 · 075 · 097 · 099 · 113. 서울시가 구역을 폐지한 흔적으로 보인다.

적재·검증 로직이 번호의 연속성을 가정하면 안 된다. "POI001부터 POI121까지" 같은 범위 생성은
틀린다.

### 5.6 다국어 이름 (R31)

대응표는 spec의 `area-names.md`에 121행으로 있다. 마이그레이션에 그대로 넣는다.

- **EN은 서울시 원본**(`ENG_NM`)이다. 수정하지 않는다.
- **JA/ZH는 spec에서 작성한 초안**이며 중국어는 **번체**다. 원어민 검수 전이므로, 검수 결과가
  나오면 데이터만 갱신한다(마이그레이션 추가 또는 UPDATE).
- 폴백은 **조회 시점**에 처리한다: 활성 언어 → EN → KO. 적재 시 빈 칸을 EN으로 채워두면
  나중에 실제 번역이 들어왔는지 구분할 수 없다.

**활성 언어는 `Accept-Language` 헤더에서 온다(부재 시 EN).** 계약에 `locale` 인자를 두지
않는다 — 기존 `Locale` enum이 스키마에 "인자로 받지 않는다"고 명시하고 있고, 관광지 API
전체가 이 방식이다. 지도만 인자 방식이면 클라이언트가 두 방식을 함께 관리해야 한다.

기존 `DomainLocale`과 헤더 해석 경로를 그대로 재사용한다. 새로 만들지 않는다.

## 6. 부분 실패 (R11)

`mapViewport`와 `seoulCongestion`을 **별개 최상위 필드**로 둔 것이 설계의 핵심이다. 한
리졸버의 실패가 다른 쪽에 전파되지 않는다.

서울 API 장애를 **예외로 던지지 않는다.** `degraded` 표식이 붙은 정상 응답으로 만든다
(spec §7.6). 예외로 던지면 DGS가 최상위 `errors[]`에 실어 클라이언트의 오류 분기로
들여보내고, 지도 전체가 실패한 것처럼 다뤄지기 쉽다.

예보 부재·상권 부재도 마찬가지로 오류가 아니다 — 부재로 표현한다.

## 7. 테스트 — 애플리케이션·도메인 계층만

인프라 테스트는 범위 밖이다(플랫폼 방침). 아래 단위가 수용 기준을 진다.

| 단위 | 지는 기준 |
|---|---|
| bbox 검증 도메인 로직 | R4 · R5 — 뒤집힌 bbox, 범위 밖 좌표, 면적 상한, 줌 범위 |
| 클러스터링 도메인 로직 | R2 — 상호배타, 개수 집계, 우세 카테고리 과반 규칙 |
| 상한·잘림 판정 | R3 |
| 혼잡도 단계 매핑 | R7 — 4값 매핑, 미정의 값 거절 |
| 상권 3상태 판정 | R10 — 부재 / 기본값 / 실측 |
| 캐시 신선도 판정 | R13 · R14 — 재호출 여부, 블록 독립성 |
| 구역 코드 일치 검증 | R15 |
| 좌표 매핑 | R12 — `EVENT_X`→경도, `EVENT_Y`→위도 |
| 조회 서비스 (포트 스텁) | R6 · R9 · R11 — 필터 필수, 예보 부재, degraded |
| 구역명 언어 선택 | R31 — 활성 언어별 반환, EN → KO 폴백 순서, 헤더 부재 시 EN |

`SpotCachePort`·업스트림 클라이언트 포트·`SpotQueryPort`를 스텁으로 두고 애플리케이션
서비스를 검증한다.

**인프라로만 관측 가능해 테스트하지 않는 것**: PostGIS 공간 질의의 실제 인덱스 사용 여부,
Valkey 직렬화 왕복, 실제 HTTP 호출. 이들은 명시적으로 미검증으로 남긴다 — 억지로 테스트를
만들지 않는다.

## 9. 환경 변수

정의는 spec §12에 있다. 서버가 읽는 값만 옮겨 적는다.

```yaml
ieuri:
  seoul-citydata:
    api-key:              ${IEURI_SEOUL_CITYDATA_API_KEY:}
    base-url:             ${IEURI_SEOUL_CITYDATA_BASE_URL:http://openapi.seoul.go.kr:8088}
    min-refetch-seconds:  ${IEURI_SEOUL_CITYDATA_MIN_REFETCH_SECONDS:300}   # [TBD] 실측 후 조정
    daily-call-limit:     ${IEURI_SEOUL_CITYDATA_DAILY_CALL_LIMIT:1000}
```

기존 `IEURI_TOUR_*` 관행과 같은 형태다. Valkey 설정은 기존 값을 재사용한다.

**키가 비어 있어도 기동에 실패하지 않는다.** 혼잡도 조회만 `degraded`로 응답하고 지도의
나머지는 정상 동작한다(R11). 로컬 개발에서 키 없이 지도를 띄울 수 있어야 한다.

`daily-call-limit`은 호출 수를 세어 상한에 닿으면 업스트림을 더 부르지 않고 캐시만 반환한다.
쿼터를 넘겨 차단당하는 것보다 낡은 데이터를 주는 편이 낫다. 카운터는 자정 기준으로 리셋한다.

`[TBD]` 값들은 실측이 정확하다. 정해지면 `[AMEND] SPEC-0014: ...`로 이슈에 회신한다.
