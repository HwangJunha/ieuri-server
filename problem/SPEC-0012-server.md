# SPEC-0012 서버 설계 — 인증 식별자 보호 및 provider 연결 해제

요구사항과 수용 기준은 스펙이 권위를 가진다. 이 문서는 서버가 그것을 어떻게 실현하는지만 다룬다.

## 1. 전제 확인

구현 착수 전 확인해야 한다. 스펙이 결정을 내리지 않고 남겨둔 것이 아니라, provider 문서를 대조해야 확정되는 사실이다.

**`provider_user_id`는 토큰이 아니다.** `ProviderUserId.kt`의 주석대로 provider가 부여한 영구 식별자(google sub, apple sub, kakao 회원번호)이며 자격증명이 아니다. 만료되지 않고 이 값으로 provider API를 호출할 수 없다. 현재 `SnsTokenRevokerPort.revoke(provider, providerUserId)`가 이 값을 받는 시그니처라 revoke가 가능한 것처럼 보이지만, dev 스텁이 로그를 찍기 위한 인자일 뿐이다.

따라서 확인할 것은 다음 세 가지다.

- 애플·구글·카카오 각각의 폐기·해제 API가 실제로 요구하는 자격증명이 무엇인가
- `provider_user_id`만으로 가능한 경로가 있는가. **카카오는 어드민 키 + 회원번호 방식이 있어 유일한 예외 가능성**이 있다
- 그 경로가 있다면 해당 provider는 토큰 저장(R5) 없이 R10을 만족할 수 있는가

카카오가 예외로 확인되면 R10이 R5에 의존하지 않아 구현 순서가 유연해진다.

## 2. 인증 식별자 보호 (R1·R2·R3)

### 문제의 성질

`member.provider_user_id`는 세 역할을 겸한다.

- `Provider.EMAIL` 회원에게는 로그인 식별자(= 이메일)
- SNS 회원에게는 provider가 준 영구 식별자
- `uq_member_provider_user UNIQUE (provider, provider_user_id)`의 구성 요소

`findByProviderAndProviderUserId`·`existsByProviderAndProviderUserId`가 등호 조회로 이 컬럼을 쓴다. 가입 중복 검사, 이메일 로그인, 비밀번호 재설정이 모두 이 경로다.

현재 `AesGcmEmailEncryptor`는 호출마다 임의 IV를 쓴다. 같은 평문도 매번 다른 암호문이 나오므로 그대로 적용하면 등호 조회가 절대 맞지 않고 유니크 제약도 의미를 잃는다.

### 방향

스펙은 방식을 규정하지 않는다(R1). R2가 조회 동작 보존을, R3이 기존 데이터 이전을 요구하므로 이 둘을 만족하는 방식이면 된다. 두 갈래가 있다.

1. **결정론적 변환** — 같은 평문이 항상 같은 값이 되게 한다. 조회와 유니크 제약이 그대로 동작한다. 대신 같은 이메일이 같은 값을 낳으므로 값의 동일성으로 두 계정이 같은 이메일인지 알 수 있다
2. **조회용 컬럼 분리** — `provider_user_id`는 암호문으로 두고 조회용 파생 컬럼을 따로 둔다. 유니크 제약과 인덱스를 그 컬럼으로 옮긴다

2가 더 깨끗하지만 마이그레이션과 제약 이동이 따르고, 1은 단순하지만 값의 성질이 바뀐다. 어느 쪽이든 R1·R2·R3을 함께 만족하면 스펙 위반이 아니다.

주의할 점은 **SNS 회원의 식별자는 개인정보가 아니라는 것**이다(R1 네 번째 기준). provider가 부여한 불투명 식별자이므로 보호 대상이 아니다. `Provider.EMAIL` 행만 다루면 되고, 이는 마이그레이션 범위도 좁힌다.

정규화도 함께 봐야 한다. R2의 다섯 번째 기준이 대소문자·공백만 다른 이메일의 동일 판정을 요구한다. 보호 이전에 정규화가 선행되어야 하며, 기존 동작이 이미 그런지 확인한다.

### 마이그레이션 (R3)

무중단은 요구사항이 아니다. 정식 출시 전이라 사용자가 없고, 무중단 검증 비용이 실익을 넘는다.

`Provider.EMAIL` 행만 대상이다. SNS 행은 건드리지 않는다(R3 세 번째 기준).

SPEC-0011 R7(이메일 변경)이 같은 컬럼을 갱신한다. **두 스펙이 같은 컬럼을 건드리므로 구현 순서를 조율한다.** SPEC-0011이 먼저 나가면 이메일 변경이 평문을 쓰게 되고, SPEC-0012가 먼저면 SPEC-0011이 보호된 형태로 써야 한다. 후자가 낫다.

## 3. provider 토큰 확보 (R5·R6·R7)

### 흐름

클라이언트가 `authorizationCode`를 보내면(R4) 서버가 provider와 교환해 폐기용 토큰을 얻고 저장한다. code는 일회용이며 짧게 만료된다.

교환은 provider마다 다르다. 애플은 client secret을 ES256 JWT로 직접 서명해야 하고, 구글은 client secret 문자열을 그대로 쓴다. 카카오는 어드민 키 경로가 되면 교환 자체가 불필요할 수 있다.

`Provider.EMAIL` 회원은 교환 대상이 아니다(R5 네 번째 기준).

### 저장 (R6)

토큰은 개인 자격증명이므로 암호문으로 저장한다(POL-012). 이쪽은 조회 키가 아니므로 **기존 `AesGcmEmailEncryptor`를 그대로 쓸 수 있다** — 식별자와 달리 등호 조회가 필요 없어 임의 IV가 문제되지 않는다.

저장 위치는 새 컬럼 또는 별도 테이블이다. 회원 1:1이고 provider별로 하나이므로 `member` 컬럼으로 충분해 보이나, 토큰 갱신 이력이 필요해지면 테이블이 낫다. 현재 요구사항은 이력을 요구하지 않는다.

### 실패 처리 (R7)

교환 실패가 로그인·가입을 막아서는 안 된다. provider 장애로 로그인이 불가능해지면 revoke를 위해 가용성을 희생하는 셈이다.

따라서 교환은 **인증 흐름의 곁가지**로 둔다. 실패해도 인증 명령의 결과에 영향을 주지 않고, 실패 사실만 기록한다. 이때 code와 토큰 값은 기록하지 않는다(POL-013).

## 4. 탈퇴 시 연결 해제 (R8~R11)

### 포트 시그니처

현재 `SnsTokenRevokerPort.revoke(provider: Provider, providerUserId: String)`는 **잘못된 인상을 준다.** 식별자로 revoke가 가능한 것처럼 읽히기 때문이다. 저장된 토큰을 받도록 바꾼다.

카카오가 어드민 키 경로로 확인되면 식별자만으로 충분하므로, 포트가 두 경우를 모두 표현할 수 있어야 한다. provider별 구현이 필요한 값을 각자 선택하도록 회원 정보를 넘기는 형태가 무난하다.

### 실행 위치

`MemberLifecycleService.withdraw`가 이미 `snsTokenRevoker.revoke(...)`를 호출한다. 호출 지점은 그대로 두고 구현을 채운다.

현재 호출이 회원 삭제 **앞**에 있다. 토큰이 회원 행에 저장된다면 삭제 전에 읽어야 하므로 이 순서가 맞다.

### 실패 처리 (R11)

해제 실패가 탈퇴를 막아서는 안 된다. 외부 의존 실패로 사용자의 탈퇴 권리가 방해받는 것은 받아들일 수 없다.

`withdraw`가 `@Transactional`이므로 revoke에서 예외가 나가면 회원 삭제까지 롤백된다. **예외를 안에서 흡수**해야 한다. 실패는 감사 로그에 provider와 회원 식별자로 남기고, 토큰과 이메일은 남기지 않는다(R11 세 번째 기준).

외부 호출이 트랜잭션 안에 있어 응답이 늦으면 트랜잭션이 길어진다. **대기 상한을 둔다**(R11 네 번째 기준). 상한을 넘으면 실패로 처리하고 탈퇴를 계속한다.

토큰이 없는 회원은 시도하지 않는다(R8·R9의 두 번째 기준). 클라이언트 업데이트 전에 로그인한 회원이 여기 해당한다.

## 5. 상태값 정합 (R12)

`MemberStatus`는 `ACTIVE`/`SUSPENDED` 두 값인데 `V1__create_member.sql`의 체크 제약은 `'WITHDRAWN'`도 허용한다. hard delete 방침상 쓰이지 않는 값이다.

제약에서 제거한다. 기존 행에 그 값이 있으면 제약 변경이 실패하므로 확인이 선행된다. 없을 것으로 보인다 — 어떤 코드도 이 값을 쓰지 않는다.

## 6. 자격증명 관리

스펙의 선행 조건 절에 목록이 있다. 모두 환경변수로 주입하고 코드에 두지 않는다.

애플 `.p8`은 파일이라 다루기가 다르다. 파일 경로를 주입하든 내용을 문자열로 주입하든, 저장소에 커밋되지 않아야 한다. 재다운로드가 불가능하므로 분실하면 키를 다시 만들어야 한다.

`SnsProperties`는 id_token 검증용 공개 식별자만 담고 있다. revoke 자격증명은 성격이 달라 **별도 설정 클래스**로 분리하는 편이 낫다 — 공개 식별자와 비밀을 한 클래스에 섞으면 실수로 로그에 찍기 쉽다.

## 7. 단위 테스트 대상

애플리케이션·도메인 레이어만. 어댑터·인프라는 범위 밖이다(CLAUDE.md 테스트 범위표).

| 단위 | 검증 |
|---|---|
| 식별자 보호 변환 | 평문과 불일치, 서로 다른 입력의 구분, 같은 입력의 동일 결과 (R1) |
| 이메일 가입 유스케이스 | 저장 값이 평문이 아님, SNS 식별자는 미변환 (R1) |
| 가입 중복 검사 | 기존 이메일 거절 (R2) |
| 이메일 로그인 유스케이스 | 성공, 미가입 실패, 정규화 동일 판정 (R2) |
| 비밀번호 재설정 조회 | 회원 조회 성공 (R2) |
| SNS 로그인 유스케이스 | code 있을 때 교환·저장, 없을 때 미시도, 기존 토큰 갱신 (R5) |
| SNS 로그인 유스케이스 — 실패 | 교환 실패해도 로그인 성공 (R7) |
| SNS 가입 유스케이스 | 교환 실패해도 가입 성공 (R7) |
| 토큰 저장 | 평문 미저장, 복원 일치 (R6) |
| 탈퇴 유스케이스 — 애플 | 토큰과 함께 폐기 호출, 토큰 없으면 미호출, 타 provider 미호출 (R8) |
| 탈퇴 유스케이스 — 구글 | 위와 동일 (R9) |
| 탈퇴 유스케이스 — 카카오 | 대상 지정 호출, 타 provider 미호출 (R10) |
| 탈퇴 유스케이스 — 실패 | 실패해도 탈퇴 완료, 기록 내용, 대기 상한 (R11) |
| 상태값 집합 | 도메인 enum과 허용값 일치 (R12) |

provider 클라이언트, 암호화기, 저장소는 전부 포트로 스텁한다.

**마이그레이션(R3)은 단위 테스트로 검증하지 않는다.** 실제 데이터 이전은 인프라 동작이며 애플리케이션 경계 위에서 관찰할 수 없다. 변환 함수 자체는 R1의 테스트가 덮고, 이전 결과는 실행 환경에서 확인한다.

애플 revoke JWT의 서명 유효성도 마찬가지다. 서명 로직은 어댑터에 있고 실제 검증은 애플만 할 수 있다. R8의 세 번째 기준은 "설정된 값이 사용되는지"까지만 요구하며 서명 자체의 유효성은 요구하지 않는다.

## 8. 마이그레이션

| 대상 | 내용 |
|---|---|
| `member.provider_user_id` | `EMAIL` 행의 평문 이메일을 보호된 형태로 이전. 방식에 따라 조회용 컬럼·인덱스 추가 (R1·R3) |
| provider 토큰 저장소 | 컬럼 또는 테이블 신설 (R5·R6) |
| `ck_member_status` | `'WITHDRAWN'` 제거 (R12) |

## 9. 확인 사항

- provider별 폐기·해제 API가 실제로 요구하는 자격증명. 특히 카카오가 어드민 키 + 회원번호로 토큰 없이 가능한지
- 이메일 정규화가 현재 어느 지점에서 이루어지는지, 보호 변환 전에 선행되는지
- `ck_member_status`에 `'WITHDRAWN'` 값을 가진 기존 행이 있는지
- SPEC-0011 R7(이메일 변경)과의 구현 순서. 같은 컬럼을 건드리므로 이 스펙이 먼저 나가는 편이 낫다
