## 범위 (Scope)

1. **[항목 1] termsCode enum화** — `AgreementInput.termsCode`를 `String` → GraphQL enum `TermsCode`. RoleCode는 enum화하지 않고 `assignableRoles` 조회쿼리로 대체(아래 근거).
2. **[항목 2] 자체(이메일) 회원가입 추가** — SNS 전용이던 가입에 이메일+비밀번호 가입/로그인/비밀번호 재설정을 추가. 이메일 인증으로 계정 활성화.
3. **[항목 3] 공통 응답 규약** — GraphQL `interface BaseResponse { success, userErrors }` 정의, **모든 mutation payload가 구현**.
4. **[항목 4] 페이지네이션 규약** — **커서 페이지네이션(Relay Connection)을 기본**으로 공통 인프라 신설. offset은 공통 규약으로 남겨두되 필요한 화면에서만 사용.
5. **[항목 5] `handle` → `Service` 네이밍** — `XxxHandler` → `XxxService`, `application/service/` 패키지로 이동, `handle()` → 의미 있는 메서드명.
6. **[항목 6] 기능 통합** — 조각난 단일-메서드 유스케이스/핸들러를 `MemberQueryUseCase`(me/member/members)처럼 **공통으로 묶을 수 있는 것은 전부** 응집도 있는 서비스로 통합하고 의미 있는 함수로 정리.

**명시적 제외**: 실제 SMTP 운영 설정, SNS 실검증, Valkey 토큰 저장소(Step 6 이월).

## [항목 1] termsCode enum · roleCode 조회쿼리

### termsCode → enum (채택)
- 스키마: `enum TermsCode { SERVICE  PRIVACY  LOCATION  MARKETING }` — `R__seed_terms.sql` 시드 코드와 1:1 일치.
- `input AgreementInput { termsCode: TermsCode!  agreed: Boolean! }`.
- **경계 매핑**: 리졸버가 `TermsCode` enum → `String`으로 변환해 Command에 담는다. **도메인(`Agreement.termsCode`)은 String 유지** — 약관은 버전 관리·시드 주도이므로 도메인은 순수(데이터주도)하게 둔다. enum은 프런트 DX 용도로 스키마 경계에만 존재.
- **트레이드오프(문서화)**: 새 약관 코드 추가 시 시드 + 스키마 enum 동시 수정 필요. 약관 코드 집합은 안정적이라 수용. 활성 약관 목록/버전은 여전히 DB 주도이며, 가입 화면용 `activeTerms` 조회는 별도(선택).

### roleCode → enum 미채택, 조회쿼리로 대체 (채택)
- **근거**: Step 4 RBAC는 "코드 변경 없이 시드/관리로 역할 추가"가 핵심 원칙. RoleCode를 enum으로 박으면 새 역할을 시드해도 스키마를 안 고치면 `assignRole` 불가 → 데이터주도 확장성 파괴.
- 대신 **`assignableRoles: [RoleInfo!]!`** 조회쿼리 신설(권한 `role:assign` 필요). `type RoleInfo { code: String!  name: String!  description: String }`. 프런트는 이 목록으로 드롭다운을 렌더 → 하드코딩 없이 동적 인지.
- `assignRole` / `revokeRole`의 `roleCode`는 **String 유지**. 존재하지 않는 코드는 기존 `RoleNotFoundException`으로 처리(→ 항목 3에서 userErrors 매핑).

## [항목 2] 자체(이메일) 회원가입

### 개요
- 이메일을 아이디로 사용, 비밀번호 설정, **이메일 인증으로 활성화**(휴대폰/실명 인증 없음), 약관 동의 + 만 14세 확인.
- 적용: `Provider.EMAIL` 신설, `provider_user_id = 정규화된 이메일`, 비밀번호는 **단방향 해시** 저장, 가입 직후 `email_verified=false` → 인증코드 검증 시 활성화. 미인증 계정은 `loginEmail` 거부.
- 포함 플로우: **가입 / 로그인 / 이메일 인증(기존 공유) / 비밀번호 재설정**.

### 도메인
- `Provider`에 `EMAIL` 추가.
- 신규 VO `PasswordHash(value: String)` — 이미 해시된 값만 보관(도메인은 인코딩 방식 모름).
- `Member`에 nullable `passwordHash: PasswordHash?` 추가(SNS 회원은 null). `Member.registerByEmail(...)` 팩토리 신설: `emailVerified=false` 고정, 필수 약관/만14세 불변식은 기존과 동일 재사용. 기존 `register`는 `registerBySns`로 의미 명확화(항목 6과 연동). 비밀번호 변경용 도메인 메서드 `changePassword(newHash)` 추가.
- 비밀번호 **일치 판정은 도메인이 아니라 애플리케이션**에서 `PasswordEncoderPort.matches(raw, hash)`로 수행(도메인 순수성 유지).

### 비밀번호 해시 (단방향 · 키 사용)
- **알고리즘**: BCrypt(work factor 10~12) — 업계 표준 단방향 해시(솔트 내장). 여기에 **서버 비밀키(pepper)** 를 앞단에 적용한다: `bcrypt( HMAC-SHA256(rawPassword, PEPPER) )`.
  - pepper는 DB에 없고 설정에만 존재 → **DB 유출 시에도 추가 방어**(OWASP 권고 pepper 패턴).
- **키 관리**: 기존 `ieuri.encryption {key, pepper}` 패턴과 동일하게 신설 `ieuri.password.pepper`. **prod는 env 주입(기본값 없음, fail-fast)**, **로컬은 `application-local.yml`에 개발 전용 생성값**을 둬 로컬에서만 사용. 값은 base64 32바이트를 적당히 생성.
- 어댑터 `PepperedBCryptPasswordEncoder`(infra)가 `PasswordEncoderPort` 구현. Spring Security `BCryptPasswordEncoder` + HMAC 조합.
- **비밀번호 정책(경계 검증)**: 영문·숫자·특수문자 **3종 모두 포함, 최소 8자**. (개인정보보호법 「개인정보의 안전성 확보조치 기준」: 3종 조합 시 8자 이상 충족.) 형식검증은 `Command` 생성 시점. 평문 비밀번호는 로그/이벤트/감사에 절대 미기록.

### 애플리케이션 / 포트
- 신규 아웃바운드 포트 `PasswordEncoderPort { encode(raw): String; matches(raw, hash): Boolean }`.
- 가입: `MemberRegistrationService.registerByEmail(command)` — 이메일 중복확인(`existsByProviderAndProviderUserId(EMAIL, email)`) → 비밀번호 형식검증 → 해시 → `Member.registerByEmail` → 저장 → USER 역할 부여 → 인증코드 발급(기존 `EmailVerification`/`VerificationEmailRequested` 재사용) → 감사·이벤트.
- 로그인: `AuthTokenService.loginByEmail(command)` — 이메일로 회원 조회 → `passwordHash` 존재 확인(EMAIL 계정만) → `matches` → **`emailVerified=true` 요구**(미인증 거부) → 정지 상태 판정(기존 로직 재사용) → 토큰 발급(`TokenIssuer` 재사용, perms flatten).
- 이메일 검증/재발송은 기존 `verifyEmail`/`resendVerification` 그대로 공유(SNS·EMAIL 공통).

### 비밀번호 재설정 (이번 포함)
- 흐름: `requestPasswordReset(email)` → (EMAIL 계정 존재 시) 재설정 코드 발급·이메일 발송 / `resetPassword(resetId, code, newPassword)` → 코드 검증 → 새 해시 저장(`changePassword`) → 재설정 토큰 소진 → **해당 회원의 refresh 토큰 전부 폐기**(세션 무효화).
- **계정 열거 방지**: `requestPasswordReset`는 계정 유무와 무관하게 항상 동일 성공 응답.
- 도메인: `EmailVerification`을 그대로 재사용하지 않고 목적이 다른 **`PasswordReset` 애그리거트**(memberId, codeHash, ttl, maxAttempts, consumed)를 신설 — 애그리거트 목적 단일화. 코드 발급/검증 로직 형태는 `EmailVerification`을 참고(중복은 공통 코드로 최소화).
- 마이그레이션 `V10__create_password_reset.sql`(도메인 내 FK 허용): `password_reset(id, public_id, member_id→member, code_hash, expires_at, consumed_at, attempts, max_attempts, created_at)`.

### GraphQL (Mutation)
- **rename**: `registerMember`(SNS) → `registerSnsMember`, `login`(SNS) → `loginSns` (클라이언트 미연결이라 안전).
- 신규:
  - `registerEmailMember(input: RegisterEmailMemberInput!): RegisterEmailMemberPayload!`
    - `RegisterEmailMemberInput { email, password, ageVerified, agreements: [AgreementInput!]! }`
  - `loginEmail(input: LoginEmailInput!): AuthTokenPayload!` — `LoginEmailInput { email, password }`
  - `requestPasswordReset(input: RequestPasswordResetInput!): RequestPasswordResetPayload!`
  - `resetPassword(input: ResetPasswordInput!): ResetPasswordPayload!`

### 마이그레이션 (Flyway)
- `V9__add_email_registration.sql`:
  - `ALTER TABLE member ADD COLUMN password_hash VARCHAR(255)` (nullable — SNS 회원 null).
  - `ck_member_provider` 제약 **DROP 후 재생성**하여 `'EMAIL'` 허용: `CHECK (provider IN ('APPLE','GOOGLE','KAKAO','EMAIL'))`.
  - `CHECK`로 "provider='EMAIL'이면 password_hash NOT NULL" 부분 제약 추가.
- `V10__create_password_reset.sql`: 위 password_reset 테이블. 탈퇴 시 자식 삭제 순서에 포함.
- 적용된 마이그레이션 불변 규칙 준수: V8까지 immutable, V9/V10 신규.

### 보안 규칙
- `loginEmail`/`resetPassword` 실패 메시지는 계정 존재 여부를 드러내지 않도록 통일.
- `SecurityConfig`에 `registerEmailMember`/`loginEmail`/`requestPasswordReset`/`resetPassword`를 permitAll(인증 불요)로 추가.

## [항목 3] 공통 응답 규약 — BaseResponse (GraphQL interface)

```graphql
interface BaseResponse {
    success: Boolean!
    userErrors: [UserError!]!
}
type UserError {
    "머신 판독용 코드(예: MEMBER_ALREADY_REGISTERED, REQUIRED_TERMS_NOT_AGREED)."
    code: String!
    "사용자 노출 메시지."
    message: String!
    "입력 필드 경로(해당 시). 예: input.email"
    field: String
}
```

- **적용 대상: 모든 mutation payload가 `implements BaseResponse`** (전부 묶음). `AuthTokenPayload`/`LogoutPayload` 포함. 예:
  ```graphql
  type AuthTokenPayload implements BaseResponse {
      success: Boolean!
      userErrors: [UserError!]!
      accessToken: String
      refreshToken: String
      tokenType: String
      accessTokenExpiresIn: Int
      refreshTokenExpiresIn: Int
  }
  ```
  성공 데이터 필드는 실패 시 null이 될 수 있으므로 nullable로 완화(성공 시 채움).
  대상: registerSns/registerEmail, verifyEmail, resendVerification, loginSns/loginEmail, refreshToken, logout, withdraw, suspend, reactivate, assignRole, revokeRole, requestPasswordReset, resetPassword.
- **오류 이원화 규약(중요)**:
  - **예상 가능한 도메인/검증 실패**(중복가입, 필수약관 미동의, 코드 불일치, 역할 없음, 비밀번호 형식 등) → payload의 `userErrors`로 반환(`success=false`). 최상위 `errors` 오염 안 함.
  - **진짜 예외**(인증/인가 실패 403, 서버 오류, 내부 NotFound) → DGS `DataFetcherExceptionHandler`로 최상위 GraphQL error 반환.
- **구현 방식**: `common/`(공유 커널)에 `BaseResponse`/`UserError` 매핑 규약과 예외→`UserError` 매퍼를 두고, 리졸버는 유스케이스 호출을 감싸 도메인 예외를 userErrors로 변환하는 얇은 공통 함수 사용.
- **트레이드오프**: 기존 payload에 `userErrors` 필드가 추가되고 성공 데이터 필드가 nullable로 바뀜(전 resolver 영향). 성공 응답도 규약 통일로 클라 처리 일관성↑.

## [항목 4] 페이지네이션 규약 — 커서 기본, offset 보조

**커서(Relay Connection)를 기본**으로 하고, offset은 공통 규약으로 남겨 페이지번호가 꼭 필요한 화면에서만 사용한다.

### Cursor (기본)
```graphql
type PageInfo { hasNextPage: Boolean!  hasPreviousPage: Boolean!  startCursor: String  endCursor: String }
type MemberConnection { edges: [MemberEdge!]!  pageInfo: PageInfo!  totalCount: Int }
type MemberEdge { cursor: String!  node: MemberSummary! }
# 관리자 회원 목록(기본): members(status, roleCode, first: Int = 20, after: String): MemberConnection!
```
- **애플리케이션 공통 read model**: `common/`에 `CursorPage<T>(edges, pageInfo, totalCount)`, `CursorQuery(first, after)`, `Cursor` 인코딩 유틸(정렬키 base64).
- **QueryDSL keyset 페이지네이션**: `WHERE id < :afterId ORDER BY id DESC LIMIT first+1` (id 단일 키; 안정정렬). `first+1`로 hasNextPage 판정.
- 기존 `members`(offset)는 **커서로 전환**한다(관리자 목록 기본 커서). 페이지번호 UI가 실제로 필요해지면 그때 offset 변형을 추가.

### Offset (보조 — 공통 규약만 유지)
```graphql
interface Page { page: Int!  size: Int!  totalElements: Int!  totalPages: Int! }
# 필요 화면에서 XxxPage implements Page 로 구현
```
- 공통 인터페이스·read model(`OffsetPage<T>`)만 정의해 두고, 실제 적용은 요구가 생길 때.

## [항목 5] `handle` → `Service` · application/service 패키지

- 규칙 변경: **`XxxHandler` → `XxxService`**, 위치 `application/service/`. `handle(command)` → 의미 있는 메서드명.
- 현재 핸들러는 `application/` 루트에 흩어져 있음(CLAUDE.md의 `application/command/` 규약과도 이미 불일치). 이번에 `application/service/`로 정리.
- **패키지 역할 재정의**:
  - `application/command/` = Command 입력 객체만.
  - `application/query/` = read DTO/조회 모델만.
  - `application/service/` = 유스케이스 구현체(`*Service`, command·query 공통).
- **CLAUDE.md 갱신(승인됨)**: "command handlers는 application/command" → "유스케이스 구현체는 application/service의 `*Service`". 이 리팩토링과 함께 CLAUDE.md 수정.

## [항목 6] 기능 통합 — 공통으로 묶을 수 있는 것은 전부 통합

`MemberQueryUseCase`(me/member/members)·`RoleUseCase`(assign/revoke) 패턴을 나머지 조각난 유스케이스에도 전면 적용한다.

### 현재 (조각남)
- `RegisterMemberUseCase.handle`, `VerifyEmailUseCase.handle`, `ResendVerificationUseCase.handle` (각각 별도)
- `LoginHandler`, `RefreshTokenHandler`, `LogoutHandler` (각각 별도)
- `WithdrawMemberHandler`, `SuspendMemberHandler`, `ReactivateMemberHandler` (각각 별도)
- `RoleHandler`(통합됨), `MemberQueryHandler`(통합됨)

### 목표 (통합 후) — port/in + application/service
| 유스케이스(port/in) | 서비스(application/service) | 메서드(의미 있는 함수) |
|---|---|---|
| `MemberRegistrationUseCase` | `MemberRegistrationService` | `registerBySns`, `registerByEmail`, `verifyEmail`, `resendVerification`, `requestPasswordReset`, `resetPassword` |
| `AuthTokenUseCase` | `AuthTokenService` | `loginBySns`, `loginByEmail`, `refresh`, `logout` |
| `MemberLifecycleUseCase` | `MemberLifecycleService` | `withdraw`, `suspend`, `reactivate` |
| `RoleUseCase` | `RoleService` | `assign`, `revoke` (+ 조회 `assignableRoles`) |
| `MemberQueryUseCase` | `MemberQueryService` | `me`, `member`, `members`(커서) |

- 리졸버도 대응 통합(`MemberMutationResolver`/`AuthTokenMutationResolver`/`MemberLifecycleMutationResolver`/`RoleMutationResolver`/`MemberQueryResolver`)하되 인바운드 어댑터는 얇게 유지.
- 통합은 **도메인 응집도 기준**(가입 계열, 토큰/인증 계열, 생명주기 계열)으로 묶고, 관련 없는 것을 한 서비스에 몰지 않는다.

## PR 분할안 (리뷰 가능 단위, dev 브랜치 기준)

작을수록 리뷰가 쉬우므로 순서대로 별도 feature 브랜치 권장:
