# SPEC-0019 · 검색 노드 작업 지시서

> 이 문서는 **운영자가 직접 실행할 작업**을 정리한 것이다. 서버 코드는 이 문서의 결정을 전제로
> 하되, 여기 적힌 DDL과 매니페스트 수정은 사람이 수행한다.

## 0. 결론부터

**번역 테이블(`spot_catalog_translation`)에 BM25 인덱스를 건다.** 메인 DB의 `spot` 테이블은
건드리지 않는다.

이유는 **논리 복제가 행만 옮기고 구조는 옮기지 않기 때문이다.** 검색 노드에만 컬럼을 만들면
복제가 채워주지 않아 영원히 비어 있다. 그렇다고 메인 `spot`에 언어별 제목·주소 컬럼을 만들면
`spot_catalog_translation`과 같은 값이 두 곳에 저장되고, 번역이 갱신될 때마다 어긋난다.

번역 테이블은 **이미 언어별 카드(제목 + 주소)를 온전히 갖고 있으므로** 거기에 인덱스를 걸면
중복 저장도 없고 조인도 필요 없다.

## 1. 왜 조인으로 풀 수 없는가

pg_search는 `@@@`·`pdb.score()`·`ORDER BY`·`LIMIT`이 **전부 같은 질의 레벨**에 있어야 인덱스를
탄다. 조인·서브쿼리·CTE가 끼면 인덱스 푸시다운이 깨지거나
`query is incompatible with @@@ operator`로 실패한다(`db/search-node/V2` 헤더에 기록됨).

그래서 아래는 **불가능하다:**

```sql
-- 이렇게 쓰면 인덱스를 타지 못한다
FROM spot s
JOIN spot_catalog_translation t ON t.catalog_id = s.catalog_id
WHERE t.title @@@ '...'
```

번역 테이블 단독으로 질의해야 하고, 그러려면 그 테이블이 검색에 필요한 값을 갖고 있어야 한다.
제목과 주소는 이미 있다 — **좌표만 없다.**

## 2. 좌표를 어떻게 할 것인가

거리 필터(`ST_DWithin`)와 거리 정렬이 1단계 질의에 함께 들어가야 한다. 전국에서 관련도 상위
N개를 뽑고 2단계에서 반경으로 거르면, 반경 밖이 대부분이라 결과가 비어 보인다(실측: 기본 반경
20km 안에 spot이 12,000개가 넘는다 — V34).

**따라서 번역 테이블에 좌표를 복사한다.** `community_post_spot`이 좌표를 복사해 둔 것(V34)과
같은 판단이며, 이 저장소에 선례가 있다.

> **좌표는 언어와 무관하다.** 같은 카탈로그의 4개 언어 행이 같은 좌표를 갖는다. 중복이지만
> 원본(`spot`)이 갱신되면 배치가 함께 갱신한다 — 제목·주소와 같은 경로다.

## 3. 메인 DB에 필요한 것 (서버가 마이그레이션으로 처리 · 아직 미작성)

```sql
-- 번역 테이블에 좌표를 둔다. 검색 노드가 이 값을 복제로 받는다.
ALTER TABLE spot_catalog_translation
    ADD COLUMN map_x DOUBLE PRECISION,
    ADD COLUMN map_y DOUBLE PRECISION,
    ADD COLUMN location geography(Point, 4326);

-- spot 테이블과 같은 방식: 트리거가 map_x/map_y에서 파생시킨다.
CREATE OR REPLACE FUNCTION spot_catalog_translation_sync_location() RETURNS trigger AS $$
BEGIN
    NEW.location := ST_MakePoint(NEW.map_x, NEW.map_y)::geography;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_spot_catalog_translation_sync_location
    BEFORE INSERT OR UPDATE OF map_x, map_y ON spot_catalog_translation
    FOR EACH ROW EXECUTE FUNCTION spot_catalog_translation_sync_location();
```

**`ST_MakePoint`는 (경도, 위도) 순서다** — 뒤집으면 조용히 틀린다.

## 4. 검색 노드에 필요한 것 (직접 실행)

### 4.1 테이블 생성

**컬럼 정의는 메인과 문자 단위로 같아야 한다.** 어긋나면 복제가 조용히 멈추고, 앱은 정상으로
보이는데 검색 결과만 낡아간다.

```sql
CREATE TABLE spot_catalog_translation (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    catalog_id BIGINT       NOT NULL,
    language   VARCHAR(2)   NOT NULL,
    title      VARCHAR(255) NOT NULL,
    address    VARCHAR(500),
    source     VARCHAR(20)  NOT NULL,
    map_x      DOUBLE PRECISION,
    map_y      DOUBLE PRECISION,
    location   geography(Point, 4326),
    created_at TIMESTAMPTZ  NOT NULL,
    updated_at TIMESTAMPTZ  NOT NULL,
    CONSTRAINT uq_spot_catalog_translation UNIQUE (catalog_id, language),
    CONSTRAINT ck_spot_catalog_translation_language CHECK (language IN ('EN','KO','JA','ZH')),
    CONSTRAINT ck_spot_catalog_translation_source CHECK (source IN ('OFFICIAL','MACHINE'))
);

-- 거리 필터·정렬.
CREATE INDEX idx_sct_location ON spot_catalog_translation USING GIST (location);
```

> **트리거를 두지 않는다.** 복제로 `location` 값이 그대로 넘어오므로, 두면 같은 값을 두 번 쓴다
> (검색 노드 `spot` 테이블과 같은 판단 — `V1` 주석 참조).
>
> **FK도 두지 않는다.** `spot_catalog` 테이블을 여기 만들지 않는다면 그릇 없는 FK가 되어
> 복제된 행이 전부 거부된다.

### 4.2 BM25 인덱스

기존 `idx_spot_bm25`(spot 테이블)는 **그대로 둔다** — 되돌릴 때 필요하고, 테이블이 다르므로
"테이블당 인덱스 1개" 제약에 걸리지 않는다.

```sql
CREATE INDEX idx_sct_bm25 ON spot_catalog_translation
USING bm25 (
    id,
    -- 한국어(KoDic). 별칭 없는 기본 필드 — KO가 가장 흔한 경로다.
    (title::pdb.lindera(korean)),
    (title::pdb.lindera(japanese, 'alias=title_ja')),
    (title::pdb.lindera(chinese, 'alias=title_zh')),
    (title::pdb.simple('alias=title_en')),
    -- 주소는 형태소가 아니라 n-gram이다. 도로명·지명은 사전 기반 분석이 잘 맞지 않는다
    -- ("두산로 71" → {두산, 로, 71} vs 질의 "두산로" → {두, 산로} — 겹치는 토큰이 없다).
    (coalesce(address, '')::pdb.ngram(2, 3))
)
WITH (key_field = 'id');
```

기존 `spot`의 BM25 인덱스와 **토크나이저 구성이 같다** — 검색 품질이 달라지지 않게 한다.

## 5. 복제 설정 (`ieuri-manifest`)

CNPG `Publication` CRD의 테이블 목록에 **`spot_catalog_translation`을 추가**한다.
파일: `infra/cnpg/cluster/templates/logical-replication.yaml`

현재 발행 대상: `spot`, `spot_festival`, `spot_reaction`
추가 후: `spot`, `spot_festival`, `spot_reaction`, **`spot_catalog_translation`**

`spot_catalog` 본체는 **복제하지 않아도 된다** — 검색이 `catalog_id`만 있으면 되고, 카드 값은
번역 테이블에 다 있다.

> **선행 조건**: `problem/SPEC-0013-남은-단계.md`에 논리 복제 구독이 `❌ 실패 (권한)`으로
> 기록돼 있다(`permission denied to start WAL sender`). 그것이 먼저 풀려야 이 작업이 의미를
> 갖는다. 지금 검색 노드의 실사용 테이블은 0개다.

## 6. 바뀔 조회 쿼리 (서버가 반영 · 아직 미작성)

`SpotSearchJdbcAdapter`의 검색 질의가 이렇게 바뀐다:

```sql
-- 지금: spot 테이블, language로 격리
FROM spot s
WHERE s.language = ? AND s.title::pdb.alias('title_ja') @@@ ?

-- 바뀐 뒤: 번역 테이블. 조인 없음(평면 질의 유지)
SELECT t.catalog_id, t.title, t.address, t.map_x, t.map_y,
       ST_Distance(t.location, ST_MakePoint(?, ?)::geography) AS distance_meters,
       pdb.score(t.id) / (1 + ST_Distance(t.location, ST_MakePoint(?, ?)::geography) / 5000.0) AS relevance
FROM spot_catalog_translation t
WHERE t.language = ?
  AND (t.title::pdb.alias('title_ja') @@@ ?::pdb.boost(3)
       OR coalesce(t.address, '') @@@ ?::pdb.boost(0.2))
  AND ST_DWithin(t.location, ST_MakePoint(?, ?)::geography, ?)
ORDER BY relevance DESC, t.id ASC
LIMIT ? OFFSET ?
```

**`language = ?`는 그대로 남는다** — 인덱스가 언어를 가르지 않으므로 언어 격리는 전적으로 이
조건이 담당한다. 다만 이제 그 조건이 "그 언어의 spot 행이 있는가"가 아니라 **"그 언어의 제목이
있는가"**를 뜻한다. 번역된 카탈로그가 검색에 걸리는 것이 이 변경의 목적이다.

`category`·`copyright`·`thumbnail_image_url`은 번역 테이블에 없으므로, 검색 결과의
`catalog_id`로 2단계 조회를 한다. **거리 필터가 1단계에서 이미 걸렸으므로** 2단계는 이미 좁혀진
집합에 대한 단순 조회이며, 앞서 우려한 "상위 N개를 뽑고 거른다" 문제가 생기지 않는다.

## 7. 실행 순서

```
1. 복제 권한 해결 (SPEC-0013)          ← 선행 조건
2. 메인: 번역 테이블에 좌표 컬럼 추가   ← 서버 마이그레이션 (미작성)
3. 검색 노드: §4.1 테이블 생성
4. ieuri-manifest: publication에 테이블 추가
5. 복제 확인 (행 수 대조)
6. 검색 노드: §4.2 BM25 인덱스 생성
7. 서버: 검색 쿼리 전환 (미작성)
```

**6번을 3~5번보다 먼저 하면 안 된다** — 빈 테이블에 BM25 인덱스를 만드는 것 자체는 되지만,
복제가 시작되면 대량 INSERT가 인덱스를 타면서 느려진다.

## 8. 이 문서가 다루지 않는 것

- `popularSpots`·`ongoingFestivals` — 이 둘은 제목을 `spot`에서 가져오므로 같은 전환이
  필요하지만, 검색과 달리 **조인이 가능하다**(BM25를 쓰지 않는다). 복제 대상이 정해진 뒤
  별도로 처리한다.
- `spot` 테이블의 BM25 인덱스 제거 — 전환이 검증된 뒤에 판단한다. 그때까지 두 인덱스가
  공존하며, 디스크 외의 비용은 없다.
