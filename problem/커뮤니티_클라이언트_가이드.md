# 커뮤니티(SPEC-0010) — 클라이언트 구현 가이드

서버 구현이 끝났다. 이 문서는 앱(ieuri-k-trip-spot#32)이 붙일 때 필요한 계약과 제약을 담는다.
스펙 원문은 `Specs/SPEC-0010/spec.md`, 서버 설계는 `problem/SPEC-0010-server.md`에 있다.

**계약이 스펙 초안(`contract.graphql`)과 다른 곳이 몇 군데 있다.** §1에 먼저 정리했으니
초안을 보고 작업을 시작했다면 그 부분부터 확인할 것.

---

## 1. 스펙 초안과 달라진 점 (먼저 읽을 것)

초안대로 만들면 컴파일이 안 되거나 런타임에 빈 화면이 나오는 항목이다. 근거는 이슈 #45에 있다.

| 초안 | 최종 | 이유 |
|---|---|---|
| `spotPosts(spotId:)`·`nearbyPosts(...)` | **`posts(...)` 하나로 통합** | 반환 형태와 필터가 같아 나눌 이유가 없었다. 인자 조합이 범위를 정한다 |
| `Post.spot: PostSpot!` | `Post.spot: PostSpot` (**nullable**) | 장소 없이 카테고리만으로도 글을 쓴다 |
| `CreatePostInput.spotId` 필수 | **`category` 필수 + `spotId` 선택** | 위와 같음 |
| `topic` (질문/팁/후기…) | **삭제. `tags`(사용자 입력)로 대체** | 고정 다섯 종류가 실제 글을 담지 못했다 |
| (없음) | `confirmPostImageUploads` 뮤테이션 | 업로드 검증·이동 단계가 초안에 없었다. **사진 흐름이 4단계가 된다** |
| (없음) | `PostImageUploadRequest.contentLength` | 크기를 서명에 넣어야 위조·초과 업로드를 막는다 |
| 사진 1장씩 발급·확인 | **발급·확인 모두 다중** | 5장에 왕복 15회는 과했다 |
| (없음) | `deletePostImage` | 앱이 올린 사진을 뺄 통로가 없었다 |
| `CreatePostPayload.post` | `postId` 추가, `post`는 **항상 null** | 지연 필드 때문에 생성 응답에서 조립할 수 없다 |
| `discoveryTiles` 쿼리 | **`communityChips`로 대체** | 앱별 상단 구성을 서버가 내려준다 |
| (없음) | **`Post.title` 필수 추가** | 디자인 변경(당근 동네생활). 카드에서 볼드로 표시 |
| (없음) | **`Post.category` 필수** | 상단 추천 칩이 거르는 축. 글에 직접 저장된다 |

**`TOPIC_REQUIRED` 에러는 존재하지 않는다** — `topic` 자체가 없어졌다.

## 1-2. 디자인 변경(당근 동네생활)에 따른 계약

카드 구조가 바뀌면서 두 가지가 추가됐다.

**(1) 글에 제목이 생겼다.** `title`(1~50자, 필수) + `body`(1~500자, 필수).
카드는 `[태그] / **제목(볼드)** / 본문 / spot · 좋아요 · 댓글` 구조다.

```graphql
createPost(input: {
  category: TOURIST_SPOT,          # 필수
  spotId: 11094,                   # 선택 — 없으면 장소 없는 글
  tags: ["야간개장", "한복"],       # 사용자 입력. 최대 5개, 빈 배열 가능
  title: "경복궁 야간개장 후기",     # 신규 필수
  body:  "한복 입고 가면 무료예요",
  photoKeys: []
})
```

새 에러 코드 2종: `POST_TITLE_REQUIRED`, `POST_TITLE_LENGTH_INVALID`.

**(2) 상단 추천 칩은 카테고리로 거른다.**

```graphql
posts(latitude:, longitude:, category: RESTAURANT)   # 맛집 관련 글만
```

`TargetCategory`는 tourism의 `SpotCategory`와 값이 같다(TOURIST_SPOT · CULTURAL_FACILITY ·
FESTIVAL_EVENT · TRAVEL_COURSE · LEISURE_SPORTS · LODGING · SHOPPING · RESTAURANT · TRANSPORT).

- **글에 직접 저장되는 값이다.** 작성 화면에서 사용자가 고른다(필수)
- 장소를 골랐다면 **그 장소의 카테고리를 기본값으로 제안**할 것 — `PostSpot.category`가 그 용도다
- `tags`와는 **다른 축이다.** 카테고리는 고정 9종, 태그는 자유 입력이며 둘 다 필터로 쓸 수 있다
- 장소 유무와 무관하게 걸린다 — 장소 없는 글도 칩으로 잡힌다

**(3) 카드 오른쪽 상단 ⋮ 메뉴** — 서버 API는 아래가 준비돼 있다.

| 메뉴 | API | 노출 조건 |
|---|---|---|
| 이 사용자 차단하기 | `blockUser(targetMemberId:)` | 남의 글일 때 |
| 이 글 신고하기 | `reportContent(targetType: POST, targetId:)` | 남의 글일 때 |
| 삭제 | `deletePost(postId:)` | `ownedByViewer: true` |
| 수정 | `editPost(postId:, title:, body:, photoKeys:)` | `ownedByViewer: true` **이고** `hidden: false` |

**수정에는 두 가지 제약이 있다.**

1. **제목·본문·사진만 바꾼다.** 카테고리·장소·태그는 수정할 수 없다 — 카테고리나 장소가
   바뀌면 글이 다른 피드로 순간이동한다
2. **숨겨진 글(`hidden: true`)은 수정할 수 없다.** `POST_NOT_EDITABLE`이 온다.
   신고가 쌓여 숨겨진 글을 다른 내용으로 바꿔치기하면 신고 기록이 사유와 무관한 글을
   가리키게 되기 때문이다. 작성자에게는 자기 숨김 글이 보이므로 **⋮ 메뉴에서 수정을
   비활성화**하고 이유를 안내하는 편이 낫다

수정된 글은 `edited: true`로 내려온다 — 카드에 "수정됨"을 표시할 것. 수정 이력은 보관하지 않는다.

**탐색 타일(`discoveryTiles`)은 삭제됐다.** 대신 `communityChips`가 상단 구성을 내려준다.

### 상단 칩 — `communityChips`

```graphql
query { communityChips { category position } }
```

```json
{ "communityChips": [
  { "category": "RESTAURANT",     "position": 0 },
  { "category": "FESTIVAL_EVENT", "position": 1 },
  { "category": "TOURIST_SPOT",   "position": 2 } ] }
```

- **표시 문구는 서버가 주지 않는다.** `RESTAURANT` → "맛집"/"Food"/"グルメ" 매핑은 앱이 한다
  (`SpotCategory`와 같은 방식)
- `position` 오름차순으로 이미 정렬돼 있다. 그대로 그리면 된다
- 칩을 누르면 → `posts(latitude:, longitude:, category: $category)`
- **구성은 앱마다 다르다.** 아래 `X-App-Key` 참조
- 구성이 없는 앱이면 **빈 목록**이다. 오류가 아니므로 칩 영역이 비는 레이아웃을 허용할 것

### `X-App-Key` 헤더 — 모든 요청에 붙일 것

```
X-App-Key: k-trip-spot
```

앱이 여러 개 출시되면 상단 구성이 서로 달라야 해서 서버가 어느 앱인지 알아야 한다.
**헤더가 없으면 기본 앱(`k-trip-spot`)으로 간주**하므로 지금 당장 붙이지 않아도 동작하지만,
두 번째 앱이 나오는 순간 문제가 되니 처음부터 붙이는 편이 낫다.

- 인증과 무관하다 — 비로그인 요청에도 붙인다
- 값이 이상해도 요청이 깨지지 않는다(기본 앱으로 폴백)
- 지금은 칩 구성에만 쓰이지만 앞으로 앱별로 갈리는 것이 생기면 같은 헤더를 쓴다

## 2. 전체 API 목록

### 조회

```graphql
# 피드 하나. 인자 조합이 범위를 정한다
posts(
  spotId: ID                                 # 이 장소에 붙은 글 (spot 상세)
  latitude: Float, longitude: Float          # 좌표 반경 (커뮤니티 탭)
  radiusMeters: Int = 20000
  category: TargetCategory                   # 상단 칩
  tag: String                                # 태그 필터
  first: Int = 20, after: String
): PostConnection!

post(id: ID!): Post          # 차단·숨김이면 null
```

**`posts` 하나로 통합됐다**(기존 `targetPosts`·`nearbyPosts`). 반환 형태와 필터가 같아서
쿼리를 나눌 이유가 없었다 — 인자만 다르게 준다:

```graphql
# spot 상세의 글 목록
posts(spotId: 11094)

# 커뮤니티 탭 (내 주변)
posts(latitude: 37.5665, longitude: 126.9780, radiusMeters: 5000)

# 상단 칩을 누른 상태
posts(latitude: 37.5665, longitude: 126.9780, category: RESTAURANT)

# 카테고리만으로 — 좌표 없이 전체에서 거른다
posts(category: RESTAURANT)

# 태그로
posts(tag: "야경")

# 전체 피드
posts
```

- `latitude`·`longitude`는 **함께** 줘야 한다. 하나만 주면 무시된다
- `spotId`와 좌표를 둘 다 주면 **`spotId`가 이긴다**(좌표는 무시)
- `radiusMeters`는 좌표를 줄 때만 의미가 있다
- **`category`·`tag`는 위 범위와 독립이다** — 좌표 없이 단독으로도 걸린다

```graphql
blockedUsers(first: Int = 20, after: String): BlockedUserConnection!
communityChips: [CommunityChip!]!
```

## 3. 사진 업로드 — 4단계, 순서를 지킬 것

**서버는 이미지 바이트를 받지 않는다.** 앱이 R2로 직접 PUT한다. 이 경로만 GraphQL 예외다.

```
1. createPostImageUploadUrls(images: [{contentType, contentLength}, ...])   ← 여러 장을 한 번에
      → uploadUrls: [{uploadUrl, objectKey("pending/..."), expiresAt}, ...]  요청과 같은 순서
2. 각 uploadUrl로 R2에 직접 PUT           ← GraphQL 아님. 순수 HTTP PUT (장마다 1회)
3. confirmPostImageUploads(objectKeys: [...])                              ← 여러 장을 한 번에
      → confirmed: ["images/...", ...]     ← 최종 키. 이걸 써야 한다
        failed:    [{objectKey, code}]     ← 실패한 장만
4. createPost(photoKeys: [최종 키들])
```

**1·3단계는 왕복 한 번이고, 2단계만 장마다 돈다.** 5장이면 GraphQL 2회 + PUT 5회다.

### 반드시 지켜야 하는 것

**(1) PUT 요청의 `Content-Type`·`Content-Length`가 1단계에서 선언한 값과 정확히 같아야 한다.**
두 값이 서명에 포함되어 있어서, 다르면 R2가 `403 SignatureDoesNotMatch`로 거부한다.
서버를 거치지 않으므로 이 실패는 앱에서만 보인다.

```
PUT {uploadUrl}
Content-Type: image/jpeg        ← 1단계에 넘긴 값과 동일
Content-Length: 184320          ← 1단계에 넘긴 값과 동일 (실제 바이트 수)
<binary>
```

**(2) 3단계를 건너뛰면 안 된다.** 1단계가 준 `pending/...` 키를 `createPost`에 그대로 넘기면
`PHOTO_NOT_UPLOADED`로 거부된다. 반드시 3단계의 `confirmed`에 담겨 온 `images/...` 키를 쓸 것.

**(3) 30분 안에 2단계를 끝낼 것.** `expiresAt` 이후의 PUT은 거부된다. 만료되면 1단계부터
다시 한다(키가 새로 발급된다).

**(4) 발급과 확인은 성패 처리가 다르다.**

| | 실패 시 |
|---|---|
| 1단계 발급 | **전부 거부.** 한 장이라도 형식·크기가 어긋나면 `uploadUrls`가 빈 목록이다 |
| 3단계 확인 | **장별로 갈린다.** 통과한 것은 `confirmed`, 실패한 것은 `failed`에 담긴다 |

3단계에서 `failed`가 비어 있지 않으면 `success`는 `false`지만 **`confirmed`의 키는 유효하다.**
실패한 장만 다시 올리게 하고 나머지는 살릴 것 — 전부 버리면 사용자가 다 다시 올려야 한다.

**(5) 사진을 지울 때는 `deletePostImage`.** 작성을 취소했거나, 골랐다가 뺐거나,
`editPost`로 글에서 뺀 키를 정리할 때 쓴다. 임시(`pending/`)·확정(`images/`) 둘 다 지워진다.
없는 키를 지워도 오류가 아니다(멱등). 본인이 발급받은 키만 지울 수 있다.

```graphql
mutation { deletePostImage(input: { objectKey: "images/20/..." }) {
  success userErrors { code message } } }
```

**글에서 사진을 빼도 오브젝트는 남는다.** `editPost(photoKeys:)`는 글과의 연결만 바꾸므로,
스토리지에서 지우려면 `deletePostImage`를 따로 호출할 것.

### 제약

| 항목 | 값 | 위반 시 |
|---|---|---|
| 형식 | `image/jpeg`, `image/png`, `image/webp` | `UNSUPPORTED_CONTENT_TYPE` |
| 크기 | 최대 10 MiB (10485760 바이트) | `UNSUPPORTED_CONTENT_TYPE` |
| 개수 | 글당 최대 5장 (한 번의 발급 요청도 5장) | `TOO_MANY_PHOTOS` |
| 만료 | 발급 후 **30분** | R2가 403 |

3단계에서 서버가 **실제 크기와 매직바이트**를 다시 본다. 확장자만 바꾼 파일은 여기서 걸린다.

### 조회

`Post.photoKeys`는 **키 배열이지 URL이 아니다.** 앱이 CDN 베이스와 조합한다.

```
https://cdn.ieuri.co.kr/{photoKey}
```

베이스 URL은 앱 설정에 둘 것. 서버는 이 값을 내려주지 않는다 — 그래야 CDN이 바뀌어도
서버 배포 없이 앱만 고치면 된다.

> 개발 환경 시드 데이터의 사진 키는 실제 오브젝트가 없어 **404가 정상**이다.
> 키 배열과 순서만 확인하는 용도다.

## 4. 지연 필드 — 필요한 것만 요청할 것

`Post.spot` / `Post.author` / `Post.commentPreview`는 **요청할 때만 서버가 조회한다.**
`{ id body }`만 물으면 추가 I/O가 0이고, `spot`을 넣으면 관광지 조회가 붙는다.

```graphql
# 목록 카드 — 필요한 것만
{ id title body tags category createdAt likeCount commentCount
  likedByViewer ownedByViewer hidden edited
  spot { id title thumbnailImageUrl category }     # null일 수 있다
  author { id nickname profileImageUrl } }

# 카드에 댓글 몇 건을 얹고 싶으면 — 페이지네이션 없음
{ ...위 필드
  commentPreview { id body createdAt ownedByViewer author { id nickname } } }
```

**댓글은 두 갈래다.**

| | 쓰임 | 페이지네이션 |
|---|---|---|
| `Post.commentPreview` | 카드에 최신 3건 미리보기 | 없음 |
| `comments(postId:)` | 상세 화면의 전체 목록·더 보기 | 커서 |

```graphql
# 상세 화면 — 루트 쿼리로 따로 조회한다
query { comments(postId: 42, first: 20, after: $cursor) {
  edges { cursor node { id body createdAt ownedByViewer hidden author { id nickname } } }
  pageInfo { hasNextPage endCursor }
} }
```

**목록 안에 목록을 중첩해 페이지네이션하지 않는다.** 카드마다 커서를 따로 들면 화면마다
관리가 갈리고, 어느 카드의 커서인지 추적하기 어렵다. 미리보기는 상한이 고정이고,
더 보기는 상세로 넘어가 루트 쿼리를 쓴다.

`commentPreview`는 서버가 DataLoader로 **한 번에** 읽으므로 피드 20건에 얹어도 쿼리가
20번 늘지 않는다. 전체 개수는 `commentCount`다(숨김 제외).

## 5. 페이지네이션 — 커서 기반

```graphql
edges { cursor node { ... } }
pageInfo { hasNextPage hasPreviousPage startCursor endCursor }
```

- 다음 페이지: `after: pageInfo.endCursor`, `hasNextPage: false`면 끝
- `first` 기본 20 / **상한 50** — 초과해도 오류가 아니라 50으로 잘린다
- `totalCount`는 **없다.** 전체 개수를 표시하는 UI는 만들 수 없다
- **`hasPreviousPage`를 믿지 말 것.** 앞으로만 가는 피드라 `after`를 넘겼는지만 반영한다.
  이전 페이지 UI가 필요하면 앱이 스택으로 관리할 것
- 커서는 불투명 문자열이다. 파싱하거나 만들어 내면 `INVALID_INPUT`

## 6. 모더레이션 — 화면에서 놓치기 쉬운 부분

### 차단은 양방향이다

내가 차단한 사람 **그리고 나를 차단한 사람**의 글·댓글이 모든 피드에서 사라진다.
서버가 걸러서 내려주므로 앱이 필터링할 것은 없다. 다만 두 가지를 유의:

- **`blockedUsers`에는 내가 건 차단만 나온다.** 나를 차단한 사람은 목록에 없다 —
  남이 건 차단은 내가 풀 수 없기 때문이다. "왜 안 보이는데 목록에 없지"는 정상이다.
- 차단 직후 피드를 새로 고치면 그 사람 글이 사라진다. 캐시를 쓴다면 무효화할 것.

### 숨김 글은 작성자에게만 보인다

서로 다른 5명이 신고하면 자동 숨김된다. 그 글은 **작성자 본인에게만** `hidden: true`로
계속 보인다. 남에게는 애초에 목록에 들어오지 않는다.

→ **`hidden: true`인 글을 받으면 "신고 누적으로 숨겨졌다"는 배지를 보여줄 것.**
작성자는 자기 글이 왜 반응이 없는지 알 수 없으면 서버 장애로 오해한다.

### 댓글 수는 모두에게 같다

`commentCount`는 숨겨진 댓글을 제외한 수이며, **차단은 반영하지 않는다.**
내가 차단한 사람의 댓글은 목록에서 빠지지만 숫자에는 남는다 — 즉 `commentCount: 4`인데
목록에 3건만 올 수 있다. **이것은 버그가 아니다.** 숫자는 모두에게 같아야 하기 때문이다.

→ 댓글 수와 목록 길이가 다르다고 오류 처리하지 말 것.

### 단건 조회도 같은 규칙이다

`post(id:)`는 차단·숨김이면 **오류가 아니라 `null`**을 준다. 딥링크로 들어온 경우이므로
"삭제되었거나 볼 수 없는 글입니다" 정도의 안내로 처리할 것. `errors[]`를 기대하면 안 된다.

## 7. 에러 처리

### 두 갈래다

**(1) 최상위 `errors[]` — 인증 실패만**

```json
{ "errors": [{ "message": "인증이 필요합니다." }], "data": { "createPost": null } }
```

`UNAUTHENTICATED`는 **`userErrors`에 담기지 않는다.** 토큰 자동 갱신은 최상위 `errors[]`를
보는 링크 계층에서 일어나야 한다(SPEC-0005와 동일).

**(2) payload의 `userErrors[]` — 나머지 전부**

```json
{ "data": { "createPost": {
    "success": false,
    "userErrors": [{ "code": "POST_BODY_REQUIRED", "message": "본문을 입력해 주세요.", "field": null }],
    "postId": null } } }
```

**HTTP는 실패해도 200이다.** `success`와 `userErrors`로만 판정할 것.

### 코드 목록 (19종)

| 코드 | 발생 | 화면 처리 |
|---|---|---|
| `POST_TITLE_REQUIRED` | 제목이 비었거나 공백뿐 | 입력 필드 |
| `POST_TITLE_LENGTH_INVALID` | 제목 50자 초과 | 입력 필드 |
| `POST_BODY_REQUIRED` | 본문이 비었거나 공백뿐 | 입력 필드 |
| `POST_BODY_LENGTH_INVALID` | 본문 500자 초과 | 입력 필드 |
| `SPOT_NOT_FOUND` | 대상이 없음 | 토스트 |
| `TOO_MANY_PHOTOS` | 사진 6장 이상 | 선택 단계에서 미리 막을 것 |
| `PHOTO_NOT_UPLOADED` | 미확인·타인·위조 키 | 사진 재업로드 유도 |
| `UNSUPPORTED_CONTENT_TYPE` | 미지원 형식·크기 초과 | 선택 단계에서 미리 막을 것 |
| `NOT_POST_OWNER` | 남의 글 삭제·수정 시도 | 토스트 (버튼을 숨기면 안 뜬다) |
| `POST_NOT_EDITABLE` | 숨겨진 글 수정 시도 | 수정 메뉴를 비활성화해 미리 막을 것 |
| `NOT_COMMENT_OWNER` | 남의 댓글 삭제 시도 | 위와 같음 |
| `POST_NOT_FOUND` | 이미 삭제된 글 | 목록 새로고침 |
| `COMMENT_NOT_FOUND` | 이미 삭제된 댓글 | 목록 새로고침 |
| `COMMENT_BODY_REQUIRED` | 댓글이 비었거나 공백뿐 | 입력 필드 |
| `COMMENT_BODY_LENGTH_INVALID` | 댓글 500자 초과 | 입력 필드 |
| `CANNOT_BLOCK_SELF` | 자기 차단 | UI에서 미리 막을 것 |
| `MEMBER_NOT_FOUND` | 없는 회원 | 토스트 |
| `ALREADY_REPORTED` | 같은 대상 재신고 | "이미 신고했습니다" |
| `REPORT_DETAIL_REQUIRED` | `OTHER`인데 상세 없음 | 입력 필드 |
| `INVALID_INPUT` | 형식 위반 (잘못된 커서 등) | 토스트 |

**`PHOTO_NOT_UPLOADED`는 세 원인이 한 코드다** — 미업로드·타인 키·위조 키를 구분해 주지
않는다(키 존재 여부를 캐낼 수 있어서다). 앱도 구분해 안내할 수 없다.

## 8. 멱등 동작 — 오류가 아닌 것들

아래는 `success: true`로 돌아온다. 실패로 처리하지 말 것.

- 이미 좋아요한 글에 `likePost` → `likeCount` 변화 없음
- 좋아요하지 않은 글에 `unlikePost` → 0 아래로 안 내려감
- 이미 차단한 사람에게 `blockUser`
- 차단하지 않은 사람에게 `unblockUser`

**낙관적 업데이트를 쓴다면 응답의 `likeCount`로 되맞출 것.** 서버 값이 정본이다.

## 9. 신고

```graphql
reportContent(input: {
  targetType: POST | COMMENT | MEMBER
  targetId: ID!
  reason: SPAM | ABUSE | INAPPROPRIATE_CONTENT | OTHER
  detail: String     # reason이 OTHER면 필수
})
```

- `OTHER`인데 `detail`이 비면 `REPORT_DETAIL_REQUIRED`. **입력 폼에서 미리 막을 것**
- 같은 대상 재신고는 `ALREADY_REPORTED`. 신고 후 버튼을 비활성화하는 편이 낫다
- **`MEMBER` 신고는 기록만 된다.** 5명이 신고해도 그 사람의 글이 사라지지 않는다.
  "신고가 접수되었습니다" 이상을 약속하지 말 것 — 자동 조치는 글·댓글에만 있다

## 10. 다국어

- **`TargetCategory`는 앱이 매핑한다.** 서버가 표시 문자열을 내려주지 않는다
  (`SpotCategory`와 같은 방식, POL-023). `communityChips`도 enum 값과 순서만 내려준다
- **`tags`는 번역 대상이 아니다.** 사용자가 입력한 원문 그대로 내려간다(대소문자 보존).
  필터링할 때는 대소문자와 선행 `#`을 서버가 무시하므로 앱이 정규화할 필요가 없다

## 11. 글 작성 후 화면 갱신

`createPost`는 **`postId`만 준다. `post`는 항상 null이다.**

```graphql
mutation { createPost(input: {...}) { success userErrors { code message } postId } }
```

작성 직후 상세로 이동한다면 `post(id: $postId)`를 한 번 더 조회할 것.
피드로 돌아간다면 목록을 새로 고치면 된다. `createComment`도 `commentId`만 준다.

이유: `Post.spot`·`author`가 지연 필드라 생성 응답에서 채우려면 앱이 요청하지도 않은
다른 도메인 조회를 매번 왕복해야 한다.

## 12. 본문 길이와 이모지 — 주의

제목은 **50자**, 본문은 **500자**인데, 서버는 둘 다 **코드포인트**로 센다. 이모지에서 앱과 어긋날 수 있다:

| 입력 | 사용자가 보는 글자 | 서버 계산 |
|---|---|---|
| `🥲` | 1 | 1 |
| `🇰🇷` (국기) | 1 | 2 |
| `👨‍👩‍👧‍👦` (ZWJ 결합) | 1 | 7 |

앱이 `String.length`(UTF-16)나 grapheme 단위로 세면 서버와 다른 숫자가 나오고,
"499자인데 거부됨" 같은 상황이 생긴다.

**권장:** 입력 카운터를 **코드포인트 기준**으로 맞출 것.
- Dart/Flutter: `body.runes.length`
- JS: `[...body].length`

이 기준을 앱과 통일할지는 아직 확정되지 않았다([TBD]). 다르게 가려면 서버 쪽 판정도
같이 바꿔야 하므로 알려줄 것.

## 13. 인증

**모든 쿼리·뮤테이션이 인증을 요구한다.** 이 앱은 로그인 없이 들어올 수 없으므로 미인증
경로를 두지 않았다. 토큰 없이 호출하면 최상위 `errors[]`의 `UNAUTHENTICATED`다.

나중에 비로그인 열람이 필요해지면 그때 연다 — 지금 열어 두면 쓰지 않는 분기만 늘어난다.

## 14. 지역 피드 주의

```graphql
posts(latitude: 37.5665, longitude: 126.9780, radiusMeters: 5000)
```

- `radiusMeters` 기본 20000 / **상한 100000** — 초과해도 오류가 아니라 잘린다
- **반경 안의 대상 수에 상한(2000)이 있다.** 반경이 매우 넓으면 결과가 부분집합일 수 있다.
  "반경 100km 전체"를 보장하지 않으므로 그런 UI 문구는 피할 것
- 위치를 가진 대상만 결과에 든다. 지금은 관광지뿐이라 문제가 없지만, 좌표 없는 종류가
  생기면 그 글은 지역 피드에 나타나지 않는다

## 15. 아직 없는 것

- **알림 없음.** 내 글에 댓글·좋아요가 달려도 푸시가 없다(비범위)
- **수정 이력 없음.** `edited` 플래그만 있고 이전 내용은 보관하지 않는다
- **대댓글 없음.** 1단계 댓글만. `Comment`에 부모 필드가 아예 없다
- **검색 없음.** `posts(tag:)`와 상단 칩으로 갈음 — 본문 전문 검색은 없다
- 고아 오브젝트(업로드했는데 글을 안 쓴 경우) 정리 없음 — R2 lifecycle로 처리할 사안

## 16. 개발 환경 확인용 데이터

`R__seed_community.sql`이 더미 데이터를 넣는다(로컬·개발 전용). **회원 20번이 주인공**이다.

| 회원 | 20번으로 로그인해 조회했을 때 |
|---|---|
| 20 | 본인 글 4건, `ownedByViewer: true` |
| 19 | 글 2건·댓글 1건이 **안 보여야** 함 (20이 차단) |
| 18 | 글 1건·댓글 1건이 **안 보여야** 함 (18이 20을 차단 — 양방향 확인) |
| 17 | 숨김 글 1건 안 보임 + 정상 글 1건은 보임 |
| 12·14·15·16 | 글 7건 정상 표시 (그중 1건은 `edited: true`, 1건은 **장소 없는 글**) |

- 20번으로 조회 시 **16건 중 12건**이 보이면 정상
  (제외 4건 = 19번 글 2건 + 18번 글 1건 + 17번의 숨김 글 1건)
- **장소 없는 글이 1건 있다**(14번의 "여행 짐 싸는 팁"). `spot: null`로 내려오므로
  카드에서 장소 칩을 그리지 않는 분기를 이 글로 확인할 것. 좌표 반경 조회에는 잡히지 않는다
- `edited: true`인 글이 1건 있다(15번의 덕수궁 글) — "수정됨" 표시 확인용
- `communityChips`는 `X-App-Key`·`Accept-Language`에 따라 다르다: `k-trip-spot`은 언어별 8건
  (국문은 여행코스, 외국어는 교통이 들어간다) / `demo-app`은 국문 2건 /
  헤더가 없거나 모르는 값이면 기본 앱(k-trip-spot)
- `posts(latitude: 37.5665, longitude: 126.9780, radiusMeters: 5000)` — 서울 시청 기준.
  해운대 글(331km)과 장소 없는 글은 빠져야 함
- `posts(tag: "seoul")` — 대소문자가 다른 태그 2건(`Seoul`·`seoul`)이 함께 잡혀야 함
- 경복궁 후기는 `commentCount: 4`인데 20번에게는 댓글 **3건**만 온다(19번 것이 차단됨).
  북촌 글은 `commentCount: 1`인데 20번에게는 **0건**이다(18번이 20을 차단).
  둘 다 §6에서 설명한 정상 동작이다 — 수와 목록 길이가 다르다고 오류 처리하지 말 것
- 사진 키는 실제 오브젝트가 없어 CDN에서 404다. 키·순서 확인용

## 17. 시작 순서 제안

1. **읽기부터.** `posts(spotId:)`로 spot 상세에 피드를 붙인다
2. **커서 페이징**을 붙이고 `hasNextPage`로 무한 스크롤을 확정한다
3. **상호작용**(좋아요·댓글). 멱등이라 낙관적 업데이트가 쉽다
4. **글 작성 — 사진 없이 먼저.** `createPost`에 `photoKeys: []`를 넘기면 된다
5. **사진 업로드**를 마지막에. 4단계 흐름이라 가장 손이 많이 간다
6. 차단·신고·상단 칩

§1의 차이점과 §3의 업로드 순서, §6의 모더레이션 세 가지가 이 기능에서 가장 자주 어긋나는
지점이다. 막히면 이슈 #45나 PR #46에 남겨 줄 것.
