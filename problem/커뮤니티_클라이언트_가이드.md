# 커뮤니티(SPEC-0010) — 클라이언트 구현 가이드

앱이 커뮤니티 기능을 붙일 때 필요한 계약과 제약을 담는다. 서버 구현 기준으로 작성했다.

> **스키마 원문을 함께 볼 것.** 이 문서는 "왜 그렇게 되어 있고 무엇을 지켜야 하는가"를 설명하고,
> 필드 하나하나의 정의는 스키마가 정본이다.
> 문서와 스키마가 어긋나면 **스키마가 맞다.** 그런 경우를 발견하면 알려 줄 것.

---

## 0. 5분 요약

- **모든 요청에 인증이 필요하다.** 비로그인 열람 경로는 없다
- 모든 요청에 **`X-App-Key`** 헤더를 붙인다(상단 칩 구성이 앱마다 다르다)
- 글은 **카테고리가 필수, 장소(spot)는 선택**이다
- 사진은 **서버를 거치지 않는다.** 앱이 스토리지로 직접 PUT한다 (§4)
- 뮤테이션 실패는 **HTTP 200 + `userErrors`**다. 인증 실패만 최상위 `errors[]` (§7)
- 필요한 필드만 요청할 것. 안 고른 필드는 **서버가 조회조차 하지 않는다** (§3)

---

## 1. 요청 공통

### 인증 — 전부 필수

```
Authorization: Bearer <accessToken>
```

모든 쿼리·뮤테이션이 인증을 요구한다. 이 앱은 로그인 없이 들어올 수 없으므로 미인증 경로를
두지 않았다. 토큰 없이 호출하면 최상위 `errors[]`에 `UNAUTHENTICATED`가 온다(§7).

### `X-App-Key` — 붙일 것

```
X-App-Key: k-trip-spot
```

앱이 여러 개 출시되면 상단 칩 구성이 서로 달라야 해서 서버가 어느 앱인지 알아야 한다.

- **없으면 기본 앱(`k-trip-spot`)으로 간주**한다. 지금 당장은 없어도 동작하지만, 두 번째 앱이
  나오는 순간 문제가 되니 처음부터 붙이는 편이 낫다
- 모르는 값이어도 요청이 깨지지 않는다(기본 앱으로 폴백)
- 지금은 칩 구성에만 쓰이지만, 앞으로 앱별로 갈리는 것이 생기면 같은 헤더를 쓴다

### `Accept-Language`

칩의 가용 카테고리와 `PostSpot`의 제목·썸네일이 언어에 따라 달라진다.

## 2. 글 읽기

### `posts` — 피드는 이 하나뿐

목록 쿼리는 `posts` 하나다. **인자 조합이 범위를 정한다.**

```graphql
posts(
  spotId: ID                        # 이 장소에 붙은 글만
  latitude: Float, longitude: Float # 좌표 반경 안의 장소들에 붙은 글
  radiusMeters: Int = 20000
  category: TargetCategory          # 상단 칩
  tag: String                       # 태그 필터
  sort: PostSortOrder = LATEST      # 정렬 — 무엇이 보이는지도 바뀐다
  first: Int = 20, after: String
): PostConnection!
```

| 하고 싶은 것 | 호출 |
|---|---|
| spot 상세의 글 목록 | `posts(spotId: 11094)` |
| 커뮤니티 탭(내 주변) | `posts(latitude: 37.5665, longitude: 126.9780, radiusMeters: 5000)` |
| 상단 칩을 누른 상태 | `posts(latitude:, longitude:, category: RESTAURANT)` |
| 좌표 없이 카테고리만 | `posts(category: RESTAURANT)` |
| 태그로 | `posts(tag: "야경")` |
| 전체 피드 | `posts` |

**규칙:**

- `latitude`·`longitude`는 **함께** 줘야 한다. 하나만 주면 둘 다 무시된다
- `spotId`와 좌표를 둘 다 주면 **`spotId`가 이긴다**(좌표는 무시)
- `radiusMeters`는 좌표를 줄 때만 의미가 있다
- **`category`·`tag`는 위 범위와 독립이다.** 좌표 없이 단독으로도 걸린다

### 정렬 — `sort`가 "무엇이 보이는지"까지 바꾼다

| `sort` | 무엇이 보이나 | 순서 |
|---|---|---|
| `LATEST` (기본) | 반경 안 글 **+ 장소 없이 쓴 글** | 최신순 |
| `DISTANCE` | 반경 안 장소에 붙은 글만 | **가까운 장소 순**, 같은 장소끼리는 최신순 |

앱에서는 "거리순 / 최신순" 토글로 그리면 된다.

- **장소 없이 쓴 글은 `DISTANCE`에서 빠진다.** 거리가 없어 목록의 어디에 둘지 정할 수 없기
  때문이다. 그런 글까지 보려면 `LATEST`를 쓴다
- **좌표를 주지 않으면 `DISTANCE`도 `LATEST`처럼 동작한다.** 거리를 잴 기준이 없어서이며,
  오류가 아니다 — 위치 권한을 못 받아도 피드는 그려진다
- **정렬을 바꾸면 커서를 버리고 첫 페이지부터 다시 조회할 것.** 두 정렬의 커서 형식이 달라
  이전 커서를 그대로 넘기면 `INVALID_INPUT`이 온다
- `spotId`와 좌표를 **함께 줄 수 있다.** 서로 배타적이지 않으며 둘 다 조건이 된다

### 그 밖의 조회

```graphql
post(id: ID!): Post                        # 차단·숨김·삭제면 null (오류 아님). **여기서만 조회수가 오른다**
comments(postId: ID!, first:, after:)      # 글의 전체 댓글 (커서 페이징)
blockedUsers(first:, after:)               # 내가 차단한 사람만
communityChips: [CommunityChip!]!          # 상단 칩 구성
```

### 상단 칩

```graphql
query { communityChips { category position } }
```

- **표시 문구는 서버가 주지 않는다.** `RESTAURANT` → "맛집"/"Food" 매핑은 앱이 한다
- `position` 오름차순으로 이미 정렬돼 있다. 그대로 그리면 된다
- 누르면 → `posts(category: $category)`
- **구성이 없는 앱이면 빈 목록**이다. 오류가 아니므로 칩 영역이 비는 레이아웃을 허용할 것
- 언어마다 가용 카테고리가 다르다 — 국문은 `TRAVEL_COURSE`(여행코스)가 있고 `TRANSPORT`(교통)가
  없다. 외국어는 반대다

### 조회수 (`viewCount`)

**`post(id:)` 단건 조회에서만 오른다.** 피드 목록(`posts`)에 카드가 뜨는 것은 조회로 세지 않는다 —
스크롤 한 번에 수십이 올라가면 숫자가 의미를 잃기 때문이다.

- **중복을 걸러 내지 않는다.** 같은 사람이 새로고침하면 계속 오른다. 고유 방문자 수가 아니다
- **방금 올린 조회가 그 응답에는 반영되지 않을 수 있다.** 증가는 응답과 별개로 처리된다.
  상세를 열자마자 숫자가 1 늘어난 것을 보여주고 싶다면 **앱에서 +1 해서 그리는 편**이 낫다
- 차단·숨김으로 글을 못 본 경우(`null` 응답)에는 오르지 않는다
- 서버 사정으로 드물게 한 건이 누락될 수 있다. 정산·과금에 쓸 수 있는 정확한 수치가 아니다

### 댓글은 두 갈래다

| | 쓰임 | 페이지네이션 |
|---|---|---|
| `Post.commentPreview` | 카드에 최신 몇 건 미리보기 | **없음** |
| `comments(postId:)` | 상세 화면의 전체 목록·더 보기 | 커서 |

### 대댓글 — 깊이는 2단계까지다

`comments(postId:)`는 **최상위 댓글만** 준다. 답글은 각 댓글의 `replies`에 담겨 내려온다.

```graphql
comments(postId: 42) { edges { node {
  id body author { nickname }
  replies { id body parentCommentId author { nickname } }   # 오래된 순, 페이지네이션 없음
} } }
```

- `replies`는 **오래된 순**이다. 대화의 흐름이라 최신순으로 뒤집으면 문맥이 끊긴다
  (최상위 목록은 여전히 최신순이다)
- `replies`에 **페이지네이션이 없다.** 깊이가 2단계라 한 댓글의 답글이 화면을 넘길 만큼
  많지 않다
- 답글의 `replies`는 **항상 빈 목록**이다(3단계가 없다)
- `parentCommentId`가 null이면 최상위, 있으면 답글이다 — 들여쓰기 판정에 쓴다

답글 작성:

```graphql
createComment(input: { postId: 42, body: "답글이에요", parentCommentId: 7 })
```

- **답글에 답글을 달아도 거부되지 않는다.** 그 답글의 부모(최상위)에 달린 것으로 눕혀
  깊이 2단계를 유지한다 — 따라서 **응답의 `parentCommentId`가 넘긴 값과 다를 수 있다**
- 다른 글의 댓글을 지정하면 `COMMENT_NOT_FOUND`
- **`commentCount`에 답글도 포함된다.** "댓글 5개"는 최상위 3 + 답글 2일 수 있다
- 부모 댓글이 삭제돼도 답글은 남는다

목록 안에 목록을 중첩해 페이지네이션하지 않는다 — 카드마다 커서를 따로 들면 어느 카드의
커서인지 추적하기 어렵다. 미리보기는 상한이 고정이고, 더 보기는 상세로 넘어가 루트 쿼리를 쓴다.

### 페이지네이션 (커서 기반)

```graphql
edges { cursor node { ... } }
pageInfo { hasNextPage hasPreviousPage startCursor endCursor }
```

- 다음 페이지: `after: pageInfo.endCursor`. `hasNextPage: false`면 끝
- `first` 기본 20 / **상한 50** — 초과해도 오류가 아니라 **50으로 잘린다**
- `totalCount`는 **없다.** 전체 개수를 표시하는 UI는 만들 수 없다
- **`hasPreviousPage`를 믿지 말 것.** 앞으로만 가는 피드라 `after`를 넘겼는지만 반영한다
- 커서는 불투명 문자열이다. 파싱하거나 만들어 내면 `INVALID_INPUT`

## 3. 필요한 필드만 요청할 것

`Post`의 아래 필드는 **각각 다른 테이블·다른 도메인에 있다.** 요청하지 않으면 서버가
조회조차 하지 않는다.

| 필드 | 고르면 추가되는 조회 |
|---|---|
| `tags` | 태그 1회 |
| `photoKeys` | 사진 1회 |
| `category` | 카테고리 연결 1회 |
| `likedByViewer` | 좋아요 1회 |
| `spot` | 연결 1회 + 관광지 조회 1회 |
| `author` | 회원 조회 1회 |
| `commentPreview` | 댓글 1회 |

`likeCount`·`commentCount`·`viewCount`는 글 행에 함께 있어 **추가 조회가 없다.** 마음 놓고 요청할 것.

**이 조회들은 글 개수와 무관하게 각각 1회다.** 카드 20장을 받아도 `tags`는 20번이 아니라
1번 조회된다(서버가 묶어서 읽는다). 그러니 **필요한 필드는 마음 놓고 요청하되, 안 쓰는
필드는 빼는 것**이 맞다.

```graphql
# 목록 카드 — 실제로 그리는 것만
{ id title body category tags createdAt likeCount commentCount viewCount
  likedByViewer ownedByViewer hidden edited
  spot { id title thumbnailImageUrl }      # null일 수 있다
  author { id nickname profileImageUrl } }

# 본문만 훑는 화면이라면 — 추가 조회 0회
{ id title body createdAt }
```

## 4. 사진 업로드 — 반드시 이 순서대로

**서버는 이미지 바이트를 받지 않는다.** 앱이 오브젝트 스토리지로 직접 PUT한다.
전체 흐름에서 **2단계만 GraphQL이 아니다.**

```
1) createPostImageUploadUrls   여러 장 한 번에 → uploadUrl · objectKey("pending/…") · expiresAt
2) 각 uploadUrl로 HTTP PUT     ← GraphQL 아님. 장마다 1회
3) confirmPostImageUploads     여러 장 한 번에 → confirmed("images/…") · failed
4) createPost(photoKeys:)      3단계의 confirmed 키만 넘긴다
```

5장이면 **GraphQL 2회 + PUT 5회**다. 1·3단계는 왕복 한 번이고 2단계만 장마다 돈다.

### 1단계 — 발급

```graphql
mutation {
  createPostImageUploadUrls(input: {
    images: [
      { contentType: "image/jpeg", contentLength: 184320 },
      { contentType: "image/png",  contentLength: 502113 }
    ]
  }) {
    success
    userErrors { code message field }
    uploadUrls { uploadUrl objectKey expiresAt }
  }
}
```

**반드시 넣어야 하는 값 — 장마다 둘 다 필수다.**

| 필드 | 무엇을 넣나 | 제약 | 위반 시 |
|---|---|---|---|
| `contentType` | 올릴 파일의 실제 MIME 타입 | `image/jpeg` · `image/png` · `image/webp` | `UNSUPPORTED_CONTENT_TYPE` |
| `contentLength` | 올릴 파일의 **실제 바이트 수** | 1 ~ 10485760 (10 MiB) | `UNSUPPORTED_CONTENT_TYPE` |

- **`contentLength`는 추정치가 아니라 실제 파일 크기여야 한다.** 이 값이 서명에 들어가므로
  1바이트라도 다르면 2단계에서 스토리지가 거부한다
- 한 번에 **최대 5장**. 넘으면 `TOO_MANY_PHOTOS`

**`uploadUrls`는 요청한 순서와 같은 순서로 온다.** 그리고 **하나라도 어긋나면 전부 발급되지
않는다**(`uploadUrls`가 빈 목록) — 부분 발급은 클라이언트가 추적하기 어려워서다.

응답의 `objectKey`는 `pending/{memberId}/{uuid}` 형태이며 **서버가 정한다.** 앱이 키를
만들거나 바꿔서 보낼 수 없다.

### 2단계 — 스토리지로 직접 PUT

```
PUT {uploadUrl}
Content-Type: image/jpeg        ← 1단계에 넘긴 값과 정확히 동일
Content-Length: 184320          ← 1단계에 넘긴 값과 정확히 동일
<파일 바이트 그대로>
```

**두 헤더가 1단계 선언과 정확히 같아야 한다.** 두 값이 서명에 포함되어 있어서, 다르면
스토리지가 `403 SignatureDoesNotMatch`로 거부한다. 이것이 위조·크기 초과를 막는 첫 번째 층이다.

주의할 점:

- **서버를 거치지 않으므로 이 실패는 앱에서만 보인다.** GraphQL 응답에 안 나온다
- HTTP 클라이언트가 헤더를 임의로 바꾸지 않는지 확인할 것 — 일부 라이브러리가
  `Content-Type`에 charset을 덧붙이거나 압축을 걸어 `Content-Length`를 바꾼다.
  그러면 서명이 깨진다
- 인증 헤더를 붙이지 말 것. 서명이 이미 URL에 들어 있다
- **`expiresAt`(발급 후 30분) 안에 끝낼 것.** 지나면 거부되며, 그때는 1단계부터 다시 한다

### 3단계 — 확인

```graphql
mutation {
  confirmPostImageUploads(input: {
    objectKeys: ["pending/20/9f1c…", "pending/20/3ab7…"]
  }) {
    success
    userErrors { code message field }
    confirmed                       # ["images/20/9f1c…", …]  ← 이걸 쓴다
    failed { objectKey code }
  }
}
```

이 단계에서 서버가 **실제 크기와 매직바이트**를 다시 본다. 확장자만 바꾼 파일은 여기서 걸린다.
통과한 것만 `pending/` → `images/`로 옮겨진다.

**장별로 성패가 갈린다.**

- `confirmed` — 통과한 키(`images/…`). **이 값만 `createPost`에 넘길 수 있다**
- `failed` — 실패한 키와 사유
- **`failed`가 비어 있지 않으면 `success`는 `false`다. 그래도 `confirmed`의 키는 유효하다** —
  실패한 장만 다시 올리게 하고 나머지는 살릴 것. 전부 버리면 사용자가 다 다시 올려야 한다

발급과 확인의 실패 처리가 다르다:

| | 실패 시 |
|---|---|
| 1단계 발급 | **전부 거부** (`uploadUrls`가 빈 목록) |
| 3단계 확인 | **장별로 갈림** (`confirmed` / `failed`) |

### 4단계 — 글에 붙이기

```graphql
createPost(input: { …, photoKeys: ["images/20/9f1c…"] })
```

- **3단계를 건너뛸 수 없다.** `pending/…` 키를 그대로 넘기면 `PHOTO_NOT_UPLOADED`
- 배열 **순서가 표시 순서**다
- 최대 5장. 빈 배열도 유효하다(사진은 선택)

### 사진 삭제

```graphql
mutation { deletePostImage(input: { objectKey: "images/20/9f1c…" }) {
  success userErrors { code message } } }
```

- 작성을 취소했거나, 골랐다가 뺐거나, `editPost`로 글에서 뺀 키를 정리할 때 쓴다
- 임시(`pending/`)·확정(`images/`) 둘 다 지워진다
- 없는 키를 지워도 **오류가 아니다**(멱등)
- **본인이 발급받은 키만** 지울 수 있다. 남의 키면 `PHOTO_NOT_UPLOADED`
- **글에서 사진을 빼도 오브젝트는 남는다.** `editPost(photoKeys:)`는 글과의 연결만 바꾸므로,
  스토리지에서 지우려면 이걸 따로 호출해야 한다

### 사진 조회

`Post.photoKeys`는 **키 배열이지 URL이 아니다.** 앱이 CDN 베이스와 조합한다.

```
https://cdn.ieuri.co.kr/{photoKey}
```

베이스 URL은 앱 설정에 둘 것. 서버는 이 값을 내려주지 않는다 — 그래야 CDN이 바뀌어도
서버 배포 없이 앱만 고치면 된다.

> 개발 환경 시드의 사진 키는 실제 오브젝트가 없어 **404가 정상**이다. 키·순서 확인용이다.

### 업로드 제약 한눈에

| 항목 | 값 | 위반 시 |
|---|---|---|
| 형식 | `image/jpeg` · `image/png` · `image/webp` | `UNSUPPORTED_CONTENT_TYPE` |
| 크기 | 1 ~ 10485760 바이트(10 MiB) | `UNSUPPORTED_CONTENT_TYPE` |
| 개수 | 발급 5장 / 글당 5장 | `TOO_MANY_PHOTOS` |
| 만료 | 발급 후 **30분** | 스토리지가 403 |
| 미확인 키 | `pending/…`을 글에 사용 | `PHOTO_NOT_UPLOADED` |

## 5. 글 쓰기·수정·삭제

### 작성

```graphql
createPost(input: {
  category: TOURIST_SPOT        # 필수
  spotId: 11094                 # 선택 — 생략하면 장소 없는 글
  tags: ["야간개장", "한복"]     # 최대 5개. 빈 배열 가능
  title: "경복궁 야간개장 후기"   # 1~50자, 필수
  body: "한복 입고 가면 무료예요" # 1~500자, 필수
  photoKeys: []                 # 최대 5개. 빈 배열 가능
}) { success userErrors { code message field } postId }
```

**반드시 넣어야 하는 값**

| 필드 | 규칙 |
|---|---|
| `category` | **필수.** 9종 중 하나 |
| `title` | **필수.** 앞뒤 공백 제거 후 1~50자 |
| `body` | **필수.** 앞뒤 공백 제거 후 1~500자 |
| `tags` | 배열 자체는 필수(빈 배열 가능). 각 태그는 공백 없이 30자 이내, 최대 5개 |
| `photoKeys` | 배열 자체는 필수(빈 배열 가능). 확정 키만, 최대 5개 |
| `spotId` | **선택.** 생략 가능 |

**카테고리와 장소:**

- 카테고리는 **글에 직접 저장되는 값**이라 작성 화면에서 사용자가 고른다
- 장소를 골랐다면 **그 장소의 카테고리를 기본값으로 제안**할 것 — `PostSpot.category`가 그 용도다
- 장소 없이 카테고리만으로도 글을 쓸 수 있다. 그 글은 좌표 반경 조회에는 잡히지 않는다

**태그:**

- 사용자가 직접 입력한다. 앞의 `#`은 서버가 제거한다
- **공백이 들어가면 거부된다**(`INVALID_TAG`) — "맛집 추천"이 한 태그인지 둘인지 애매해서다
- 대소문자는 보존해서 보여주되 검색은 대소문자를 가리지 않는다(`Seoul` = `seoul`)

### 수정

```graphql
editPost(input: {
  postId: 42
  title: "…"               # 필수
  body: "…"                # 필수
  photoKeys: ["images/…"]  # 선택 — 생략하면 사진을 건드리지 않는다
}) { success userErrors { code message field } }
```

- **제목·본문·사진만 바꾼다.** 카테고리·장소·태그는 수정할 수 없다 — 바뀌면 글이 다른 피드로
  순간이동한다
- `photoKeys`를 주면 **전체 목록으로 교체한다.** 빠진 키는 떨어지고 새 키는 붙는다.
  생략하면 사진은 그대로다
- **숨겨진 글(`hidden: true`)은 수정할 수 없다** → `POST_NOT_EDITABLE`.
  신고가 쌓여 숨겨진 글을 다른 내용으로 바꿔치기하면 신고 기록이 무의미해지기 때문이다
- 수정하면 `edited: true`로 내려온다 — 카드에 "수정됨"을 표시할 것. 이력은 보관하지 않는다

### ⋮ 메뉴 (카드 오른쪽 상단)

| 메뉴 | API | 노출 조건 |
|---|---|---|
| 수정 | `editPost` | `ownedByViewer && !hidden` |
| 삭제 | `deletePost` | `ownedByViewer` |
| 이 사용자 차단하기 | `blockUser(targetMemberId:)` | `!ownedByViewer` |
| 이 글 신고하기 | `reportContent(targetType: POST, targetId:)` | `!ownedByViewer` |

숨겨진 자기 글은 **수정을 비활성화**하고 이유를 안내하는 편이 낫다 — 눌러서 오류를 보는 것보다 낫다.

### 작성 직후 화면 갱신

`createPost`는 **`postId`만 준다. `post`는 항상 null이다.**

작성 직후 상세로 이동한다면 `post(id: $postId)`를 한 번 더 조회할 것. 피드로 돌아간다면
목록을 새로 고치면 된다. `createComment`도 `commentId`만 준다.

이유: `spot`·`author`가 지연 필드라 생성 응답에서 채우려면 앱이 요청하지도 않은 조회를
매번 왕복해야 한다.

## 6. 모더레이션 — 화면에서 놓치기 쉬운 것

### 차단은 양방향이다

내가 차단한 사람 **그리고 나를 차단한 사람**의 글·댓글이 모든 피드에서 사라진다.
서버가 걸러서 내려주므로 앱이 필터링할 것은 없다. 다만:

- **`blockedUsers`에는 내가 건 차단만 나온다.** 나를 차단한 사람은 목록에 없다 — 남이 건
  차단은 내가 풀 수 없기 때문이다. "안 보이는데 목록에 없다"는 정상이다
- 차단 직후 피드를 새로 고치면 그 사람 글이 사라진다. 캐시를 쓴다면 무효화할 것

### 숨김 글은 작성자에게만 보인다

서로 다른 5명이 신고하면 자동 숨김된다. 그 글은 **작성자 본인에게만** `hidden: true`로
계속 보이고, 남에게는 애초에 목록에 들어오지 않는다.

→ **`hidden: true`인 글에는 "신고 누적으로 숨겨졌다"는 배지를 보여줄 것.**
작성자는 자기 글이 왜 반응이 없는지 모르면 앱 장애로 오해한다.

### 댓글 수와 목록 길이가 다를 수 있다 (버그 아님)

`commentCount`는 숨겨진 댓글만 제외한 수이며 **차단은 반영하지 않는다.**
숫자는 모두에게 같아야 하기 때문이다.

즉 `commentCount: 4`인데 목록에 3건만 올 수 있다(내가 차단한 사람의 댓글이 빠져서).
**오류로 처리하지 말 것.**

### 단건 조회도 같은 규칙이다

`post(id:)`는 차단·숨김·삭제면 **오류가 아니라 `null`**이다. 딥링크로 들어온 경우이므로
"삭제되었거나 볼 수 없는 글입니다" 정도로 안내할 것. `errors[]`를 기대하면 안 된다.

### 신고

```graphql
reportContent(input: {
  targetType: POST | COMMENT | MEMBER
  targetId: ID!
  reason: SPAM | ABUSE | INAPPROPRIATE_CONTENT | OTHER
  detail: String     # reason이 OTHER면 필수
})
```

- `OTHER`인데 `detail`이 비면 `REPORT_DETAIL_REQUIRED`. **입력 폼에서 미리 막을 것**
- 같은 대상 재신고는 `ALREADY_REPORTED`. 신고 후 버튼을 비활성화하는 편이 낫다
- **`MEMBER` 신고는 기록만 된다.** 5명이 신고해도 그 사람의 글이 사라지지 않는다.
  "신고가 접수되었습니다" 이상을 약속하지 말 것 — 자동 조치는 글·댓글에만 있다

## 7. 에러 처리

### 두 갈래다

**(1) 최상위 `errors[]` — 인증 실패만**

```json
{ "errors": [{ "message": "인증이 필요합니다." }], "data": { "createPost": null } }
```

`UNAUTHENTICATED`는 **`userErrors`에 담기지 않는다.** 토큰 자동 갱신은 최상위 `errors[]`를
보는 링크 계층에서 일어나야 한다(SPEC-0005와 동일).

**(2) payload의 `userErrors[]` — 나머지 전부**

```json
{ "data": { "createPost": {
    "success": false,
    "userErrors": [{ "code": "POST_BODY_REQUIRED", "message": "본문을 입력해 주세요.", "field": null }],
    "postId": null } } }
```

**HTTP는 실패해도 200이다.** `success`와 `userErrors`로만 판정할 것.

### 코드 목록 (22종)

| 코드 | 발생 | 화면 처리 |
|---|---|---|
| `POST_TITLE_REQUIRED` | 제목이 비었거나 공백뿐 | 입력 필드 |
| `POST_TITLE_LENGTH_INVALID` | 제목 50자 초과 | 입력 필드 |
| `POST_BODY_REQUIRED` | 본문이 비었거나 공백뿐 | 입력 필드 |
| `POST_BODY_LENGTH_INVALID` | 본문 500자 초과 | 입력 필드 |
| `INVALID_TAG` | 태그에 공백이 있거나 30자 초과 | 입력 필드 |
| `TOO_MANY_TAGS` | 태그 6개 이상 | 입력 단계에서 미리 막을 것 |
| `SPOT_NOT_FOUND` | `spotId`에 해당하는 장소가 없음 | 토스트 |
| `TOO_MANY_PHOTOS` | 사진 6장 이상 | 선택 단계에서 미리 막을 것 |
| `PHOTO_NOT_UPLOADED` | 미확인·타인·위조 키 | 사진 재업로드 유도 |
| `UNSUPPORTED_CONTENT_TYPE` | 미지원 형식이거나 크기 범위 밖 | 선택 단계에서 미리 막을 것 |
| `NOT_POST_OWNER` | 남의 글 삭제·수정 시도 | 토스트(버튼을 숨기면 안 뜬다) |
| `POST_NOT_EDITABLE` | 숨겨진 글 수정 시도 | 수정 메뉴를 비활성화해 미리 막을 것 |
| `POST_NOT_FOUND` | 이미 삭제된 글 | 목록 새로고침 |
| `NOT_COMMENT_OWNER` | 남의 댓글 삭제 시도 | 토스트 |
| `COMMENT_NOT_FOUND` | 이미 삭제된 댓글 | 목록 새로고침 |
| `COMMENT_BODY_REQUIRED` | 댓글이 비었거나 공백뿐 | 입력 필드 |
| `COMMENT_BODY_LENGTH_INVALID` | 댓글 500자 초과 | 입력 필드 |
| `CANNOT_BLOCK_SELF` | 자기 차단 | UI에서 미리 막을 것 |
| `MEMBER_NOT_FOUND` | 없는 회원 | 토스트 |
| `ALREADY_REPORTED` | 같은 대상 재신고 | "이미 신고했습니다" |
| `REPORT_DETAIL_REQUIRED` | `OTHER`인데 상세 없음 | 입력 필드 |
| `INVALID_INPUT` | 형식 위반(잘못된 커서 등) | 토스트 |

**`PHOTO_NOT_UPLOADED`는 세 원인이 한 코드다** — 미업로드·타인 키·위조 키를 구분해 주지
않는다(키 존재 여부를 캐낼 수 있어서다). 앱도 구분해 안내할 수 없다.

### 오류가 아닌 것 (멱등 동작)

아래는 `success: true`로 돌아온다. 실패로 처리하지 말 것.

- 이미 좋아요한 글에 `likePost` → `likeCount` 변화 없음
- 좋아요하지 않은 글에 `unlikePost` → 0 아래로 안 내려감
- 이미 차단한 사람에게 `blockUser` / 차단하지 않은 사람에게 `unblockUser`
- 이미 없는 오브젝트에 `deletePostImage`

**낙관적 업데이트를 쓴다면 응답의 `likeCount`로 되맞출 것.** 서버 값이 정본이다.

## 8. 글자 수 세기 — 이모지 주의

제목 **50자**, 본문·댓글 **500자**, 태그 **30자**인데, 서버는 전부 **코드포인트**로 센다.

| 입력 | 사용자가 보는 글자 | 서버 계산 |
|---|---|---|
| `🥲` | 1 | 1 |
| `🇰🇷` (국기) | 1 | 2 |
| `👨‍👩‍👧‍👦` (ZWJ 결합) | 1 | 7 |

앱이 `String.length`(UTF-16)나 grapheme 단위로 세면 서버와 숫자가 어긋나
"499자인데 거부됨" 같은 상황이 생긴다.

**권장:** 입력 카운터를 **코드포인트 기준**으로 맞출 것.
- Dart/Flutter: `body.runes.length`
- JS: `[...body].length`

앞뒤 공백은 서버가 제거한 뒤 판정한다.

## 9. 다국어

- **`TargetCategory`는 앱이 매핑한다.** 서버가 표시 문자열을 내려주지 않는다
  (`SpotCategory`와 같은 방식, POL-023). `communityChips`도 enum 값과 순서만 내려준다

  필터링 시 대소문자와 선행 `#`은 서버가 무시하므로 앱이 정규화할 필요가 없다
- `PostSpot`의 제목·썸네일은 `Accept-Language`를 따른다

## 10. 지역 피드 주의

```graphql
posts(latitude: 37.5665, longitude: 126.9780, radiusMeters: 5000)
```

- `radiusMeters` 기본 20000 / **상한 100000** — 초과해도 오류가 아니라 잘린다
- **반경 안의 결과는 잘리지 않는다.** 예전에는 장소 수 상한(2000) 때문에 반경 안인데도
  안 보이는 글이 있었으나(기본 반경에서 대부분이 잘렸다), 지금은 반경 조건이 글 조회에
  직접 걸려 상한이 없다
- **장소 없는 글은 지역 피드에 나타나지 않는다.** 좌표가 없으니 당연하지만,
  "내가 쓴 글이 안 보인다"는 문의로 이어질 수 있다

## 11. 아직 없는 것

- **알림 없음.** 내 글에 댓글·좋아요가 달려도 푸시가 없다(비범위)
- **수정 이력 없음.** `edited` 플래그만 있고 이전 내용은 보관하지 않는다
- **대댓글 없음.** 1단계 댓글만. `Comment`에 부모 필드가 아예 없다
- **본문 검색 없음.** `posts(tag:)`와 상단 칩으로 갈음
- **고아 오브젝트 정리 없음.** 업로드만 하고 글을 안 쓴 경우 — 스토리지 lifecycle로 처리할 사안

## 12. 개발 환경 확인용 데이터

`R__seed_community.sql`이 더미 데이터를 넣는다(로컬·개발 전용). **회원 20번이 주인공**이다.

| 회원 | 20번으로 로그인해 조회했을 때 |
|---|---|
| 20 | 본인 글 4건, `ownedByViewer: true` |
| 19 | 글 2건·댓글 1건이 **안 보여야** 함 (20이 차단) |
| 18 | 글 1건·댓글 1건이 **안 보여야** 함 (18이 20을 차단 — 양방향 확인) |
| 17 | 숨김 글 1건 안 보임 + 정상 글 1건은 보임 |
| 12·14·15·16 | 글 7건 정상 표시 |

확인 포인트:

- 20번으로 조회 시 **16건 중 12건**이 보이면 정상
  (제외 4건 = 19번 글 2건 + 18번 글 1건 + 17번의 숨김 글 1건)
- **장소 없는 글 1건**(14번 "여행 짐 싸는 팁") — `spot: null`로 내려온다.
  장소 칩을 그리지 않는 분기를 이 글로 확인할 것. 좌표 반경 조회에는 안 잡힌다
- `edited: true`인 글 1건(15번 덕수궁 글) — "수정됨" 표시 확인용
- 경복궁 후기는 `commentCount: 4`인데 20번에게는 **3건**만 온다(19번 것이 차단)
- 북촌 글은 `commentCount: 1`인데 20번에게는 **0건**이다(18번이 20을 차단)
  → 둘 다 §6에서 설명한 정상 동작이다
- `posts(tag: "seoul")` — 대소문자가 다른 태그 2건이 함께 잡혀야 함
- `communityChips`는 `X-App-Key`·`Accept-Language`에 따라 다르다:
  `k-trip-spot`은 언어별 8건, `demo-app`은 국문 2건, 헤더가 없거나 모르는 값이면 기본 앱
- 사진 키는 실제 오브젝트가 없어 CDN에서 404다. 키·순서 확인용

## 13. 붙이는 순서 제안

1. **읽기부터.** `posts(spotId:)`로 spot 상세에 피드를 붙인다
2. **커서 페이징**을 붙이고 `hasNextPage`로 무한 스크롤을 확정한다
3. **상호작용**(좋아요·댓글). 멱등이라 낙관적 업데이트가 쉽다
4. **글 작성 — 사진 없이 먼저.** `photoKeys: []`를 넘기면 된다
5. **사진 업로드**를 마지막에. 4단계 흐름이라 가장 손이 많이 간다
6. 차단·신고·상단 칩

§4의 업로드 순서와 §6의 모더레이션이 이 기능에서 가장 자주 어긋나는 지점이다.
