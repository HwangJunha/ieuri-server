# 커뮤니티 클라이언트 가이드 (2차) — 추가된 기능

1차 가이드(`problem/커뮤니티_클라이언트_가이드.md`) 이후 **추가된 것만** 담는다.
기존 내용(인증·헤더·사진 업로드·페이지네이션·에러 처리·모더레이션)은 1차 문서를 그대로 따른다.

> **스키마가 정본이다.** `src/main/resources/schema/community.graphqls`를 함께 볼 것.
> 문서와 스키마가 어긋나면 스키마가 맞다.

---

## 0. 작업 범위 한눈에

네 가지가 추가됐다. **기존 호출은 하나도 깨지지 않는다** — 새 인자에 전부 기본값이 있다.

| # | 기능 | 클라이언트 작업 | 필수도 |
|---|---|---|---|
| 1 | **대댓글** | 답글 UI + `replies` 요청 | 큼 |
| 2 | **게시물 숨기기** | ⋮ 메뉴 + 숨김 목록 화면 | 중간 |
| 3 | **거리순 정렬** | 정렬 토글 | 중간 |
| 4 | **조회수** | 숫자 하나 표시 | 작음 |
| 5 | **글 수정 범위 확대** | 수정 화면에 카테고리·장소·태그 추가 | 중간 |

우선순위를 매긴다면 **2 → 1 → 3 → 4**를 권한다. 2는 스토어 심사와 맞닿아 있고,
1은 화면 구조가 바뀌어 손이 가장 많이 간다.

## 1. 대댓글 (깊이 2단계)

### 무엇이 바뀌나

**`comments(postId:)`가 이제 최상위 댓글만 준다.** 답글은 각 댓글의 `replies`에 담겨 온다.

```graphql
query {
  comments(postId: 42, first: 20) {
    edges {
      node {
        id body createdAt ownedByViewer hidden
        author { id nickname profileImageUrl }
        replies {                       # ← 답글. 요청해야 조회된다
          id body createdAt ownedByViewer hidden
          parentCommentId
          author { id nickname profileImageUrl }
        }
      }
    }
    pageInfo { hasNextPage endCursor }
  }
}
```

**기존 화면을 안 고치면** 답글이 안 보일 뿐 깨지지는 않는다 — `replies`를 요청하지 않으면
지금까지처럼 최상위 댓글만 나온다.

### 답글 달기

```graphql
mutation {
  createComment(input: { postId: 42, body: "답글이에요", parentCommentId: 7 }) {
    success userErrors { code message } commentId
  }
}
```

`parentCommentId`를 생략하면 최상위 댓글이다.

### 반드시 알아야 할 것

- **답글에 답글을 달아도 거부되지 않는다.** 그 답글의 부모(최상위)에 달린 것으로 눕혀
  깊이 2단계를 유지한다. 따라서 **응답의 `parentCommentId`가 넘긴 값과 다를 수 있다** —
  화면을 낙관적으로 갱신한다면 이 점을 감안할 것
  ```
  최상위 댓글 #7 에 답글 → parentCommentId: 7
  답글 #9(부모 #7)에 답글 → parentCommentId: 7  ← 9가 아니다
  ```
- `replies`는 **오래된 순**이다. 대화 흐름이라 최신순으로 뒤집으면 문맥이 끊긴다
  (최상위 목록은 여전히 최신순)
- `replies`에 **페이지네이션이 없다.** 깊이가 2단계라 한 댓글의 답글이 화면을 넘길 만큼
  많지 않다고 봤다. 아주 많이 달리는 글이 생기면 알려 줄 것
- 답글의 `replies`는 **항상 빈 목록**이다(3단계가 없다). 굳이 요청할 필요 없다
- `parentCommentId`가 null이면 최상위, 있으면 답글이다 — **들여쓰기 판정에 쓴다**
- **`commentCount`에 답글도 포함된다.** "댓글 5개"는 최상위 3 + 답글 2일 수 있다
- 부모 댓글이 삭제돼도 **답글은 남는다**("삭제된 댓글입니다" 자리에 답글이 달린 모습)
- 다른 글의 댓글을 `parentCommentId`로 지정하면 `COMMENT_NOT_FOUND`
- `Post.commentPreview`는 **최상위만** 올린다(카드 미리보기라 답글까지 넣지 않는다)

### 화면 구조 제안

```
┌────────────────────────────────┐
│ 댓글 (commentCount: 5)          │
├────────────────────────────────┤
│ 홍길동  경복궁 좋네요            │
│                    [답글 달기]  │
│    └ 김철수  저도요!            │   ← replies (들여쓰기)
│    └ 이영희  언제 가셨어요?      │
├────────────────────────────────┤
│ 박민수  주차가 문제죠            │
│                    [답글 달기]  │
└────────────────────────────────┘
```

답글 카드에는 **"답글 달기" 버튼을 띄우지 않아도 된다** — 눌러도 최상위에 달리므로
사용자가 혼란스러울 수 있다. 대신 답글에 답하려면 **최상위 댓글의 버튼**을 쓰게 하거나,
멘션(`@김철수`)을 본문에 넣는 방식이 자연스럽다.

## 2. 게시물 숨기기

### 무엇을 위한 것인가

지금은 마음에 안 드는 글 하나를 안 보려면 **작성자를 통째로 차단**해야 한다. 과한 조치라
사용자가 잘 쓰지 않는다. 글 단위로 감출 수단을 추가했다.

**신고·차단과 각각 다르다.**

| | 대상 | 효과 | 되돌리기 |
|---|---|---|---|
| `hidePost` | 글 하나 | **내 화면에서만** 즉시 사라짐 | 가능 |
| `blockUser` | 사람 | 그 사람 글·댓글 전부 사라짐(양방향) | 가능 |
| `reportContent` | 글·댓글·사람 | 운영 조치 요청(5건 누적 시 자동 숨김) | 불가 |

### API

```graphql
mutation { hidePost(input: { postId: 42 }) { success userErrors { code message } } }
mutation { unhidePost(input: { postId: 42 }) { success userErrors { code message } } }

# 숨긴 글 목록 (해제 화면)
query { posts(hiddenByViewer: true) { edges { node { id title createdAt } } } }
```

### 반드시 알아야 할 것

- **숨긴 글은 모든 조회에서 빠진다** — 피드도, `post(id:)` 단건도 null이다.
  **`hiddenByViewer: true`일 때만** 보인다
- **남의 글이든 내 글이든** 숨길 수 있다(소유권을 보지 않는다). 조치가 아니라 화면 설정이다
- 둘 다 **멱등**이다 — 이미 숨긴 글에 다시 호출해도, 숨기지 않은 글을 해제해도 `success: true`
- 해제는 **삭제된 글에도 동작한다** — 그래야 목록에 남지 않는다
- `hiddenByViewer: true`에도 **카테고리·태그 필터와 정렬이 그대로** 적용된다.
  별도 쿼리로 만들지 않은 이유가 이것이다
- **`Post.hidden`과 다른 값이다.** 그쪽은 신고 5건 누적으로 **모두에게** 감춰진 글이고
  (작성자 본인에게만 보인다), 이건 내가 나에게만 감춘 것이다. 이름이 비슷하니 주의할 것

### ⋮ 메뉴 (갱신)

| 메뉴 | API | 노출 조건 |
|---|---|---|
| 수정 | `editPost` | `ownedByViewer && !hidden` |
| 삭제 | `deletePost` | `ownedByViewer` |
| **이 글 숨기기** | **`hidePost`** | **항상** |
| 이 사용자 차단하기 | `blockUser` | `!ownedByViewer` |
| 이 글 신고하기 | `reportContent` | `!ownedByViewer` |

숨김 목록은 설정 화면에 두는 것이 일반적이다(차단 목록 옆).

## 3. 거리순 정렬

### 두 문제를 함께 고쳤다

이전에는 **가까운 글이 위로 오지 않았고**(내부 정렬이 id 순이었다), **장소 없이 쓴 글이
지역 피드에서 아예 안 보였다.**

```graphql
posts(latitude: 37.4665, longitude: 126.8956, sort: DISTANCE)
posts(latitude: 37.4665, longitude: 126.8956, sort: LATEST)    # 기본
```

| `sort` | 무엇이 보이나 | 순서 |
|---|---|---|
| `LATEST` (기본) | 반경 안 글 **+ 장소 없이 쓴 글** | 최신순 |
| `DISTANCE` | 반경 안 장소에 붙은 글만 | **가까운 장소 순**, 같은 장소끼리는 최신순 |

앱에서는 **"거리순 / 최신순" 토글**로 그리면 된다(당근 동네생활과 같은 형태).

### 반드시 알아야 할 것

- **장소 없이 쓴 글은 `DISTANCE`에서 빠진다.** 거리가 없어 목록의 어디에 둘지 정할 수 없다.
  그런 글까지 보려면 `LATEST`
- **좌표를 주지 않으면 `DISTANCE`도 `LATEST`처럼 동작한다.** 오류가 아니다 —
  위치 권한을 못 받아도 피드는 그려진다
- **정렬을 바꾸면 커서를 버리고 첫 페이지부터 다시 조회할 것.** 두 정렬의 커서 형식이 달라
  이전 커서를 그대로 넘기면 `INVALID_INPUT`이 온다
- **반경 안의 결과가 더 이상 잘리지 않는다.** 이전에는 내부 상한(2,000곳) 때문에 반경 안인데도
  안 보이는 글이 있었다 — 기본 반경 20km 기준으로 대부분이 잘리고 있었다
- `spotId`와 좌표를 **함께 줄 수 있다.** 서로 배타적이지 않으며 둘 다 조건이 된다

## 4. 조회수

`Post.viewCount`가 추가됐다. 필드 하나만 요청하면 된다.

```graphql
{ id title likeCount commentCount viewCount }
```

### 반드시 알아야 할 것

- **`post(id:)` 단건 조회에서만 오른다.** 피드 목록에 카드가 뜨는 것은 조회로 세지 않는다 —
  스크롤 한 번에 수십이 올라가면 숫자가 의미를 잃는다
- **중복을 걸러 내지 않는다.** 같은 사람이 새로고침하면 계속 오른다. **고유 방문자 수가 아니다**
- **방금 올린 조회가 그 응답에는 반영되지 않을 수 있다.** 증가는 응답과 별개로 처리된다.
  상세를 열자마자 +1을 보여주고 싶다면 **앱에서 더해 그리는 편**이 낫다
- 차단·숨김으로 못 본 글은 오르지 않는다
- 정산·과금에 쓸 수 있는 정확한 수치가 아니다

## 5. 글 수정 — 카테고리·장소·태그도 바뀐다

이전에는 제목·본문·사진만 고칠 수 있었다. 이제 **작성 화면과 같은 항목을 전부** 고칠 수 있다.

```graphql
mutation {
  editPost(input: {
    postId: 42
    title: "새 제목"          # 필수
    body: "새 본문"           # 필수
    category: RESTAURANT      # 생략하면 그대로
    tags: ["야경", "맛집"]     # 생략하면 그대로, []면 전부 뗀다
    changeSpot: true          # 장소를 바꾸겠다는 의도
    spotId: 11094             # changeSpot이 true일 때만 쓰인다
  }) { success userErrors { code message } }
}
```

### null과 빈 값이 다르다

| 필드 | 생략(null) | 빈 값 |
|---|---|---|
| `photoKeys` | 사진 그대로 | `[]` → 사진 전부 뗌 |
| `tags` | 태그 그대로 | `[]` → 태그 전부 뗌 |
| `category` | 그대로 | — (빈 값 없음) |

### 장소는 `changeSpot` 플래그로 의도를 받는다

`spotId`의 null 하나로는 **"장소를 떼겠다"**와 **"장소를 건드리지 않겠다"**를 구분할 수 없다.
그래서 플래그를 따로 뒀다.

| `changeSpot` | `spotId` | 결과 |
|---|---|---|
| 생략/`false` | 무엇이든 | **장소 그대로** |
| `true` | `11094` | 그 장소로 바꿈 |
| `true` | 생략 | **장소를 뗌**(카테고리만 있는 글이 됨) |

- 없는 장소를 주면 `SPOT_NOT_FOUND`
- 태그 규칙은 생성과 같다 — 공백 불가, 30자 이내, 최대 5개, 선행 `#`은 서버가 제거
- **숨겨진 글(`hidden: true`)은 여전히 수정할 수 없다** → `POST_NOT_EDITABLE`
- 수정하면 `edited: true`가 된다(항목과 무관하게)

**장소를 바꾸면 그 글이 지역 피드에서 옮겨 간다.** 거리순 정렬에서 위치가 달라지고,
장소를 떼면 거리순에서 아예 빠진다(최신순에는 남는다).

## 6. 사진 키 형식 변경 (주의)

오브젝트 키에 도메인 구간이 들어갔다.

```
이전:  images/{memberId}/{uuid}
이후:  images/community/{memberId}/{uuid}
```

**앱이 키를 만들거나 파싱하지 않는다면 영향이 없다** — 서버가 주는 값을 그대로 쓰고,
CDN 베이스와 조합하는 방식도 그대로다.

```
https://cdn.ieuri.co.kr/{photoKey}
```

다만 **키 형식을 하드코딩한 곳이 있다면 고쳐야 한다.** 옛 형식 키는 서버가 거부한다.

## 7. 개발 환경 확인용 데이터 (갱신)

시드가 바뀌었다. **회원 20번이 주인공**인 것은 그대로다.

| 확인 항목 | 기대 결과 |
|---|---|
| `posts()` | **16건 중 10건** |
| `posts(hiddenByViewer: true)` | **2건** (경복궁 휴무일, 청계천 야경) |
| `comments(postId:)` — 경복궁 후기 | 최상위 3건 + 그중 하나에 `replies` 2건 |
| `posts(sort: DISTANCE, latitude: 37.4665, longitude: 126.8956)` | 가까운 순 |
| `posts(tag: "seoul")` | 2건 (대소문자 무관) |

**10건이 되는 계산:** 전체 16건 − 차단 3건(19번 2 + 18번 1) − 자동 숨김 1건(17번)
− **개별 숨김 2건**(20번이 숨김).

숨긴 글의 작성자(12·16번)는 **차단 대상이 아니다** — 그 사람의 **다른 글은 그대로 보인다**.
12번의 서울광장 글이 남아 있는 것으로 확인할 수 있다. 차단과 숨기기가 다른 축이라는 증거다.

## 8. 정리 — 스키마 변경 목록

| 종류 | 이름 | 비고 |
|---|---|---|
| 쿼리 인자 | `posts(sort:)` | 기본 `LATEST` |
