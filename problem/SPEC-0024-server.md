# SPEC-0024 — 서버 설계

요구사항·수용 기준·계약은 위 스펙에 있습니다. 이 문서는 서버 쪽 설계 결정만 다룹니다.

## 1. 변경의 성격

세 층이 각각 바뀝니다.

| 층 | 변경 |
|---|---|
| 도메인 | `Member.registerSns`의 인증 면제 판정 축소, 이메일 변경 가능 여부 불변식 신설 |
| 애플리케이션 | `loginByEmail`의 미인증 차단 제거, 인증 주소 재입력 유스케이스 신설, 이메일 변경의 provider 판정 |
| 어댑터 | 미인증 게이트(횡단 관심사), `EMAIL_NOT_VERIFIED`의 예외 분류 이동 |

## 2. 도메인

### 인증 면제 판정의 축소 (R2·R3)

`Member.registerSns`의 현재 판정은 3중 조건입니다.

```
providerEmailVerified && providerEmail != null && providerEmail == submittedEmail
```

이것이 `providerEmail != null` 하나로 축소됩니다. 나머지 두 조건이 사라지는 근거는 서로 다릅니다.

- **`providerEmailVerified` 제거** — R2가 provider의 검증 플래그를 판단에 쓰지 않기로 정했습니다. 우리가 provider의 서명을 신뢰해 신원을 위임하는 이상(POL-030), 같은 provider가 준 이메일을 따로 의심할 근거가 없습니다.
- **`providerEmail == submittedEmail` 제거** — R1이 편집을 막으므로 두 값은 항상 같습니다. 조건이 의미를 잃습니다.

**R12가 이 축소를 안전하게 만듭니다.** provider가 이메일을 준 경우 서버는 제출값을 쓰지 않고 provider 응답값을 저장합니다. 따라서 클라이언트가 R1을 어겨 편집을 허용하더라도 편집된 값은 저장에 도달하지 않습니다 — 비교를 없앨 수 있는 이유가 R1(클라이언트가 지켜줄 것)이 아니라 R12(제출값을 아예 쓰지 않음)입니다.

구현 시 주의: `registerSns`에 provider 이메일과 제출 이메일을 **둘 다 넘기지 말고**, 호출부에서 이미 결정된 하나의 값만 넘기는 편이 안전합니다. 두 값이 도메인까지 흘러가면 어느 쪽을 써야 하는지 판단이 도메인에 새로 생깁니다.

`registerSns`의 시그니처에서 `providerEmailVerified` 파라미터가 불필요해집니다. 호출부(`CompositeSnsIdentityVerifier`가 채우는 경로)까지 함께 정리합니다.

### 이메일 변경 가능 여부 (R6)

`Member`에 provider 기반 판정을 둡니다. 애플리케이션 계층이 `if (provider != EMAIL) throw`를 직접 쓰지 않고 도메인에 묻습니다 — 규칙이 도메인 불변식이지 서비스의 분기가 아니기 때문입니다.

이 값이 그대로 `Me.canChangeEmail`로 나갑니다. 조회 모델(`MemberReadModels`)에 필드를 추가하되, 저장하지 않고 `provider`에서 파생합니다. 저장하면 provider와 어긋날 수 있는 두 번째 진실이 생깁니다.

### 인증 주소 재입력 (R7)

`Member`에 인증 대기 주소를 정정하는 동작을 둡니다. 불변식은 **`emailVerified`가 거짓일 때만 허용**입니다. 참인 회원의 호출은 도메인에서 거부합니다.

`Provider.EMAIL` 회원의 경우 이메일이 곧 식별자이므로(`provider_user_id` = 정규화 이메일의 HMAC, SPEC-0012 R1), 주소 정정은 **식별자 재계산을 동반**합니다. SNS 회원은 식별자가 provider가 준 id이므로 이메일만 바뀝니다. SPEC-0011 R7이 이미 `updateEmail(memberId, newEmail, protectedIdentifier)` 형태로 이 비대칭을 다루고 있으므로 같은 형태를 따릅니다 — SNS는 `null`을 전달합니다.

> **[구현 변경 · 2026-08-17] 정정 시점이 아니라 인증 통과 시점에 반영합니다.**
>
> 착수 시 설계는 정정 요청 즉시 회원의 이메일을 바꾸는 것이었으나, 구현 리뷰에서 **주소 선점**이 드러나 바꿨습니다. R5의 `(provider, email)` 유니크는 회원 행을 기준으로 판정하므로, 소유를 증명하지 않은 주소를 즉시 회원 행에 쓰면 그 주소가 곧바로 선점됩니다. 미인증 회원이 정정을 반복하면 임의의 주소로 타인의 가입을 막을 수 있고, 게이트(R9)는 본인의 앱 사용만 막을 뿐 이 피해를 막지 못합니다. `Provider.EMAIL` 회원은 `provider_user_id`까지 함께 옮겨가 원래 주소로 로그인할 수도 없게 됩니다.
>
> 그래서 **`EmailChangeService`의 선례를 따릅니다** — 새 주소를 `EmailVerification.targetEmailEncrypted`에 암호문으로 두고(POL-012), `verifyEmail`이 통과할 때 회원에게 확정합니다. 이 구조가 이미 이메일 변경에 있으므로 새 장치를 만들지 않았습니다.
>
> 부수 변경: V42의 `ck_ev_target_email`이 "REGISTRATION이면 대상이 없다"를 강제하고 있어 V63에서 완화했습니다. 남는 규칙은 "EMAIL_CHANGE는 대상이 반드시 있다" 한쪽입니다. 도메인 `EmailVerification`의 `init` 불변식도 같이 맞췄습니다.

## 3. 애플리케이션

### 로그인 (R8)

`AuthTokenService.loginByEmail`의 `EmailNotVerifiedException` 분기를 제거합니다. 비밀번호 검증과 `ensureLoginable`은 그대로입니다. `loginBySns`는 원래 이 검사가 없었으므로 변화가 없습니다.

이 제거로 두 로그인 경로의 인증 관련 동작이 동일해집니다 — 어느 쪽도 `emailVerified`를 보지 않습니다.

### 인증 주소 재입력 유스케이스 (R7)

기존 `EmailVerification` / `VerificationPolicy`를 재사용합니다. SPEC-0011이 이메일 변경에서 같은 판단을 내렸고(별도 테이블을 만들면 코드 발급·만료·시도 상한을 두 번 구현하게 됨), 여기서도 같습니다.

동작 순서:

1. 회원의 `emailVerified`가 참이면 거부 (R7-2)
2. 새 주소가 같은 provider에 이미 있으면 거부 (R7-4, R5)
3. 재발송 쿨다운 창을 확인 — `resendVerification`과 **같은 창**을 공유 (R7-3)
4. 기존 대기 검증을 무효화하고 새 주소로 코드 발급 (R7-1)

`VerificationPurpose`에 새 값을 추가할지 기존 회원가입 목적을 재사용할지는 서버 하네스 판단입니다(스펙 §8 Q3). 재입력은 새 목적이 아니라 같은 목적의 대상 변경에 가까우므로 재사용이 자연스러워 보이나, R7-1이 무효화 범위를 **가입 인증 목적만**으로 규정하므로 그 범위를 정확히 표현할 수 있는 쪽을 택하십시오. 같은 회원이 이메일 변경 검증을 동시에 대기 중일 수 있습니다.

### 이메일 변경의 provider 판정 (R6)

`changeEmail` 유스케이스 진입 시 도메인에 변경 가능 여부를 물어 거짓이면 `NOT_EMAIL_MEMBER`로 거부합니다. `confirmEmailChange`·`resendEmailChange`에는 같은 판정을 두지 않습니다 — `changeEmail`이 성립하지 않으면 도달할 수 없는 경로이고, 같은 규칙을 세 곳에 복제하면 어긋날 여지만 생깁니다.

## 4. 미인증 게이트 (R9)

이 스펙에서 가장 침습적인 부분입니다.

### 위치

허용 목록 7개를 제외한 모든 오퍼레이션에 걸리는 **횡단 관심사**이므로, 리졸버마다 검사를 심지 않고 단일 지점에 둡니다. `SecurityGraphqlExceptionHandler`가 이미 `UNAUTHENTICATED`·`FORBIDDEN`을 최상위 오류로 내보내고 있으므로(POL-016), 같은 계층에 얹는 것이 자연스럽습니다.

허용 목록은 화이트리스트입니다 — 블랙리스트로 두면 새 오퍼레이션이 추가될 때마다 조용히 열립니다.

```
query    me
mutation verifyEmail
mutation resendVerification
mutation retargetEmailVerification
mutation withdrawMember
mutation refreshToken
mutation logout
```

`withdrawMember`와 `logout`이 들어가는 이유는 인증 화면에 갇힌 회원의 탈출구이기 때문입니다. 이것이 없으면 잘못된 주소로 가입한 회원이 계정을 버릴 수도, 쓸 수도 없는 상태가 됩니다.

> **[구현 추가 · 2026-08-17] 인증 이전 단계 오퍼레이션 7개를 함께 통과시킵니다.**
>
> `loginEmail` · `loginSns` · `registerEmailMember` · `registerSnsMember` · `requestPasswordReset` · `resetPassword` · `authHealth`.
>
> 게이트는 "주체가 있는가"로 걸리는데, JWT 필터는 오퍼레이션을 가리지 않고 유효한 토큰이면 주체를 세웁니다. R8이 미인증 회원에게 오래 쓰는 토큰을 주기로 한 이상, 그 토큰을 든 채 **다른 계정으로 로그인**하려는 요청이 `loginEmail`에서 `EMAIL_NOT_VERIFIED`로 막힙니다. 목록에 없으면 탈출구가 탈퇴·로그아웃뿐이 됩니다.
>
> 이 7개는 토큰의 주체를 읽지 않으므로 통과시켜도 접근 범위가 넓어지지 않습니다. 스펙 R9의 "일곱 가지"는 **인증 화면이 쓰는 오퍼레이션**의 목록이고, 이 추가분은 그와 다른 축이라 코드에서도 두 집합을 나눠 두었습니다.

`refreshToken`은 세션 유지 때문입니다. accessToken 만료가 5분이므로(POL-008) 갱신을 막으면 인증 코드를 입력하는 도중 세션이 끊깁니다. R8이 미인증 회원에게 토큰을 발급하기로 한 이상, 그 토큰이 갱신 가능해야 의미가 있습니다.

### 예외 분류의 이동

`EmailNotVerifiedException`은 현재 `UserFacingException("EMAIL_NOT_VERIFIED")`이며 payload의 `userErrors`로 나갑니다. 이것을 최상위 인증류 예외로 옮깁니다. 코드 문자열은 같고 위치가 바뀝니다.

`loginEmail`이 이 예외를 던지던 유일한 곳이었고 R8이 그것을 제거하므로, 기존 사용처와 충돌하지 않습니다.

### 인증되지 않은 요청과의 구분 (R9-5)

토큰이 없는 요청은 이 게이트에 도달하기 전에 기존 인증 처리에서 걸러져야 합니다. 게이트는 "인증됐으나 이메일 미인증"만 판정합니다. 순서가 뒤집히면 비로그인 요청이 `EMAIL_NOT_VERIFIED`를 받아 클라이언트가 잘못된 화면으로 보냅니다.

### 판정 단위의 분리

허용 목록 판정은 **오퍼레이션 이름과 인증 완료 여부를 받아 통과·거부를 반환하는 순수 함수**로 분리합니다. 스펙 R9-1~R9-5가 이 함수를 대상으로 쓰여 있습니다. 어댑터는 이 함수를 호출하고 결과에 따라 예외를 던지는 역할만 합니다.

분리하지 않으면 게이트가 어댑터 안에만 존재해 시험할 수 없습니다.

### 판정에 쓸 값의 출처

게이트가 매 요청 DB를 조회하면 비용이 큽니다. 토큰 클레임에 `emailVerified`를 넣는 방법이 있으나, **인증 완료 시점과 토큰 만료 시점의 불일치**를 낳습니다 — 인증을 마쳐도 기존 토큰이 만료될 때까지 게이트에 걸립니다. accessToken 만료가 5분이므로(POL-008) 최대 5분입니다.

서버 하네스 판단에 맡기되, 클레임을 쓴다면 **인증 성공 시 토큰을 재발급**해 이 창을 없애는 편이 낫습니다. 클라이언트는 인증 직후 메인으로 진입해야 하는데(R10-3), 그 시점에 게이트에 막히면 요구사항이 깨집니다.

## 5. 유니크 제약 (R5)

`(provider, email)` 유니크입니다. 식별 키는 `provider_user_id` 그대로이며 이 제약이 식별 방식을 바꾸지 않습니다.

주의할 점 두 가지입니다.

- **이메일 컬럼은 암호화 저장 대상입니다**(POL-012). 암호문에 유니크 인덱스를 걸면 암호화 방식이 결정론적이어야 성립합니다. `provider_user_id`가 이미 결정론적 HMAC으로 같은 문제를 푼 선례입니다(SPEC-0012 R1). 이메일 컬럼의 현재 저장 방식을 확인하고, 결정론적이지 않다면 유니크 판정용 파생 컬럼이 필요합니다.
- **정규화가 선행되어야 합니다.** 대소문자·공백 차이가 서로 다른 값으로 저장되면 제약이 무력해집니다. SPEC-0012 R2가 이미 정규화 규칙을 정해 두었으므로 그것을 따릅니다.

`(KAKAO, a@b.com)`과 `(EMAIL, a@b.com)`은 공존합니다 (R5-2, POL-002).

## 6. 데이터 전제

**운영 데이터가 없습니다.** 착수 시 회원·reaction·community 데이터를 전량 삭제합니다. 이 삭제는 스펙의 요구사항이 아니라 구현의 전제이며, 서버 하네스가 착수 시점에 수행합니다.

따라서 기존 회원의 `emailVerified` 소급 전환, 유니크 제약 위반 데이터의 사전 정리, `provider_user_id` 재계산 같은 마이그레이션 작업이 **전부 불필요**합니다.

SPEC-0012 R3 마이그레이션(`V39__ProtectEmailLoginIdentifier`)이 실제 DB에 적용됐다는 기록이 없습니다(스펙 §8 Q2). 데이터를 지우더라도 스키마 상태는 남으므로, R5의 유니크 제약을 얹기 전에 현재 스키마가 어느 버전인지 확인하십시오.

## 7. 단위 테스트가 짊어질 단위

**도메인**

- `Member.registerSns` — provider 이메일 유무에 따른 `emailVerified` 산출 (R2-1, R2-2, R3-1). 특히 **검증 플래그가 거짓인데도 참이 되는 경우**(R2-2)가 이 변경의 핵심이므로 반드시 포함합니다
- `Member`의 이메일 변경 가능 여부 판정 — provider별 (R6-3, R6-4)
- `Member`의 인증 주소 재입력 불변식 — `emailVerified`가 참이면 거부 (R7-2)

**애플리케이션** (포트는 스텁)

- `loginByEmail` — 미인증 회원의 성공 (R8-1)
- 인증 주소 재입력 유스케이스 — 쿨다운 공유(R7-3), 중복 주소 거부(R7-4), 기존 검증 무효화(R7-1), 정정 후 인증 완료(R7-5)
- `changeEmail` — SNS 회원 거부(R6-2), EMAIL 회원 성공(R6-1)
- 가입 유스케이스 — provider 유무에 따른 `verificationId` 반환 여부 (R2-3, R3-1, R4-1)
- 유니크 충돌 시 응답·로그에 상대 회원 정보 미포함 (R5-4)

- 게이트 판정 함수 — §4에서 분리한 순수 함수. 허용 목록 통과·비목록 거부·인증 완료 시 전면 통과 (R9-1~R9-5)
- 저장 이메일의 출처 — provider 제공 시 제출값 무시, 미제공 시 제출값 사용 (R12-1, R12-2, R12-3)

**시험하지 않는 것.** 실제 GraphQL 요청이 최상위 오류로 나가는지는 전송 계층에서만 관찰되므로 시험하지 않습니다. 인프라 테스트를 만들지 않습니다.

**R5의 유니크 제약**은 DB 제약이므로 단위 테스트로 증명되지 않습니다. 애플리케이션 수준에서는 저장소 조회를 스텁으로 주고 "중복이면 거부"까지만 시험합니다(R5-1~R5-3, R5-5). 제약 자체는 최종 방어선으로 두고 시험하지 않습니다.

## 8. 알려진 약점

**클라이언트 폼과 저장값의 괴리 (R12의 대가).** provider가 이메일을 준 경우 서버가 제출값을 버리므로, 클라이언트가 R1을 어겨 편집을 허용하면 **사용자가 입력한 주소와 실제 저장된 주소가 달라집니다.** 보안은 지켜지지만 사용자는 자기가 입력한 주소로 가입됐다고 믿게 됩니다.

서버가 이 괴리를 감지할 수는 있습니다 — 제출값과 provider 값이 다르면 로그를 남기는 정도입니다(POL-047의 마스킹 형식 적용). 요청을 거부하지는 않습니다. 거부하면 R12가 조용히 무시하기로 한 값 때문에 가입이 실패하게 되어, 클라이언트 버그가 가입 장애로 번집니다.

근본 해결은 클라이언트가 R1을 지키는 것입니다. 서버는 저장값의 정확성만 보장합니다.
