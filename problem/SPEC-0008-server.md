# SPEC-0008 — 서버 설계

요구사항·수용 기준·컨트랙트는 스펙이 authority다. 이 문서는 이 저장소의 설계 결정만 담는다.

담당 요구사항: **R-1 ~ R-6, R-15 ~ R-17.** 나머지 9건은 클라이언트 단독이다.
관련 이슈: #39 (이 스펙) · #34 (SPEC-0006 R9·R10, **#39가 흡수**).

---

## 1. 두 가지 다른 문제를 구분한다

이 스펙의 서버측은 표면적으로 하나지만 실제로는 **성격이 다른 두 문제**를 다룬다. 이 구분이
설계 전체를 가른다.

| | 부재 (R-1 ~ R-4) | 실패 (R-5 · R-6) |
|---|---|---|
| 무엇 | 업스트림에 데이터가 **없다** | 업스트림 호출이 **깨졌다** |
| 재시도 | 무의미 — 다시 물어도 없다 | 유의미 — 다음엔 될 수 있다 |
| 적재 | 부재 사실을 **기록한다** (R-3) | 기록하지 않는다 |
| 표현 | 정상 응답, `errors[]` 없음 | 필드 null + `errors[]` 항목 |
| 결과 | `overview` 등이 null인 성공 | `gallery`가 null인 부분 성공 |

두 경우 모두 클라이언트 화면에서는 "섹션이 안 보인다"로 같아 보이지만(R-8·R-9), 서버는 절대
섞으면 안 된다. 섞으면 일시적 장애가 부재로 적재되어 신선도 기준이 지날 때까지 데이터가
복구되지 않는다.

**AC-4가 이 경계를 지키는 시험이다** — 상세 조회 포트가 예외를 던지면 그것은 부재가 아니라
실패이며, 부재로 적재해서는 안 된다.

## 2. 부재의 적재 (R-3 · R-4)

### 2.1 선례를 확장한다

`spot_detail_intro`는 이미 "조회했으나 값이 없음"을 **전 컬럼 null 행**으로 남긴다. V16의 주석이
그 이유를 적어 두었다 — 그러지 않으면 값 없는 항목을 매 조회마다 미스로 판정해 TourAPI를 계속
두드린다. `spot_detail`(본문)에 같은 방식을 적용한다.

즉 이것은 새 발명이 아니라 **이미 있는 패턴을 본문 테이블로 확장**하는 일이다.

### 2.2 세 가지 상태를 구분해야 한다

R-3이 요구하는 것은 두 상태의 구분이지만, 실제로는 셋이다.

| 상태 | 판별 | 동작 |
|---|---|---|
| 미조회 | `spot_detail` 행 없음 | 업스트림 호출 (AC-10) |
| 조회함 · 부재 | 행 있음 + 부재 표시 | 업스트림 호출 안 함 (AC-9) |
| 조회함 · 존재 | 행 있음 + 본문 채워짐 | 업스트림 호출 안 함 |

**행의 존재 자체가 "조회했다"를 뜻하고, 본문 컬럼의 null 여부가 "있다/없다"를 가른다.**
별도 상태 컬럼(enum, boolean)을 두는 방법도 있으나, `spot_detail_intro`가 이미 컬럼 null만으로
같은 판정을 하고 있으므로 일관성을 위해 같은 방식을 택한다.

다만 `spot_detail`은 `spot_detail_intro`와 사정이 하나 다르다 — **`title`·`category`·
`thumbnail_image_url`·`copyright`가 NOT NULL이다.** 부재 행을 만들려면 이 컬럼들에 값이
있어야 한다. R-2가 답을 준다: 그 값들은 `spot` 행에서 온다. 부재 행은 `spot`의 값으로 채우고
`overview`·`homepage`·`tel`·`address`만 null로 둔다.

> `[TBD-1]`이 미결인 동안, 부재 행의 `fetched_at`은 정상 행과 같은 의미로 기록한다.
> 신선도 판정 로직 자체는 `[TBD-1]`이 확정되어야 완성된다(AC-13).

### 2.3 결정하지 않은 것

부재 판정을 **어느 컬럼으로 하느냐**는 구현에 맡긴다. `overview IS NULL`로 충분한지, 아니면
`overview`가 정상적으로 비어있는 spot과 구분해야 하는지는 실제 TourAPI 응답을 봐야 안다
(`[TBD-4]`가 이 관측을 요구한다). 구분이 필요하다고 판명되면 명시적 상태 컬럼이 필요하며,
그것은 `[AMEND]` 대상이다.

## 3. 부분 실패 (R-5 · R-6) — #34에서 이월

### 3.1 변경

| 필드 | 현재 | 변경 후 |
|---|---|---|
| `SpotDetail.gallery` | `[SpotImage!]!` | `[SpotImage!]` |
| `SpotDetail.infoItems` | `[SpotInfoItem!]!` | `[SpotInfoItem!]` |

`tourism.graphqls`의 해당 두 줄(현재 165행·181행 부근)이 변경 지점이다.

### 3.2 완화하지 않는 것 — 전부 의도적이다

| 대상 | 유지 | 이유 |
|---|---|---|
| `Query.spotDetail` 루트 | `SpotDetail!` | 부재해도 `spot` 값으로 유효한 객체를 구성할 수 있다(R-2). 완화하면 클라이언트에 화면 결과가 동일한 분기가 생긴다 |
| `likeCount` | `Int!` | `spot_reaction` DB 집계. 업스트림 실패 모드가 없다 (AC-22) |
| `intro` | `SpotIntro` | 이미 nullable |
| `thumbnailImageUrl` | `String!` | `spot` 행이 보유. 부재 시에도 값이 있다 |
| `copyright` · `attributionText` | non-null | `spot` 행이 둘 다 non-null로 보유. `attributionText`는 `UNSPECIFIED`여도 최소 출처를 담는다 (AC-6) |

**누락이 아니라 검토 후 제외다.** 특히 마지막 줄은 계약 설계 단계에서 갭 후보로 제기되었다가
라이브 SDL 확인으로 해소된 항목이다 — `Spot`이 두 필드를 non-null로 갖고 있어 부재 시에도
구성 가능하다.

### 3.3 null / 빈 배열을 구분하지 않는다

구분하는 필드·상태 enum·오류 payload를 **추가하지 않는다.** SPEC-0006이 내린 결정이며 이
스펙도 유지한다. 클라이언트가 두 경우를 동일하게 처리하기로 확정했다(R-8 · AC-28).

## 4. 좋아요 목록 (R-15 ~ R-17)

### 4.1 데이터는 이미 있다

`spot_reaction`이 회원별 반응을 보유한다. V20 이후 식별은 `spot_id`로 일원화되었고
유니크 제약은 `(member_id, spot_id)`다 — **`member_id`가 선행이므로 "내 좋아요 목록" 조회를
이 인덱스가 그대로 커버한다.** 새 인덱스가 필요한지는 정렬 키에 달렸다(§4.3).

`reaction = LIKE`만 반환한다. DISLIKE는 포함하지 않는다(AC-45).

**요청 언어로 한정한다**(AC-49). V20 이후 `spot_reaction`은 `language` 컬럼을 갖지 않으므로
언어 판정은 `spot` 조인으로 한다 — `spot.language = :language`. 이는 종료 축제 조회가 같은
이유로 `spot`을 조인하는 것과 동일한 패턴이다(V20 주석).

한정하지 않으면 EN 세션에서 KO로 좋아요한 spot의 id가 목록에 섞이고, 그 카드를 탭하는 순간
SPEC-0007 R-14의 교차 언어 거부에 걸린다. 목록에는 멀쩡히 보이는데 진입만 실패하는 형태라
사용자에게는 원인이 드러나지 않는다.

### 4.2 조인 대상

`LikedSpot`의 필드는 전부 `spot` 행에 있다 — `title`·`thumbnail_image_url`·`address`·
`category`·`copyright`. `attributionText`는 `copyright`에서 도출되는 기존 규칙을 그대로 쓴다.
`spot_detail`을 조인할 필요가 **없다.** 좋아요 목록은 상세 데이터와 무관하므로, 상세가 부재한
spot도 좋아요 목록에 정상적으로 나타난다(AC-55이 이를 전제한다).

`spot_reaction`은 `spot`에 `ON DELETE CASCADE` FK를 갖는다. 따라서 삭제된 spot(종료 축제 등,
SPEC-0007 R-8)의 좋아요는 자동으로 사라지며, 목록에 유령 항목이 남지 않는다.

### 4.3 정렬과 커서

`likedAt` 내림차순(AC-46). 동률 시 결정적이어야 한다(AC-47 · POL-019) — `spots`가
`compareBy({ distance }, { id })`로 이미 타이브레이크를 쓰는 것과 같은 규율이다.

`spot_reaction`에 좋아요 시각 컬럼이 있는지, `created_at`을 쓸 수 있는지는 구현 시 확인한다.
없다면 컬럼 추가가 필요하며 그것은 마이그레이션 사안이다. **정렬 키가 인덱스로 뒷받침되는지도
함께 확인할 것** — `(member_id, spot_id)` 유니크는 `spot_id` 선행이 아니라 정렬을 커버하지
못할 수 있다.

커서는 정렬 키에서 파생하며 불투명 문자열이다(POL-021). `first` 기본 20 · 상한 100은
`members`의 잠정값을 따랐다(`[TBD-2]`).

### 4.4 인증

미인증은 최상위 `errors[]`의 `UNAUTHENTICATED`로 거부한다(AC-52 · POL-008). 빈 목록으로
대체하지 않는다(AC-53) — 빈 목록은 "좋아요가 없음"이라는 다른 의미다.

`reactToSpot`의 `userErrors`에 인증 실패를 담던 경로는 #32가 정리 중인 별건이다. 쿼리인
`likedSpots`는 처음부터 최상위 `errors[]`만 쓴다.

## 5. 아키텍처 준수

- 도메인 모델 `SpotDetail`·`Spot`에 JPA 애노테이션을 두지 않는다. JPA 엔티티와 도메인 모델은
  분리된 채로 유지한다.
- application 레이어가 infrastructure를 직접 참조하지 않는다. 상세 조회는 기존 `TourInfoPort`
  뒤에서 이뤄지며, 부재 판정도 포트 뒤의 관심사다.
- `likedSpots`는 CQRS의 쿼리 측이다. 새 커맨드가 없다.

## 6. 테스트가 실릴 단위

application·domain 레이어 단위 테스트만. 포트는 목/스텁으로 대체한다.

| 단위 | 검증 |
|---|---|
| 상세 조회 application 서비스 | AC-1 ~ AC-4 (부재와 실패의 구분), AC-5 ~ AC-8 (목록 값 구성) |
| 상세 적재 판정 로직 | AC-9 ~ AC-14 (미조회/부재/존재 3상태, 신선도 전환) |
| 상세 조회 application 서비스 | AC-17 · AC-19 ~ AC-22 (부분 실패 시 본문 보존, 빈 배열 구분) |
| 좋아요 목록 쿼리 서비스 | AC-45 ~ AC-53 (LIKE 필터, 정렬, 소유자 격리, 페이징, 인증) |

**AC-18은 단위 테스트로 검증하지 않는다.** `errors[].path`의 실제 형태는 DGS 전송 계층을
세워야 관찰되며, application 레이어에는 그 표면이 없다(`[TBD-3]`). 어댑터·인프라 테스트는
이 스펙의 범위 밖이므로 **명세하지 않고 미검증으로 남긴다.** 구현 시 실제 응답을 육안으로 한 번
확인하고, `["spotDetail","gallery"]` 가정과 다르면 `[AMEND]`로 보고할 것.

테스트 인프라·픽스처·컨테이너·DB 시딩 전략은 이 문서가 규정하지 않는다.

## 7. 작업 순서

1. **`gallery`·`infoItems` nullability 완화** — #34에서 이월된 부분. 가장 작고 독립적이며,
   클라이언트(#30)가 codegen을 위해 이것을 기다린다. **먼저 배포해 introspection에 반영할 것.**
2. **부재 적재 및 조회 경로** — R-1 ~ R-4. `[TBD-1]`은 여기서 판명된다.
3. **좋아요 목록** — R-15 ~ R-17. 앞의 둘과 독립이므로 병행 가능하다.

1번이 먼저인 이유는 클라이언트의 선행 조건이기 때문이다. 완화 전에는 codegen이 non-null 타입을
만들어 클라이언트의 부분 실패 매핑이 죽은 코드가 된다 — k-trip-spot #28이 이월된 사유가 정확히
이것이다.
