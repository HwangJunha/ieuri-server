# 이으리(ieuri) 로그인 기능 명세 — Step 2: 로그인 / 토큰 발급(서버)

> 기능을 쪼개서 단계적으로 진행합니다. 이 문서는 **로그인 및 JWT 토큰 발급·갱신·폐기 서버 로직**만 다룹니다.
> 회원가입(Step 1)은 별도 명세(`회원_기능_개발.md`)에서 이미 완료되었습니다.

---

## 범위 (Scope)

- **이번 스텝**: SNS 로그인 → 회원 조회 → **JWT accessToken/refreshToken 발급** → 토큰 갱신(refresh, 회전) → 로그아웃(토큰 폐기). refresh 토큰은 **지금은 In-memory 저장소**로 관리.
- **다음 스텝(별도)**: 권한/역할(RBAC), 자체 로그인(ID/PW), MFA, httpOnly 쿠키 전송, 멀티 디바이스 세션 관리 UI, **저장소 Redis/Valkey 전환**.

---

## 정책 결정사항 (Decisions)

- **인증 수단은 SNS 전용**(Step 1과 동일): `apple`, `google`, `kakao`. 로그인도 provider `id_token` 검증을 재사용한다(`SnsIdentityVerifierPort`).
- **로그인 = 기존 회원 인증**. `(provider, provider_user_id)`로 회원을 조회한다.
  - 회원이 없으면 로그인 거부(`MEMBER_NOT_FOUND`) → 클라이언트는 회원가입(Step 1)으로 유도. **로그인 단계에서 자동 가입하지 않는다.**
  - 회원 상태가 `ACTIVE`가 아니면(향후 `SUSPENDED`/`WITHDRAWN`) 로그인 거부.
  - `email_verified` 여부는 로그인을 막지 않는다(이메일 검증은 독립 흐름).
- **토큰 방식: JWT (HS256 대칭키)**. 단일 서버이므로 대칭키로 서명한다. (멀티서비스로 확장 시 RS256/비대칭 전환은 다음 스텝.)
  - **accessToken**: **5분**. Stateless — 서버에 저장하지 않고 서명·만료만으로 검증.
  - **refreshToken**: **30일**. **설정값으로 조정 가능**.
- **JWT 라이브러리: jjwt (`io.jsonwebtoken`)** — JVM 진영에서 가장 널리 쓰이고 오래 검증된 표준 라이브러리로 확정.
- **refresh 토큰 저장소는 지금 In-memory**(`ConcurrentHashMap` + 만료 정리). **인터페이스(`RefreshTokenStorePort`)로 추상화**해, 나중에 **Redis/Valkey 구현으로 갈아끼우기만** 하면 되도록 한다.
  - 저장 키는 refresh 토큰의 `jti`(토큰 식별자). 값은 `member_id` + 만료시각(+추후 디바이스 정보 확장 여지).
  - Redis/Valkey 전환 시 TTL을 refresh 만료와 일치시켜 자동 소멸시킨다.
- **refresh 회전(rotation)**: refresh를 쓸 때마다 **새 refresh를 발급하고 이전 것을 폐기**한다(1회용).
- **재사용 감지(reuse detection)**: 이미 폐기된(회전된) refresh가 다시 들어오면 **탈취 가능성**으로 보고 **해당 회원의 모든 refresh를 폐기**한다.
- **로그아웃**: 제출된 refresh(또는 access의 회원)에 해당하는 refresh를 저장소에서 폐기한다. accessToken은 짧으므로 만료까지 유효(블랙리스트는 이번 스텝 범위 밖).
- **비밀값(JWT 서명 키)**: 암호화 키·Gmail 앱 비밀번호와 동일하게 취급. `prod`는 환경변수 주입(기본값 없이 → 없으면 부팅 실패, fail-fast), `local`은 개발 전용 값. **코드/깃 커밋 금지.**
- **DB 스키마 변경 없음**: 토큰은 In-memory 저장이라 이번 스텝에 **Flyway 마이그레이션이 없다**. (Redis 전환도 DB 스키마와 무관.)

## 포함 기능 (In Scope)

1. SNS 로그인 — `id_token` 검증(재사용) 후 `(provider, provider_user_id)`로 회원 조회
2. accessToken(5분)·refreshToken(14일) 발급
3. refreshToken으로 accessToken 재발급 + **refresh 회전**
4. 로그아웃 — refresh 폐기
5. refresh 재사용 감지 시 해당 회원 전체 폐기
6. refresh 저장소 추상화(In-memory 구현, Redis/Valkey 교체 대비)

---

## 제외 기능 (Out of Scope — 다음 스텝)

1. 권한/역할(RBAC), 스코프
2. 자체 로그인(ID/PW), 소셜 계정 연동/통합
3. MFA, 디바이스 신뢰
4. accessToken 블랙리스트(즉시 무효화) — access는 5분 만료로 대체
5. httpOnly 쿠키 기반 전송(지금은 GraphQL 응답 페이로드로 반환)
6. 멀티 디바이스 세션 목록/개별 로그아웃 UI (저장소 구조는 확장 가능하게만 둠)
7. **refresh 저장소 Redis/Valkey 전환** (지금은 In-memory)

---

## 필수 규칙 (Invariants)

1. accessToken은 **5분**, refreshToken은 **설정된 만료(기본 30일)** 를 정확히 준수한다.
2. refresh는 **1회용**이며 사용 시 **반드시 회전**(신규 발급 + 이전 폐기)된다.
3. 폐기·만료·회전된 refresh로는 재발급되지 않는다. 폐기된 refresh 재사용 시 **회원 전체 refresh 폐기**.
4. `ACTIVE` 상태가 아닌 회원, 존재하지 않는 회원은 로그인·재발급 불가.
5. JWT 서명 키는 비밀값. **로그·응답·커밋 어디에도 토큰/키를 노출하지 않는다.**
6. 토큰 저장/검증 로직은 **포트 뒤에** 둔다. In-memory→Redis/Valkey 교체가 애플리케이션 계층 변경 없이 가능해야 한다.

---

## 토큰 설계 (Token Design)

- **서명**: HS256, 비밀키는 설정/환경변수 주입.
- **accessToken 클레임**: `sub`(=member_id), `jti`, `iat`, `exp`(+5분), `typ=access`, `iss`(=ieuri). (역할/스코프는 다음 스텝)
- **refreshToken 클레임**: `sub`(=member_id), `jti`, `iat`, `exp`(+30일), `typ=refresh`, `iss`.
- **검증**: 서명·`exp`·`iss`·`typ` 확인. refresh는 추가로 **저장소에 `jti`가 살아있는지** 확인(폐기/회전 감지).
- member_id는 토큰의 `sub`로만 전달하며, refresh의 식별·폐기는 `jti`로 한다(원문 토큰을 저장소 키로 쓰지 않음).

## 흐름 (Flows)

### 1) 로그인
1. `login(provider, idToken)` → `SnsIdentityVerifierPort.verify`로 `(provider, provider_user_id)` 확보.
2. 회원 조회 → 없으면 `MEMBER_NOT_FOUND`, `ACTIVE` 아니면 거부.
3. accessToken·refreshToken 발급 → refresh의 `jti`를 저장소에 저장(만료시각 포함).
4. 응답: `{ accessToken, refreshToken, tokenType: "Bearer", accessTokenExpiresIn, refreshTokenExpiresIn }`.

### 2) 토큰 재발급(refresh, 회전)
1. `refresh(refreshToken)` → 서명·`exp`·`typ=refresh` 검증.
2. 저장소에서 `jti` 확인:
   - 없음(이미 회전/폐기) → **재사용 감지**: 회원 전체 refresh 폐기 후 거부.
   - 있음 → 통과.
3. 회전: 이전 `jti` 폐기 → 새 accessToken·refreshToken 발급 → 새 `jti` 저장.
4. 응답: 새 토큰 쌍.

### 3) 로그아웃
1. `logout(refreshToken)` → refresh 검증 후 해당 `jti` 폐기(저장소에서 제거).
2. accessToken은 만료까지 유효(즉시 무효화는 범위 밖).

---

## 저장소 추상화 (Refresh Token Store)

- 포트: `RefreshTokenStorePort`
  - `save(jti, memberId, expiresAt)`
  - `existsActive(jti): Boolean`
  - `revoke(jti)`
  - `revokeAllByMember(memberId)`
- **지금 구현**: `InMemoryRefreshTokenStore` — `ConcurrentHashMap`, 만료 항목 지연/주기 정리. 단일 인스턴스 메모리(서버 재시작 시 소실 — 재시작하면 재로그인 필요, 개발 단계 허용).
- **추후 구현**: `RedisRefreshTokenStore` / `ValkeyRefreshTokenStore` — 키 `refresh:{jti}`, 값 `memberId`, TTL=refresh 만료. `revokeAllByMember`는 회원별 인덱스(`member:{id}:jti` set) 유지. **포트 시그니처는 그대로**, 구현만 교체.

---

## 헥사고날 배치 (Placement)

- **domain**: JWT는 인프라 관심사이므로 도메인에 넣지 않는다. 도메인 규칙은 최소(예: "ACTIVE 회원만 인증 가능"). 토큰 자체는 도메인 모델이 아님.
- **application**: `LoginUseCase` / `RefreshTokenUseCase` / `LogoutUseCase` + 커맨드/결과. 아웃바운드 포트: `TokenProviderPort`(JWT 발급·검증), `RefreshTokenStorePort`, 회원 조회 포트(`MemberRepositoryPort` 확장 또는 신규 조회 포트).
- **infrastructure**: `JwtTokenProvider`(JWT 라이브러리), `InMemoryRefreshTokenStore`, DGS GraphQL 리졸버(`login`/`refreshToken`/`logout` 뮤테이션 + 응답 타입은 codegen), Security 설정에서 로그인/재발급 엔드포인트 permit.
- 의존성 방향(infrastructure → application → domain)은 ArchUnit 테스트로 계속 강제.

## 설정 (Config) — 예시

```yaml
ieuri:
  jwt:
    issuer: ieuri
    secret: ${IEURI_JWT_SECRET}          # prod: 환경변수(기본값 없이 fail-fast) / local: 개발 전용 값
    access-ttl: 5m
    refresh-ttl: 30d
```

- 비밀값 소스만 프로파일별로 분리(`application-{profile}.yml`), 컴포넌트는 동일 인터페이스.
- JWT 라이브러리: **jjwt** (`io.jsonwebtoken:jjwt-api` + 런타임 `jjwt-impl`, `jjwt-jackson`). HS256 서명 키는 base64 인코딩 비밀값으로 주입.

## 보안 체크리스트

- accessToken 짧게(5분)로 탈취 피해 최소화. refresh는 1회용·회전·재사용 감지.
- 서명 키/토큰을 로그·응답·에러 메시지·커밋에 노출 금지.
- refresh 저장소 TTL = 토큰 만료와 일치(좀비 토큰 방지).
- 토큰 검증 실패는 사유를 과도하게 노출하지 않는다(일반화된 인증 실패).

## 결정 완료

**결정됨**: SNS 로그인(기존 회원만) · JWT HS256 · **access 5분** · **refresh 30일**(설정 가능) · refresh 회전+재사용 감지 · In-memory 저장소(→ Redis/Valkey, 포트 추상화) · 로그아웃=refresh 폐기 · DB 스키마 변경 없음 · 서명 키 프로파일 분리(fail-fast) · **JWT 라이브러리 jjwt** · **미가입 회원 로그인 거부(`MEMBER_NOT_FOUND`) → 회원가입 유도**.

**남은 판단 없음.** 이 스텝 명세 확정.
