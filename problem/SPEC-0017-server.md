# SPEC-0017 — 피드와 다이렉트 메시지 (서버 설계)

요구사항·수용 기준·계약은 원본 스펙에 있다. 이 문서는 **서버 구현 결정만** 담으며 요구사항은
번호로만 참조한다.

**Breaking 변경 없음.** 기존 `Post`·`Comment`와 모든 기존 뮤테이션은 손대지 않는다.

## 도메인 배치

피드와 DM 모두 **community 도메인**에 둔다. 별도 도메인을 만들지 않는다 — 차단·신고·이미지 업로드를
커뮤니티와 공유하고, 이들을 갈라놓으면 같은 정책을 두 곳에서 강제하게 된다.

`Post`와 `FeedItem`은 **같은 도메인 안의 서로 다른 애그리게잇**이다. 공통 상위 타입을 만들지 않는다 —
불변식이 정반대다(`FeedItem`은 spot·사진 필수, `Post`는 둘 다 선택). 공통 추상을 두면 그 추상이
어느 쪽 불변식도 표현하지 못한다.

## 설계 결정

### 1. `FeedItem`은 독립 애그리게잇 (R1·R2)

spot 1곳과 사진 1~5장은 **애그리게잇 생성 시점의 불변식**이다. 도메인 모델의 생성자·팩토리에서
강제하며, 애플리케이션 서비스나 리졸버에서 검사하지 않는다. 불변식을 도메인 밖에 두면 새 호출
경로가 생길 때마다 검사가 빠진다.

- `spotId` 부재 → `SPOT_REQUIRED`
- 사진 0개 → `PHOTO_REQUIRED` / 6개 이상 → `TOO_MANY_PHOTOS`
- **6개를 받아 앞 5개만 취하지 않는다**(AC2-4). 조용한 절삭은 사용자가 올린 것을 말없이 버리는 것이다

spot 존재 확인은 포트를 통해 조회하며, 미해석 시 `SPOT_NOT_FOUND`다. 이 검사는 애플리케이션 계층에
둔다 — 도메인은 다른 애그리게잇의 존재를 스스로 확인하지 않는다.

### 2. 이미지 업로드 경로를 새로 만들지 않는다 (R3)

기존 `createPostImageUploadUrls` / `confirmPostImageUploads`를 그대로 쓴다(POL-042). 피드 전용
업로드 뮤테이션을 만들면 사전 서명·확정·만료 로직이 두 벌이 되고, 그 둘은 반드시 어긋난다.

확정 키의 **재사용 방지**가 필요하다(AC3-3). 이미 다른 피드나 글에 실린 키가 다시 제출되면
`PHOTO_NOT_CONFIRMED`로 거부한다. 키 소비 여부를 어디서 추적할지는 기존 확정 저장소의 구조에 맞춘다.

### 3. 피드 조회는 정렬 인자를 받지 않는다 (R4)

`createdAt` 내림차순 고정이다. 정렬 인자를 두면 커서 인코딩이 정렬 키에 종속되어, 나중에 정렬을
추가할 때 기존 커서가 깨진다. 최신순만 필요하다면 인자를 두지 않는 편이 정직하다(POL-019).

커서는 `(createdAt, id)` 복합으로 인코딩한다. `createdAt`만으로는 동일 시각 항목에서 페이지 경계가
어긋난다.

차단 필터링은 **질의 단계에서** 적용한다(AC11-1·11-2). 조회 후 필터링하면 페이지 크기가 들쭉날쭉해지고
`hasNextPage`가 거짓말을 한다.

### 4. 대화 시작의 입력은 회원 id가 아니라 피드 id (R7)

`startConversation(feedItemId:)`다. 이 선택이 R7을 **구조적으로 강제한다** — 커뮤니티 글 작성자를
가리킬 방법이 애초에 없다. 권한 검사만으로 막으면 검사를 빠뜨린 경로가 생길 수 있지만, 입력 타입으로
막으면 그런 경로가 존재할 수 없다.

- 자기 자신의 피드 → `NOT_FEED_AUTHOR`(AC7-4)
- 존재하지 않는 피드 → `FEED_ITEM_NOT_FOUND`. 커뮤니티 글 id를 넣어도 같은 코드다(AC7-3)
- 동일 상대와 기존 대화가 있으면 **새로 만들지 않고 기존 것을 반환**한다(AC7-2). 두 사용자 쌍에 대한
  유니크 제약으로 보장하며, 경합 시 삽입 실패를 조회로 흡수한다

대화 시작과 첫 메시지 전송은 **별개 연산**이다. 빈 대화가 존재할 수 있으므로 `Conversation.lastMessage`가
nullable이다.

### 5. 차단은 두 지점에서 판정한다 (R11)

기존 `blockUser`를 재사용하고 새 뮤테이션을 만들지 않는다. 판정 지점은 두 곳이다.

| 지점 | 동작 |
|---|---|
| 피드 조회 | 차단 관계 작성자의 항목을 질의에서 제외 |
| 대화 시작 · 메시지 전송 | `BLOCKED`로 거부 |

**기존 대화가 차단을 우회하지 못한다**(AC11-4). 대화 성립 이후에 차단이 발생해도 전송 시점에 다시
판정한다. 대화 생성 시점에만 검사하면 차단이 소급되지 않는다.

### 6. 신고 — 피드는 기존 뮤테이션, DM은 신규 (R12·R15)

**피드**는 `reportContent`를 재사용하고 `ReportTargetType`에 `FEED_ITEM`을 더한다. 가산적 변경이다.

**DM은 별도 뮤테이션 `reportMessages`를 둔다.** 기존 `ReportContentInput.targetId`가 단수라 다건
신고를 표현할 수 없다. 억지로 끼우려면 같은 신고를 N번 접수하게 되고, 그러면 운영자에게 한 사건이
N건으로 보인다.

검증 순서는 **존재 → 소유 → 대화 일관성 → 중복**이다.

- 빈 목록 → `INVALID_INPUT`
- 여러 대화의 메시지가 섞임 → `INVALID_INPUT`. 한 신고는 한 대화에 대한 것이다
- 자기 메시지 포함 → `INVALID_INPUT`
- 이미 신고한 메시지 포함 → `ALREADY_REPORTED`

**운영자 열람 범위는 신고에 포함된 메시지로 한정된다.** 전후 맥락을 자동으로 끌어오지 않는다.
이 제약은 조회 쿼리 수준에서 강제하며, 운영 도구가 대화 전체를 열 수 있는 경로를 만들지 않는다.

**누적 신고 자동 숨김의 적용 범위가 대상마다 다르다.**

| 대상 | 5인 누적 자동 숨김 |
|---|---|
| `POST` · `COMMENT` · `FEED_ITEM` | 적용 (POL-041 3항) |
| `MEMBER` | 미적용 — 기록만 (POL-041 4항) |
| `MESSAGE` | **미적용** — 기록만 (POL-049 제안) |

1:1 대화에는 서로 다른 신고자 5명이라는 개념이 성립하지 않는다. 임계값을 1로 낮추면 신고 한 번으로
상대의 발언을 지우는 도구가 된다.

### 7. Subscription — 플랫폼 최초 (R10·R14)

이 스펙이 첫 `Subscription`을 도입한다. 세 가지가 실제 과제다.

**(1) 인증 시점.** 연결 수립(`connection_init`)에서 1회 인증하고, 구독별 참여자 검사는 `subscribe`
시점에 한다. 연결이 살아 있다는 것이 특정 대화를 볼 자격의 증명은 아니다.

accessToken은 5분 만료다(POL-008). 장시간 연결에서 토큰이 만료되어도 **기존 연결을 끊지 않는다** —
끊으면 대화 중 주기적으로 타이핑 표시가 사라진다. 만료는 새 `subscribe` 시점부터 적용한다.

**(2) 멀티 인스턴스 전달 — 이 설계의 핵심 제약.** 서비스는 k3s에서 **여러 파드로 운영된다.**
따라서 in-process 이벤트(POL-028의 Spring ApplicationEvent)로는 성립하지 않는다. 발신자가 파드 A에,
수신자가 파드 B에 연결되어 있으면 이벤트가 도달하지 않는다.

이 실패는 **조용하다.** 단일 인스턴스 개발 환경에서는 완벽히 동작하고, 운영에서 "가끔 되는 기능"이
된다 — 두 사용자가 같은 파드에 붙었을 때만 동작하기 때문이다. 유닛테스트로도 잡히지 않는다.

따라서 타이핑 이벤트는 **공유 브로커를 경유해야 한다.** Valkey는 이미 토큰 저장소로 스택에 있고
pub/sub를 제공하므로 새 인프라를 들이지 않고 해결된다. 각 파드가 자신에게 연결된 구독자에게만
전달하고, 발행은 브로커로 보낸다.

Kafka는 쓰지 않는다. 타이핑 이벤트는 유실 허용이고 순서 보장도 필요 없다 — 영속 로그가 필요한
성질이 아니다.

**(3) 유실 허용은 계약이다.** 타이핑 이벤트는 영속화하지 않고, 재연결 시 재전송하지 않는다. 이를
살리려고 큐·재시도·아웃박스를 도입하지 않는다. 브로커가 끊기면 타이핑 표시만 죽고 메시지 전송·조회는
영향받지 않아야 한다(AC14-2).

`notifyTyping`은 **수신자가 없어도 성공한다**(AC10-2). 받을 사람이 없는 것은 실패가 아니다.

### 8. 권한 실패의 표면화 위치가 조회와 뮤테이션에서 갈린다

같은 "참여자가 아님" 조건이 연산 종류에 따라 다른 경로로 나간다. 근거는 spec.md의 "권한 실패의
표면화 위치"에 있으며, 여기서는 구현 지점만 적는다.

| 연산 | 위치 | 코드 |
|---|---|---|
| `conversationMessages`, `typingIndicator` 구독 | 최상위 `errors[]` | `FORBIDDEN` |
| `sendMessage`, `notifyTyping` | `userErrors[]` | `NOT_CONVERSATION_PARTICIPANT` |

**없는 대화와 권한 없는 대화를 같은 코드로 뭉뚱그리지 않는다**(AC9-5·AC10-5). 존재 확인이 먼저이고
참여자 판정이 그다음이다. 순서를 뒤집으면 존재하지 않는 대화가 권한 오류로 보고된다.

이 순서는 대화 식별자의 존재 여부를 노출한다. 대화 id는 추측 가능한 값이 아니고 열거 공격의 대상이
아니므로 허용한다 — 숨겨야 할 값이라면 순서를 뒤집는 편이 맞다.

### 9. 메시지 본문은 암호화해 저장한다 (R16)

POL-012의 적용이다. 이메일 암호화(SPEC-0012, V39)의 방식을 확장하며 새 패턴을 발명하지 않는다.

**E2E는 하지 않는다.** 신고된 메시지를 운영자가 열람해야 하므로(R15) 서버가 복호화할 수 있어야 한다.
두 요구를 동시에 만족시킬 수 없으며, E2E를 택하면 신고 처리가 불가능해진다.

**한계를 문서에 남긴다.** at-rest 암호화는 저장 매체·백업·덤프 유출을 막는 수단이지 애플리케이션
침해를 막지 못한다. 서버가 뚫리면 키도 함께 있다. 이 사실을 감추고 "암호화했으니 안전하다"고 쓰지
않는다.

**부수 효과: 본문 검색이 불가능해진다.** 암호화 컬럼은 `LIKE`·전문 검색의 대상이 아니다. 대화 검색은
이번 스펙 비범위라 지금은 문제가 없으나, 필요해지면 재설계 대상이다. 검색을 위해 평문 사본을 두는
선택은 암호화를 무의미하게 만들므로 하지 않는다.

### 10. 6개월 삭제 배치 (R16)

기준은 **메시지 생성 시각**이다. 대화의 마지막 활동 시각이 아니다 — 활발한 대화라고 해서 개별
메시지의 보관 기간이 늘어나지 않는다(AC16-3). 기준이 단순해야 "언제 지워지는가"를 사용자에게 설명할
수 있다.

배치는 **삭제 대상을 나눠 처리한다.** 6개월치가 한 번에 쌓인 상태에서 단일 트랜잭션으로 지우면 락과
WAL이 함께 커진다. 회차당 상한을 두고 반복하며, 상한은 설정값으로 뺀다(POL-044 — 근거 없는 계수를
코드에 박지 않는다).

**삭제는 물리 삭제다.** 소프트 삭제로 두면 보관 기간을 정한 의미가 없다 — 지웠다고 하면서 데이터는
남아 있게 된다.

배치 실행 주기·상한은 설정으로 두고 spec에 기본값을 기록한다. 실측 전까지 확정값이 아니다.

### 11. 탈퇴 시 삭제, 정지 시 보존 (R17)

탈퇴는 **되돌릴 수 없으므로** 메시지를 삭제한다. 정지는 **해제될 수 있으므로** 보존한다. 정지 시
삭제하면 해제 후 복구할 방법이 없다.

상대방 화면에서 조회가 깨지지 않아야 한다(AC17-2). 발신자가 사라진 메시지가 목록에 남아 조회 자체를
실패시키면 안 된다 — 상대의 남은 메시지는 정상 표시된다.

이 처리는 POL-009(탈퇴·정지)가 `[TBD]`인 상태에서 **DM에 한해** 정하는 것이다. 다른 데이터의 탈퇴
처리를 여기서 결정하지 않는다.

### 12. DM 본문은 로그에 남기지 않는다 (POL-013)

메시지 본문·수신자 식별자를 로그에 남기지 않는다. 이메일에 대해서는 POL-047의 마스킹 형식이 있으나
메시지 본문은 마스킹 대상이 아니라 **애초에 기록 대상이 아니다.**

## 테스트

CLAUDE.md 테스트 범위표에 따라 **도메인·애플리케이션 계층 유닛테스트만** 대상이다. 포트는 스텁으로
둔다. 어댑터·인프라(실제 WebSocket 전송, DB, Valkey, Spring 컨텍스트)는 대상이 아니다.

|---|---|---|

| 피드 생성 서비스 (spot 존재 확인, 확정 키 검증) | 애플리케이션 | R1·R3 — AC1-3, AC3-1~3-3 |
| 피드 조회 서비스 (정렬·커서·상한 절삭·차단 필터) | 애플리케이션 | R4·R11 — AC4-1~4-4, AC11-1~11-2 |
| 좋아요 멱등성 | 애플리케이션 | R6 — AC6-1~6-3 |
| 대화 시작 자격 판정 (본인 여부, 기존 대화 반환, 차단) | 애플리케이션 | R7·R11 — AC7-1~7-4, AC11-3 |
| 메시지 전송 (본문 검증, 참여자 판정, 차단 재판정, 부재 대화 구분) | 애플리케이션 | R9·R11 — AC9-1~9-5, AC11-4 |

| 신고 대상별 자동 숨김 분기 (DM 메시지 제외) | 도메인 | R12 — AC12-4 |
| 다건 메시지 신고 검증 (빈 목록·대화 혼재·자기 메시지·중복) | 애플리케이션 | R15 — AC15-1~15-6 |
| 삭제 대상 선별 로직 (생성 시각 6개월 경과 판정) | 도메인 | R16 — AC16-1~16-3 |
| 탈퇴·정지 분기 (탈퇴는 삭제, 정지는 보존) | 애플리케이션 | R17 — AC17-1, AC17-3 |

**R14는 유닛테스트 대상이 아니다.** 파드 경계를 넘는 전달은 인프라에서만 관측된다. 멀티 인스턴스
환경에서 실제로 확인하며, 그 사실을 감추고 인프라 테스트 계획을 지어내지 않는다.

실제 WebSocket 핸드셰이크, Valkey pub/sub 왕복, DB 유니크 제약의 경합 동작은 **테스트하지 않는다.**

**AC16-4·AC16-5(암호화 저장·복원)도 유닛테스트 대상이 아니다.** 저장된 값이 평문이 아님을 확인하려면
실제 저장소를 들여다봐야 한다. 암호화 적용 여부는 매핑 계층 코드 리뷰와 실제 저장 확인으로 검증한다.
배치의 실제 삭제 수행(회차 상한·락 동작)도 같은 이유로 인프라 확인 대상이다 — **삭제 대상을 고르는
판정 로직만** 유닛테스트로 떼어낸다.

## 승격 대기 정책

`implemented` 도달 시 `policies.md`로 승격해야 한다.

- **POL-048 실시간 구독 전송 규약** — WebSocket 인증 시점, 멀티 인스턴스 전달, 유실 허용 명시
- **POL-049 1:1 대화의 신고 취급** — 누적 자동 숨김 미적용, 메시지 단위 다건 신고, 운영자는 신고분만 열람
- **POL-050 DM 보관·파기와 암호화** — 6개월 보관 후 물리 삭제, 본문 at-rest 암호화, E2E 미채택, 탈퇴 삭제·정지 보존

POL-028(이벤트 발행 방식)은 in-process 전제라 이 스펙의 요구를 담지 못한다. POL-048이 그 공백을
메우며, POL-028 자체의 개정이 필요한지는 정책 승격 시 판단한다.

## 구현 시 확정한 사항 (2026-08-12)

설계 문서가 비워 두었거나 구현 과정에서 정해진 것들이다.

### 암호화 유틸을 `common/`으로 승격

이메일 암호화(SPEC-0012)의 AES-256-GCM 구현이 `auth` 도메인 안에 있어 community가 크로스 도메인
규칙상 쓸 수 없었다. 알고리즘만 `common/security/AesGcmCipher`로 올리고 두 도메인이 **같은 키
(`ieuri.encryption.key`)를 공유**한다. 키를 나누면 배포 환경마다 주입할 비밀값이 느는데, 두 값의
유출 반경이 같은 애플리케이션·같은 DB라 나눠 얻는 것이 없다.

`AesGcmEmailEncryptor`는 포트에 잇는 얇은 어댑터로 남았다.

### `unreadCount`는 항상 0이다

계약이 `Conversation.unreadCount`를 요구하지만 **읽음 확인이 비범위**라 마지막 읽은 지점을 기록할
곳이 없다. 자리는 두되 없는 근거로 숫자를 지어내지 않는다 — 스키마 설명에 그 사실을 적었다.
읽음 상태를 도입할 때 채워진다.

### 조회 경로에서는 부재도 `FORBIDDEN`이다

설계 문서는 뮤테이션의 `CONVERSATION_NOT_FOUND`/`NOT_CONVERSATION_PARTICIPANT` 구분만 정했다.
조회·구독은 둘 다 `FORBIDDEN`으로 답한다 — 조회에서 존재 여부를 구분해 주면 대화 id 존재 확인
수단이 되고, 뮤테이션과 달리 클라이언트가 두 경우를 나눠 처리할 이유가 없다.

### 사진 키 재사용 판정은 유일 제약이 맡는다

설계 문서가 "기존 확정 저장소의 구조에 맞춘다"고만 두었는데, 확정 키를 추적하는 테이블이 **없었다**
(`images/` 접두어가 확정 표시다). `community_feed_item_photo.object_key`에 전역 유니크를 걸어
그 판정을 맡겼다 — 미리 조회해 확인하면 경합에서 두 피드가 같은 키를 나눠 갖는다.

`Post`의 사진에는 이 제약이 없다. 기존 데이터를 깨지 않기 위해서이며, AC3-3은 피드에 한한 불변식이다.

### 배치 실행 주기는 k8s CronJob이 소유한다

회차 상한(`batch-size`)과 실행당 최대 회차 수(`max-batches-per-run`)만 설정으로 뒀고 실행 주기는
잡에 두지 않았다 — 기존 tourism 잡과 같은 방식이다. **보관 기간(6개월) 자체는 정책이라
`Message.RETENTION`이 소유하며 설정으로 빼지 않았다.**

### WebSocket 인증은 `auth`에 둔다

`connection_init` 인터셉터가 토큰을 해석해야 하는데 그것은 auth의 책임이라
`GraphqlWebSocketAuthInterceptor`를 auth에 두었다. community는 이 클래스를 모르고 SecurityContext로
memberId만 읽는다 — 기존 `JwtAuthenticationFilter`와 같은 구조다.

`spring.graphql.websocket.path`를 명시하지 않으면 **핸들러가 등록되지 않아 구독이 조용히 붙지
않는다.** application.yaml에 경로를 두었다.

### 리뷰에서 잡힌 것 (2026-08-12)

**신고 대상 CHECK 제약(V50).** `ReportTargetType`에 `FEED_ITEM`을 더했는데 `community_report`의
CHECK 제약이 V28에서 `POST`·`COMMENT`·`MEMBER`로 고정돼 있어 **피드 신고가 런타임 INSERT에서
전부 실패**하는 상태였다. 애플리케이션·스키마·엔티티가 모두 통과하고 DB만 거부하며, 신고
저장소를 스텁으로 두는 유닛테스트로는 잡히지 않는다. V50으로 제약을 재정의했다.

**WebSocket SecurityContext 누출.** `intercept`에서 인증 주체를 스레드에 세우고 지우지 않았다.
서블릿 경로는 `FilterChainProxy`가 요청 종료 시 정리해 주지만 **WebSocket 프레임에는 그 래퍼가
없고**, 스레드는 HTTP 요청과 공유된다. 인증 헤더 없는 다음 요청이 앞 회원으로 인증되어 그의
대화를 읽을 수 있었다 — 인증 실패가 아니라 잘못된 성공이라 조용하다. `try/finally`로 반드시
지우고, 인증 정보가 없으면 비우도록 고쳤다.

**읽기 서비스가 쓰기 포트를 쓰고 있었다.** `ConversationQueryService`의 참여자 판정이
`ConversationRepositoryPort`로 애그리게이트를 복원했다. 같은 용도의
`ConversationQueryPort.findConversation`이 이미 있었고 그쪽으로 옮겼다.

**`FeedItemPersistenceAdapter.save`의 갱신 분기 제거.** 호출자가 없는데 사진을 반영하지 않아,
나중에 누가 부르면 **사진이 조용히 사라진다.** 생성 전용으로 못박았다.

**죽은 코드 정리.** `MessagePurgePort.deleteBySender`가 `MemberDataErasePort.deleteMessagesBySender`와
기능이 겹쳐 한쪽만 고쳐지면 두 경로가 갈릴 수 있었다. 그 외 호출자 없는 포트·리포지터리
메서드를 함께 지웠고, 반대로 **누락돼 있던 피드 좋아요 탈퇴 삭제는 추가했다**(글 좋아요와 같은 취급).

**배치 실행 경로를 문서화했다.** 잡 선택 프로퍼티가 tourism 소유(`ieuri.tourapi.sync.job`)라
`IEURI_TOUR_SYNC_JOB=messageRetentionJob`으로 돌려야 한다는 사실이 어디에도 없었다.
`application-batch.yaml`에 적었다. 도메인 중립 이름으로 옮기는 것은 기존 CronJob 설정을 함께
바꿔야 해 별도 작업으로 둔다.

**남은 지적(NOTE).** `Conversation.originFeedItem`이 DataLoader 없이 대화마다 조회해 N+1이다
(`conversations(first:20){ originFeedItem }` → 쿼리 40회). 즉시 막을 문제는 아니라 두었고,
필요해지면 `ViewerContext`를 받는 로더를 추가한다.

### 시안 확인 후 변경 (2026-08-12) — **스펙 변경**

클라이언트 시안을 검토하며 두 가지가 정해졌다. 마이그레이션 적용 전이라 V49를 직접 고쳤다.

**피드 인용을 방이 아니라 메시지에 붙인다.** `community_conversation.origin_feed_item_id`를
제거하고 `community_message.feed_item_id`를 추가했다.

근거는 **방이 하나인데 피드는 여러 개**라는 데 있다. A가 피드를 여러 개 올리고 B가 그중
두 번째 피드를 보고 말을 걸어도, 두 사람의 방은 이미 있으므로 기존 방이 반환된다. 그런데
`origin_feed_item_id`는 처음 값에 고정돼 있어 **대화방 상단에 엉뚱한 피드가 남는다.**
인스타그램 스토리 답장이 그 스토리를 *메시지에* 딸아 붙이는 것과 같은 이유로, 맥락은
메시지의 속성이지 방의 속성이 아니다.

**DM 사진 전송을 추가한다**(스펙의 "DM의 사진·파일 전송 비범위"를 해제). 같은 자리
(`community_message.photo_object_key`)에 들어가며 기존 업로드 경로를 그대로 쓴다(POL-042) —
전용 업로드 뮤테이션을 만들지 않는다.

따라오는 결정들:

- **본문이 빈 문자열일 수 있다.** 사진만·인용만 보낼 수 있어야 한다. NULL이 아니라 빈
  문자열인 이유는 "본문 없음"과 "복호화 실패"를 구분하기 위해서다. 조회 시 빈 값은
  복호화를 건너뛴다(빈 문자열을 복호화하려 들면 base64 디코딩에서 터진다).
- **셋 다 비면 거부한다** — 도메인과 DB CHECK 양쪽에서 막는다.
- **보관 만료 시 R2 오브젝트도 함께 지운다.** 행만 지우면 "6개월 뒤 삭제"가 사진에 대해
  거짓이 된다. 행 삭제 **뒤에** 지운다 — 먼저 지웠다 롤백되면 깨진 첨부가 되고, 반대
  순서의 최악은 고아 오브젝트라 그쪽이 낫다.

**남은 과제**: 신고된 메시지에 사진이 있을 때 운영자의 이미지 열람 범위. POL-049는 텍스트를
전제로 쓰였으므로 정책 승격 시 함께 다뤄야 한다.

### 새 메시지 구독 추가 (2026-08-12) — **스펙 변경**

**타이핑만 실시간이고 메시지는 폴링인 상태였다.** 스펙이 푸시 알림을 비범위로 두면서
"앱이 떠 있는 동안의 실시간 표시"를 타이핑으로만 좁혔는데, 그러면 채팅방을 열어 둔 사람이
상대의 메시지를 보려고 주기적으로 재조회해야 한다. **타이핑 표시를 위해 WebSocket 인프라를
통째로 들여놓고 정작 메시지는 폴링**인 셈이라 앞뒤가 맞지 않았다.

`Subscription.newMessage(conversationId:)`를 추가한다. 인프라(WebSocket·Valkey pub/sub)가
이미 있어 재사용하며, `TypingEventPort`를 `ConversationEventPort`로 일반화했다.

**FCM은 필요 없다.** 앞서 "실시간 메시지는 푸시와 한 세트"라고 판단했으나 과했다 — 앱이
떠 있는 동안만 실시간이어도 채팅은 성립한다. 알림은 앱이 꺼져 있을 때의 별개 문제이며
계속 비범위다.

**두 이벤트의 성질이 다르다.**

| | 타이핑 | 새 메시지 |
|---|---|---|
| 유실 허용 | 허용 | **불가** |
| 브로커 페이로드 | JSON(`senderId`, `emittedAtEpochMilli`) | JSON(`messageId`) |
| 끊긴 동안 | 버린다 | 재연결 후 조회로 메꾼다 |

**구독은 "새 메시지가 있다"는 신호이지 전달 보장 수단이 아니다.** 이벤트에는 id만 싣고
(본문을 브로커에 흘리지 않는다, POL-013) 구독 시점에 DB에서 다시 읽어 내려준다. 그래서
값의 원본은 항상 DB이고, 브로커가 끊긴 순간의 메시지도 재연결 후 `conversationMessages`로
복구된다. 메시지를 이벤트로만 전달하면 그 구간이 영원히 사라진 것처럼 보인다.

채널을 둘로 나눈 이유는 한 채널에 섞으면 타이핑만 필요한 구독자도 메시지 이벤트를 받아
걸러내야 하고 페이로드에 종류 판별자가 붙기 때문이다.

#### 구독 배선을 리액티브 컨테이너로 바꿨다 (2026-08-12)

처음에는 `ConversationSubscription`이라는 자체 콜백 인터페이스를 두고, 구독 요청마다
`RedisMessageListenerContainer`에 리스너를 붙였다. **이벤트가 일부만 도착하는 결함이 났다**
(실측: 5건 발행에 1·3번째만 도착). 원인은 구독마다 리스너를 새로 붙여 같은 채널에 리스너가
여러 개 걸린 것이었고, 발행 하나가 그중 한 곳에만 도착해 GraphQL이 읽는 쪽이 아니면 사라졌다.

`ReactiveRedisMessageListenerContainer.receive()`로 바꿨다. 채널 구독의 생명주기(마지막 구독
취소 시 UNSUBSCRIBE 포함)를 컨테이너가 관리하므로 채널당 싱크 캐시와 해제 경로를 직접 만들
필요가 없다. 자체 래퍼(`ConversationSubscription`)도 걷어내고 포트가 `Flux`를 그대로 노출한다 —
GraphQL Subscription의 계약이 이미 `Publisher`라 한 겹 더 감쌀 이유가 없었고, 그 래퍼가 오히려
"구독마다 스트림을 새로 만든다"는 잘못된 형태를 유도했다.

같이 정리한 것:
- 블로킹 조회를 위한 스레드 전환(`publishOn`)은 **어댑터가 결정한다** — 이벤트가 어느
  스레드에서 올라오는지는 어댑터만 아는 사실이라 application이 알 이유가 없다.
- 구독 경로의 필드 리졸버는 **SecurityContext를 읽을 수 없다**(이벤트마다 도는 실행에는
  ThreadLocal이 없다). 조회자를 `MessageView.viewerId`로 실어 넘긴다.
- 타이핑은 발신자 본인에게도 되돌아오므로 조회자 기준으로 걸러낸다 — 계약상 이 스트림은
  "상대가 입력 중"이다.

### 검증하지 못한 것

`ddl-auto: validate`가 엔티티와 스키마를 대조하는 **실제 부팅 검증을 하지 못했다** — DB 비밀번호가
사용자 셸에만 있다. 마이그레이션 컬럼 타입·FK 규약은 기존 테이블과 대조해 맞췄으나, 최종 확인은
`./gradlew bootRun`이 필요하다.

R14(멀티 인스턴스 전달)와 AC16-4·16-5(암호화 저장·복원)도 스펙이 명시한 대로 유닛테스트 대상이
아니며 실제 환경 확인이 남아 있다.
