# SPEC-0011 서버 설계 — 설정 및 마이페이지

요구사항과 인수 기준은 스펙이 권위를 가진다. 이 문서는 서버가 계약을 어떻게 실현하는지만 다룬다.

## 1. 도메인 배치

이 스펙의 작업은 세 도메인에 걸친다.

| 도메인 | 담당 요구사항 |
|---|---|
| `auth` | R5·R6·R7·R8(프로필), R9~R12(약관), R16·R17(탈퇴 시작점), R20(닉네임 생성) |
| `community` | R3(내 글 조회), R17의 게시물·댓글 삭제 |
| `tourism` | R17의 좋아요 삭제 |

`auth`가 회원 애그리거트를 소유하므로 프로필·약관·탈퇴는 전부 `auth`에 둔다. R3는 `Post` 애그리거트 조회이므로 `community`에 두고, GraphQL 스키마 파일 위치와 무관하게 리졸버도 `community`에 둔다.

## 2. 프로필 수정 (R5·R6·R7·R8)

### 닉네임 (R5)

`Member` 애그리거트에 닉네임 변경 행위를 추가한다. 고유성은 애그리거트 내부에서 판정할 수 없으므로 애플리케이션 레이어가 저장소 포트로 확인한 뒤 도메인에 위임한다. 길이·허용 문자 규칙은 `Nickname` 값 객체가 갖는다.

`member.nickname`에 유니크 제약이 없다. 마이그레이션으로 추가하되, 기존 행에 중복이 있으면 제약 생성이 실패하므로 **중복 해소를 선행하는 마이그레이션이 필요**하다. 정식 출시 전이라 데이터가 적을 것으로 보이나, 실제 중복 여부는 구현 시 확인한다.

경합으로 두 요청이 같은 닉네임을 동시에 통과할 수 있다. 유니크 제약 위반을 잡아 `NICKNAME_ALREADY_TAKEN`으로 변환하는 것이 확인-후-저장보다 정확하다.

### 프로필 이미지 (R6)

게시물 이미지의 3단계 흐름과 같은 구조를 쓰되 **오브젝트 키 네임스페이스를 분리**한다. 프로필 이미지는 `user`(또는 `profile`) 구간을 쓰고 커뮤니티 구간과 섞이지 않는다. 회원 프로필을 커뮤니티와 별개로 보관·삭제할 수 있어야 하기 때문이다.

게시물 이미지는 최대 5장·순서 있는 배열이지만 프로필은 1장이다. 다중 발급·부분 성공 개념이 없으므로 별도 뮤테이션을 두고, 기존 게시물 이미지 뮤테이션을 재사용하지 않는다. 스토리지 어댑터는 공유할 수 있다.

교체 시 이전 오브젝트를 정리한다. 정리 실패가 프로필 반영을 막아서는 안 된다.

### 이메일 변경 (R7·R8)

기존 `email_verification`은 가입 흐름에 묶여 있다 — 회원 생성 시점에 발급되고 `verifyEmail`이 `member.email_verified`를 세운다. 이메일 **변경**은 이미 존재하는 회원의 이메일을 교체하는 다른 흐름이므로, 검증 레코드에 "확정 시 적용할 새 이메일"을 담을 자리가 필요하다.

두 가지 방향이 가능하다.

1. `email_verification`에 대상 이메일 컬럼과 용도 구분(가입/변경)을 추가해 한 테이블로 처리
2. `email_change_request` 별도 테이블

1을 권한다. 코드 발급·만료·시도 상한·쿨다운 로직이 완전히 같고, `VerificationPolicy`를 그대로 쓸 수 있다. 다만 새 이메일은 개인정보이므로 **암호화 저장**한다(POL-012). 검증 통과 전까지 `member.email_encrypted`는 기존 값을 유지한다.

정책 값은 이미 `VerificationProperties`에 있다 — TTL 10분, 최대 5회, 쿨다운 60초. 새 상수를 만들지 말고 재사용한다.

`provider`가 `EMAIL`인 회원은 `provider_user_id`가 로그인 식별자를 겸한다(현재 평문 이메일이 들어간다). 이메일이 바뀌면 **이 값도 함께 갱신되어야** 다음 로그인이 성공한다. R8의 세 번째 인수 기준이 이것을 검증한다. `provider_user_id`의 평문 저장 자체는 SPEC-0012 소관이며, 이 스펙은 값의 정합만 맞춘다. 두 스펙이 같은 컬럼을 건드리므로 구현 순서를 조율한다.

`EMAIL` 회원의 새 이메일은 `(provider, provider_user_id)` 유니크와도 충돌할 수 있다. `EMAIL_ALREADY_IN_USE` 판정은 이 제약과 일관되어야 한다.

## 3. 약관과 게이트 (R9~R12)

테이블은 이미 충분하다. `terms(code, version, required, effective_at)`와 append-only `member_terms_agreement`가 있고 **새 컬럼이나 테이블이 필요 없다**.

### 현재 상태 계산 (R9·R11)

"현재 시행 중인 약관"은 `effective_at <= now`인 것 중 `code`별 최신 버전이다. 회원의 동의 상태는 그 버전에 대한 `member_terms_agreement` 행 중 가장 최근 것으로 판정한다.

핵심은 **버전이 올라가면 이전 동의가 이월되지 않는다**는 점이다. 새 버전이 시행되면 그 버전에 대한 동의 행이 없으므로 `agreed`가 거짓이 되고, 필수 약관이면 게이트가 걸린다. R11의 두 번째 인수 기준이 이 동작을 고정한다.

이 계산은 조회 전용이므로 CQRS의 쿼리 측에 두고 애그리거트를 거치지 않는다.

### 동의 변경 (R10·R12)

append-only를 유지한다. 철회도 `agreed = false` 행을 **추가**하는 것이지 기존 행 수정이나 삭제가 아니다. 동의 이력은 법적 증빙이므로 덮어쓰지 않는다.

`updateAgreement`는 선택 약관만, `agreeToRequiredTerms`는 필수 약관만 받는다. 이 구분은 도메인 규칙이며 리졸버가 아니라 애플리케이션 레이어에서 판정한다. 필수 약관 철회 경로는 만들지 않는다 — 스펙의 결정이다.

### 게이트 (R11)

서버는 상태만 노출하고 차단하지 않는다. 화면 접근 제어는 클라이언트 몫이다(CLAUDE.md 책임 분리표 — 권한에 따른 UI 표시는 서버가 준 필드를 근거로 클라이언트가 판단).

서버는 미동의 회원의 개별 오퍼레이션 호출을 거절하지 않는다 — R11의 단서가 명시한다. 게이트는 화면 진입 차단이며, 서버 측 강제가 필요해지면 별도 결정으로 다룬다. 이 스펙에서 그것을 구현하지 않는다.

## 4. 내가 작성한 글 (R3)

`myPosts`는 인증 주체를 작성자로 고정한 조회다. 기존 `posts()`가 위치·반경 중심이라 재사용하지 않고 별도 쿼리를 둔다.

정렬은 작성 시각 내림차순, 커서는 기존 커넥션과 같은 방식을 쓴다(POL-017). 작성 시각만으로는 동시 생성 시 순서가 불안정하므로 식별자를 보조 키로 함께 쓴다.

숨김·차단 필터는 적용하지 않는다. 자기 글은 자기가 숨겼더라도 마이페이지에 보여야 한다.

## 5. 탈퇴와 데이터 삭제 (R16·R17)

`withdrawMember`는 이미 있고 시그니처를 바꾸지 않는다. 바뀌는 것은 **삭제 범위**다.

현재 `MemberLifecycleService.withdraw`는 회원과 auth 도메인 소유 데이터를 지우고 `MemberWithdrawn`을 발행한다. 이 이벤트를 받는 핸들러가 없어서 커뮤니티 글·댓글과 좋아요가 남는다. R17은 이것을 닫는다.

### 오케스트레이션

`MemberWithdrawn`을 각 도메인이 구독해 자기 데이터를 지운다. 스펙의 결정이며 현재는 `ApplicationEventPublisher`, 이후 Kafka로 옮긴다.

- `community` — 해당 회원의 글·댓글 삭제
- `tourism` — 해당 회원의 좋아요 삭제

각 핸들러는 자기 도메인 저장소만 만진다. 도메인 간 직접 호출을 만들지 않는 것이 이 구조의 이유다.

### 트랜잭션 경계

현재 `withdraw`는 `@Transactional`이고 이벤트는 그 안에서 발행된다. 동기 핸들러라면 같은 트랜잭션에서 실행되어 원자적이지만, 도메인이 늘수록 트랜잭션이 길어진다.

Kafka 전환을 고려하면 **커밋 후 발행**이 맞다. 그러면 회원은 지워졌는데 글이 남는 창이 생기는데, 스펙이 이 창을 허용한다 — R17의 마지막 두 인수 기준이 그것을 고정한다. 한 도메인의 삭제 실패가 다른 도메인의 삭제를 막지 않고, 실패해도 회원 삭제 자체는 되돌아가지 않는다. 즉 최종 일관성이며 보상은 재시도와 실패 기록으로 처리한다.

이 창 동안 작성자가 없는 글이 조회될 수 있다. 커뮤니티 조회가 작성자 정보를 필수로 요구한다면 이 상태에서 오류가 나므로, 작성자 부재를 견디는지 확인하고 필요하면 방어한다. 이는 기존 조회 경로의 성질이며 이 스펙이 새로 만드는 문제는 아니다.

### 애플 revoke

`withdraw`가 호출하는 `snsTokenRevoker.revoke()`는 현재 로그만 찍는 스텁이다. **이 스펙의 범위가 아니다** — SPEC-0012에서 다룬다.

## 6. 닉네임 자동 생성 (R20)

가입 시 형용사·명사·숫자를 조합해 만든다. 100만 이상의 조합이 요구사항이며, 형용사 200 × 명사 100 × 4자리 숫자면 8천만이다. 단어 목록을 작게 유지하면서 충돌을 숫자로 흡수하는 편이 목록을 키우는 것보다 관리하기 쉽다.

생성값이 이미 쓰이고 있으면 다시 뽑는다. 재시도 상한을 두고, 상한을 넘으면 가입이 실패하는 대신 충돌 가능성이 없는 형태로 물러난다.

현재 SNS 가입은 provider가 준 값을 닉네임으로 쓴다(POL-006). R20은 이를 자체 생성으로 바꾸므로 **POL-006 개정 대상**이며, 스펙의 신규 정책 후보에 올라 있다.

## 7. 단위 테스트 대상

애플리케이션·도메인 레이어만. 어댑터·인프라는 범위 밖이다(CLAUDE.md 테스트 범위표).

| 단위 | 검증 |
|---|---|
| 닉네임 변경 유스케이스 | 성공, 중복 거절, 형식 거절, 동일값 (R5) |
| `Nickname` 값 객체 | 길이·문자 규칙, 공백 제거 (R5) |
| 닉네임 생성기 | 형식, 충돌 시 재시도, 조합 수 (R20) |
| 프로필 이미지 발급·확정 유스케이스 | 형식·크기 거절, 키 네임스페이스, 미업로드 키 (R6) |
| 프로필 이미지 제거 유스케이스 | 멱등성 (R6) |
| 이메일 변경 요청 유스케이스 | 핸들 발급, 기존 이메일 유지, 중복·동일 주소 거절 (R7) |
| 이메일 변경 확정 유스케이스 | 성공 후 교체, 코드 불일치·만료·시도 초과 (R7) |
| 이메일 변경 확정 — `EMAIL` 회원 | `provider_user_id` 동시 갱신 (R8) |
| 재발송 유스케이스 | 쿨다운 (R7) |
| 약관 상태 쿼리 | 필수·선택 혼재, 미동의 시 `agreedAt` null, 버전 상승 시 미동의 (R9·R11) |
| 약관 토글 유스케이스 | 선택 약관 성공, 필수 약관 거절, 미시행 코드 거절 (R10) |
| 필수 약관 동의 유스케이스 | 전체·부분 동의, 선택 약관 거절 (R12) |
| 내 글 조회 쿼리 | 정렬, 페이지네이션, 빈 결과 (R3) |
| 탈퇴 유스케이스 | 이벤트 발행 (R17) |
| 커뮤니티 탈퇴 핸들러 | 글·댓글 삭제 (R17) |
| 관광 탈퇴 핸들러 | 좋아요 삭제 (R17) |
| 가입 유스케이스 | 필수 약관 미동의 시 실패 (R19) |

저장소·이벤트 발행기·검증 코드 발송기는 전부 포트로 스텁한다.

이벤트 **순서**나 커밋 후 발행 타이밍은 애플리케이션 레이어에서 관찰할 수 없다. 인프라 동작이므로 테스트하지 않고, 필요하면 실행 환경에서 확인한다.

## 8. 마이그레이션

| 대상 | 내용 |
|---|---|
| `member.nickname` | 유니크 제약 추가. 기존 중복 해소 선행 (R5) |
| `email_verification` | 대상 이메일(암호화)·용도 구분 컬럼 추가 (R7) |
| `member.profile_image_key` | 현재 컬럼 유무 확인 후 필요 시 추가 (R6) |

`terms`·`member_terms_agreement`는 변경 없다.

## 9. 확인 사항

- `member.nickname`에 기존 중복이 있는지, 유니크 제약 추가 전 해소가 필요한지
- 프로필 이미지 오브젝트 키의 도메인 구간을 `user`와 `profile` 중 무엇으로 할지. 스토리지 어댑터가 커뮤니티 전용으로 굳어 있지 않은지
- 커뮤니티 조회가 작성자 부재를 견디는지. 견디지 못하면 삭제 진행 중 조회에 방어가 필요하다
- `EMAIL` 회원의 이메일 변경 시 `provider_user_id` 갱신이 SPEC-0012의 암호화 작업과 어떻게 맞물리는지
