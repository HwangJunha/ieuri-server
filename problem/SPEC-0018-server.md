# SPEC-0018 서버 설계 — 비관광 spot 필터링

요구사항과 수용 기준은 spec이 소유한다. 이 문서는 **ieuri-server가 그것을 어떻게 실현하는가**만
다루며 요구사항을 다시 적지 않는다.

> **2026-08-14 전면 개정 — 적재 시점 제외로 방향을 바꿨다.**
>
> 원안은 `spot.active` 불리언 컬럼을 두고 배치가 매 실행 전량을 재판정하는 방식이었다. 구현을
> 마치고 리뷰까지 통과한 뒤, 사용자 판단으로 **"애초에 적재하지 않는다"** 로 바꿨다.
>
> **바꾼 이유.** 원안이 `active`를 필요로 한 근거는 "이미 적재된 행을 지울 수 없다"였는데, 그
> 전제가 성립하지 않았다. 지워도 되는 이유가 셋이다.
>
> 1. **운영 DB에 해당 데이터가 없다.** 지워서 잃을 것이 없다.
> 2. **오탐 교정은 다음 배치가 한다.** 잘못 지운 관광지는 업스트림(TourAPI)에 그대로 있으므로,
>    키워드를 고치면 다음 실행이 자연히 다시 적재한다. 별도 복구 경로가 필요 없다.
> 3. **피드 기능을 폐기할 예정이다.** 글이 spot을 참조하는 쓰기 경로가 사라지면, 원안이 만든
>    조회 포트 분기(활성만 보는 것 / 무시하는 것)의 존재 이유도 함께 사라진다.
>
> **그래서 사라진 것**: `spot.active` 컬럼과 마이그레이션 2개(메인·검색노드), 판정 전용
> Step·유스케이스·포트·어댑터, 조회 경로 11곳의 활성 조건, 커뮤니티/tourism의 조회 함수 3쌍.
> 원안 대비 변경 파일이 42개에서 16개로 줄었다.
>
> **남은 것**: 도메인 판정 규칙(`SpotExclusionRule`), 설정의 키워드 목록, 그리고 적재 경로에서
> 걸러내는 분기 하나. 아래 본문은 이 방식을 기준으로 다시 썼다.

## 1. 도메인 귀속

tourism 바운디드 컨텍스트. 제외 판정은 **도메인 규칙**이며 인프라 관심사가 아니다.

판정 로직은 제목 문자열과 카테고리를 입력으로 받아 제외 여부를 돌려주는 순수 함수다
(`domain/specification/SpotExclusionRule`). 프레임워크 의존이 없으므로 도메인 계층에 두고
단위 테스트로 전량 검사한다(spec §7의 R4~R7 기준이 이 단위를 대상으로 한다).

키워드 목록은 설정에서 오지만, 도메인은 **주입받은 목록**을 볼 뿐 설정 메커니즘을 알지 않는다.
`TourismConfig.spotExclusionRule`이 `SpotExclusionProperties`를 읽어 빈으로 만든다.

## 2. 적재 시점 제외

### 2.1 판정 위치

`TourApiSyncClient.mapPage`에서 걸러낸다. 이미 같은 성격의 선례가 있다 —
`excludeLclssystm2`(분류코드 기반 제외)가 바로 옆에 있고, 키워드 판정은 그것이 덮지 못하는
행까지 덮는다.

**카테고리 해석 이후에 판정해야 한다.** 규칙이 `TOURIST_SPOT`·`CULTURAL_FACILITY`를 보호하므로
(R5) 카테고리가 정해져 있어야 판정할 수 있다.

### 2.2 컬럼도 마이그레이션도 없다

적재하지 않으므로 상태를 표현할 컬럼이 필요 없다. 메인 DB와 검색 노드 모두 스키마 변경이 없고,
따라서 **논리 복제 양립성 확인도 필요 없다** — 원안에서 가장 큰 배포 위험이었던 항목이
방식 변경으로 통째로 사라졌다.

조회 경로도 손대지 않는다. 행이 없으면 어떤 질의에도 잡히지 않으므로 R2가 자동으로 성립한다.

### 2.3 이미 적재된 행은 정리 단계가 지운다

이것이 방식의 핵심이자, 원안과 가장 크게 갈리는 지점이다.

`SpotSyncTasklet`은 수집한 contentId를 `collectedIds`에 모으고, 정리 단계가 **그 집합에 없는
행을 삭제**한다. 비관광 항목은 `page.records`에 없으므로 `collectedIds`에도 들어가지 않고,
그래서 이전 실행에서 적재됐던 행이 이번 실행의 정리 단계에서 지워진다.

별도의 백필이나 삭제 로직을 쓰지 않는다 — 기존 정리 메커니즘이 그대로 수행한다.

**종료 축제 제외와는 반대로 동작한다.** 종료 축제는 `page.records`에 남긴 채 적재 대상에서만
빼는데(그래야 `collectedIds`에 들어가 지워지지 않는다), 비관광 항목은 `records` 자체에서
빠져야 지워진다. 두 제외가 정반대 이유로 정반대 위치에 있으므로, 코드를 옮길 때 주의한다.

### 2.4 멱등성과 재판정

spec R19가 요구하는 "모든 실행의 동일성"이 구조적으로 성립한다. 실행 회차 개념이 없고, 매
실행이 업스트림 전량을 같은 규칙으로 판정한다.

**오탐 교정도 같은 경로다.** 키워드에서 항목을 빼면 다음 실행이 그것을 적재하고, 정리 단계가
지우지 않는다. 배포 없이 설정만 고치면 되는 것(spec §8.5)은 원안과 같으나, 복구까지 배치
1회가 걸린다는 점이 다르다.

**주의**: 삭제 후 재적재되면 `spot.id`(surrogate)가 새로 발급된다. `content_id + language`는
같지만 id는 달라지므로, id로 spot을 참조하는 좋아요·글의 연결이 끊긴다. 현재 운영 데이터가
없어 무해하고, 피드 폐기 후에는 참조가 좋아요뿐이라 영향이 더 줄어든다.

### 2.5 언어 간 일관성

spec R8은 같은 장소의 전 언어 행이 같은 상태를 갖도록 요구한다.

**원안의 `thumbnail_image_url` 그룹 전파를 구현하지 않았다.** 적재 시점 판정은 행 단위이고,
어댑터가 한 언어의 한 페이지만 보므로 언어 간 전파를 할 자리가 없다.

실측상 ja·zh 제목이 한글명을 병기해 한/영 키워드만으로 전 언어가 걸린다(spec §8.7). 이 관행이
바뀌면 언어에 따라 보였다 안 보였다 할 수 있으며, 그때는 키워드 목록에 해당 언어 표기를 추가해
교정한다 — 설정 변경만으로 가능하다.

### 2.6 관측

제외 건수를 `SpotSyncPage.excludedCount`로 돌려주고, 태스클릿이 `ExecutionContext`(`excluded`)와
로그에 누적한다.

**`droppedCount`와 따로 센다.** 앞은 필수 필드가 비어 적재할 수 없는 항목, 뒤는 비관광이라
의도적으로 뺀 항목이다. 섞으면 키워드 설정 오류가 데이터 결손에 묻힌다.

건수가 갑자기 크게 늘면 **키워드 설정이 잘못됐다는 신호**다. `categoryFallbackCount`가 설정
오류의 신호로 쓰이는 것과 같은 성격이다.

## 3. 정리 게이트

`cleanup`은 두 겹의 게이트(재개 실행 · 0건)를 갖는다.

> **2026-08-14 변경 — 급감(비율) 게이트를 제거했다.** 사용자 판단이다("과하다").
>
> 제거한 것은 "이번 수집 건수가 기존 적재의 50% 미만이면 정리를 건너뛴다"는 세 번째 게이트뿐이다.
> **재개 실행·0건 두 게이트는 남는다** — 각각 다른 사고를 막으며, 특히 0건 게이트가 "업스트림이
> 빈 목록을 주면 전량 삭제"를 막는 실질적 안전장치다.
>
> 함께 사라진 것: `SpotSyncProperties.cleanupMinRatio`, `application-batch.yaml`의
> `cleanup-min-ratio`(환경변수 `IEURI_TOUR_SYNC_CLEANUP_MIN_RATIO`), 그리고
> `SpotStorePort.countByLanguage`와 그 어댑터 구현 — 이 조회는 게이트의 분모 용도뿐이라
> 호출자가 사라지면서 죽은 코드가 됐다.

비관광 제외는 이 게이트에 영향을 준다 — 제외분만큼 수집 건수가 줄기 때문이다. 급감 게이트가
없어져 실질적 영향은 없으나, 0건 게이트는 여전히 유효하다(전량이 제외되는 일은 없다).

## 4. 커뮤니티 영향

**없다.** 원안에서는 비활성 spot을 참조하는 글의 수정이 막히는 문제(R16)가 있어 조회 포트를
둘로 나눠야 했다. 적재하지 않는 방식에서는 그 spot이 애초에 존재하지 않으므로 분기가 필요 없고,
`SpotLookupPort`는 `dev` 상태 그대로다.

다만 **이미 적재됐던 spot이 나중에 제외되어 삭제되면** 그 spot을 참조하던 글은 없는 id를
가리키게 된다(`community_post.spot_id`는 도메인 간 물리 FK가 없다). 현재 운영 데이터가 없어
발생하지 않으며, 피드 폐기 예정이라 항구적 문제도 아니다.

## 5. 테스트

단위 테스트만 작성한다.

| 대상 | 계층 | 검사 내용 |
|---|---|---|
| 제외 판정 규칙 | 도메인 | R4~R7 전량. 키워드 일치·카테고리 보호·지점명 보호·제목 전체 검사 |
| 빈 키워드 목록 | 도메인 | R12. 빈 목록이 전량 제외로 해석되지 않음 |
| 적재 경로의 제외 | 어댑터(변환) | 걸린 항목이 `records`에서 빠지는지, 건수가 `dropped`와 분리되는지 |

**인프라 테스트는 작성하지 않는다.** 아래는 단위 테스트로 증명할 수 없다.

- 정리 단계가 실제로 기존 행을 지우는가 — DB 실행이 필요하다. **배포 시 확인 항목**이다.

## 6. 후속

`lclsSystm2` 기반 판정(spec §8.4)은 이 spec의 범위 밖이지만 구조는 열려 있다. 이미
`excludeLclssystm2` 설정이 같은 자리에서 동작하므로, 코드값이 확인되면 목록에 넣기만 하면 된다.

항목이고, 단어 경계를 느슨하게 하면 `Pharmaceutical` 같은 정상 상호를 걸 위험이 있다. 한글
`약국`이 오타 사례를 이미 커버한다(spec §4.5).

### A.2 판정 방식

- 영문 키워드는 **단어 경계**(`\b`)로 감싼다. **이 목록에서 가장 위험한 항목이 `CU`다** —
  경계 없이 쓰면 실측 표본에서 52건이 아니라 **262건**이 걸린다. 늘어난 210건은 전부 오탐이며
  인사동 문화의 거리, 문화역 서울 284, 동대문역사문화공원, 판문점(Joint Se**cu**rity Area)이
  포함된다
- 경계만 있으면 대소문자 구분은 불필요하다 — `CU`는 두 경우 모두 52건으로 같다
- 한글 키워드는 경계를 두지 않는다. 교착어라 `명동명약국`처럼 접사 없이 붙는다
- 대소문자를 구분하지 않는다 (`emart24` · `E-Mart 24` 표기 혼재)
- 판정 대상은 제목 문자열 전체다(R7)

### A.4 관광 카테고리 보호 (R5)

`TOURIST_SPOT` · `CULTURAL_FACILITY`는 키워드에 걸려도 제외하지 않는다. 실측으로 이 규칙이
지켜낸 항목:

| 항목 | 카테고리 |
|---|---|
| 서울 대한의원 | `TOURIST_SPOT` — 대한제국기 의료기관 건물, 사적 |
| 서울대학교병원의학박물관 | `CULTURAL_FACILITY` |
| 최혁한의원 | `TOURIST_SPOT` |
| 의료법인 서전의료재단 한사랑병원 | `TOURIST_SPOT` |

216건 전량이 `SHOPPING`이므로 이 규칙으로 놓치는 대상은 없다.

### A.5 검증 방법

목록을 고친 뒤에는 아래를 확인한다. 오탐은 사후에 드러나는 성격이라(spec §4.4) 목록 변경이
가장 위험한 순간이다.

1. 제외 건수가 급변하지 않는가 — 급증은 키워드가 넓어졌다는 신호다
2. `TOURIST_SPOT` · `CULTURAL_FACILITY`에서 걸린 항목이 늘지 않았는가
3. 새로 걸린 항목의 제목을 눈으로 확인 — 유네스코 세계유산·사적이 섞이는지(spec §4.4)

`ExecutionContext`의 `excluded` 건수가 1번의 관측 지점이다.
