# SPEC-0028 FCM 푸시 — 클라이언트 대응 요청

서버 PR: ieuri-server#95 (`feature/SPEC-0028-fcm-push`) · 스펙: SPEC-0028 · 이슈: k-trip-spot#66

앱이 꺼져 있는 동안 도착한 DM과 질문 답변을 알리는 푸시가 생겼습니다. 계약은 전부 신규
추가라 **깨지는 것은 없습니다.**

이 문서는 `.graphqls`를 읽어서는 알 수 없는 것만 담습니다. 필드 목록과 타입은 스키마를
보시고, 여기서는 **스키마가 말해 주지 않는 동작**을 다룹니다.

---

## 0. 먼저 알아야 할 두 가지

**알림에 메시지 내용이 없습니다.** 제목과 고정 안내 문구가 전부입니다.

```
제목: 내 질문에 답변이 달렸어요
본문: 앱에서 답변을 확인해 보세요
```

본문 자리에 오는 것은 **서버가 정한 고정 문구**이지 사용자가 쓴 내용이 아닙니다. 보낸 사람
이름도 없습니다. 잠금화면에 대화가 읽히지 않게 하려는 의도이며, 스펙 R13을 구현 중에 뒤집은
결과입니다(spec.md v1.1). 그래서 **알림만 보고는 누가 무엇을 보냈는지 알 수 없고**, 그
정보가 필요하면 탭 후 목적지 화면에서 조회해야 합니다.

> 본문을 아예 비우려 했으나 **iOS가 본문 없는 알림을 표시하지 않아** 고정 문구를 넣었습니다.
> FCM은 정상 접수하고 기기에서 조용히 버려지는 형태라 발견이 늦었습니다.

**푸시가 안 와도 서버는 아무 신호도 주지 않습니다.** 발송 실패·차단·설정 꺼짐·토큰 만료가
전부 조용히 처리됩니다. 발송 상태를 묻는 쿼리도, 알림 목록도 없습니다.

---

## 1. FCM 데이터 페이로드

`notification`에는 **title만** 있고, 목적지 정보는 전부 `data`에 있습니다. 값은 전부
문자열입니다(FCM 데이터 메시지 제약).

| `type` | 함께 오는 키 | 목적지 |
|---|---|---|
| `DM` | `conversationId` | `/conversations/:id` |
| `SPOT_QA_ANSWER` | `spotId` · `questionId` | `/spot/:spotId/qa/:questionId` |
| `SPOT_QA_REPLY` | `spotId` · `questionId` | 같은 질문 상세 |

**키 구성이 타입마다 다릅니다.** DM에는 `spotId`가 없고, Q&A에는 `conversationId`가
없습니다. `type`으로 먼저 분기한 다음 나머지를 읽으세요.

```dart
switch (data['type']) {
  case 'DM':
    context.go('/conversations/${data['conversationId']}');
  case 'SPOT_QA_ANSWER':
  case 'SPOT_QA_REPLY':
    context.go('/spot/${data['spotId']}/qa/${data['questionId']}');
  default:
    // 알 수 없는 type — 기본 착지점으로. 앱이 죽으면 안 됩니다(AC16.4).
}
```

**주의할 점 셋:**

- **`SPOT_QA_REPLY`에 답글 id가 없습니다.** `spotId`+`questionId`만 옵니다 — 답글 단독
  화면이 없어 목적지가 답변과 같기 때문입니다. 답글 위치로 스크롤하려면 질문 상세에서
  따로 찾아야 합니다.
- **`spotId`는 catalogId입니다.** 질문·답변이 걸린 카탈로그 id이며, 기존 질문 상세
  라우트가 쓰는 값과 같습니다.
- **`SPOT_QA_ANSWER`와 `SPOT_QA_REPLY`는 `type` 말고 완전히 동일합니다.** 두 알림을
  구분할 근거는 `type`뿐입니다.

**iOS는 `content-available`이 붙어 나갑니다.** 포그라운드에서도 알림이 앱에 전달되도록
`aps.content-available = 1`과 `apns-priority: 5`를 함께 보냅니다. 그래서 iOS는
포그라운드·백그라운드 모두에서 콜백을 받으며, **배너를 띄울지 말지는 클라이언트가
정합니다**(R15는 포그라운드에서 안 띄우는 것).

**설정하지 않은 것들:** `collapseKey`, `sound`, `badge`, `clickAction`, `AndroidConfig`
— FCM 기본값입니다. 알림 채널 지정도 서버가 하지 않으므로 Android 채널은 클라이언트가
만들어 붙이세요.

## 2. `registerDeviceToken` — 업서트이고, 기기 소유를 옮깁니다

유니크 키가 **`deviceId` 단독**입니다. `(memberId, deviceId)`가 아닙니다.

같은 `deviceId`로 다시 부르면:

| 바뀐 것 | 결과 |
|---|---|
| `fcmToken` | 덮어씀. 행이 늘지 않음 (토큰 로테이션 경로) |
| `language` | 덮어씀 |
| `platform` | 덮어씀 |
| **로그인한 회원** | **소유가 새 회원에게 넘어감** |

마지막 줄이 중요합니다. **한 기기를 다른 사람이 쓰기 시작하면 이전 회원은 그 기기로
알림을 못 받습니다.** 이전 회원에게는 아무 통지도 가지 않습니다. 공용 기기·계정 전환에서
이전 사용자에게 남의 알림이 가는 것을 막으려는 설계입니다.

**호출 시점을 이렇게 잡으세요:**

- 앱 기동 시 (인증 완료 후)
- 포그라운드 복귀 시 — 서버가 토큰을 조용히 지웠을 수 있습니다(§5 참조)
- `onTokenRefresh` 콜백
- 기기 언어가 직전 전송값과 다를 때

한 번만 등록하고 마는 구조로 만들면 **어느 시점부터 알림이 영영 안 오는데 원인을 알 수
없는 상태**가 됩니다.

응답은 `success`와 `userErrors`뿐이라 **무엇이 저장됐는지 되읽을 수 없습니다.**

## 3. `deleteDeviceToken` — `success: true`가 삭제를 뜻하지 않습니다

세 경우가 전부 `success: true`이고 구분되지 않습니다.

- 실제로 지웠다
- 그런 `deviceId`가 없었다
- **그 기기가 다른 회원 것이었다** (남의 토큰은 지워지지 않음)

빈 문자열 `deviceId`를 보내도 `success: true`입니다. 멱등 설계라 실패 모드가 없고,
`userErrors`는 항상 비어 있습니다.

**로그아웃 시 호출은 선택이 아닙니다.** 유니크가 `deviceId` 단독이라, 로그아웃하면서
해제하지 않으면 그 행이 이전 회원을 가리킨 채로 남습니다.

---

## 4. `language` — OS 로케일을 그대로 보내면 오류입니다

`Locale`은 `EN` · `KO` · `JA` · `ZH` **네 값뿐**입니다.

`zh_TW`, `en_US`, `ko-KR` 같은 BCP-47 태그를 보내면 **GraphQL 검증 오류**로 거부됩니다 —
`userErrors`가 아니라 최상위 `errors[]`이고, 뮤테이션 자체가 실행되지 않습니다. 서버는
이 값을 정규화하지 않으니 **클라이언트가 매핑해서 보내세요.** 대응하는 값이 없으면 `EN`.

```dart
AlarmLocale mapDeviceLocale(Locale l) => switch (l.languageCode) {
  'ko' => AlarmLocale.KO,
  'ja' => AlarmLocale.JA,
  'zh' => AlarmLocale.ZH,
  _    => AlarmLocale.EN,
};
```

**`ZH`는 번체(正體)입니다.** 서비스 대상이 대만·홍콩이라 간체를 쓰지 않습니다. 중국어
계열은 간체·번체 구분 없이 `ZH`로 보내면 되고, 문구는 번체로 나갑니다.

**언어는 회원이 아니라 기기 속성입니다.** 같은 사람의 폰과 태블릿이 서로 다른 언어로
알림을 받는 것이 정상 동작이며, 서버가 언어별로 나눠 발송합니다.

## 5. 알림이 조용히 사라지는 경우 (전부 무신호)

이 중 어느 것도 클라이언트에 신호를 주지 않습니다.

| # | 조건 |
|---|---|
| 1 | **자기 행위** — 내가 보낸 메시지·내가 쓴 답변으로는 나에게 오지 않음 |
| 2 | 수신자가 그 카테고리를 껐음 |
| 3 | **차단 관계** — 어느 방향이든(내가 차단했든 상대가 차단했든) |
| 4 | 수신자에게 등록된 기기 토큰이 없음 |
| 5 | 서버에 FCM 자격증명이 없음 — **환경 설정 문제이며 이때는 아무에게도 안 옴** |
| 6 | FCM 호출 실패 (네트워크·타임아웃) — **재시도하지 않음** |
| 7 | 원래 트랜잭션 롤백 |
| 8 | **서버가 이 기기 토큰을 지웠음** (아래) |

**8번을 특히 유의하세요.** FCM이 `UNREGISTERED`(앱 삭제·재설치)로 응답하면 서버가 그
토큰 행을 지웁니다. 클라이언트는 이 사실을 알 수 없고, 재등록하지 않으면 **영구히 알림을
못 받습니다.** §2의 재등록 시점 목록이 이걸 막기 위한 것입니다.

**푸시는 유실 허용입니다.** 재전송·재시도가 없으므로 "알림이 왔다"를 상태 동기화 수단으로
쓰면 안 됩니다. 진실은 항상 서버 조회에 있습니다.

**차단은 Q&A에서 알림만 막습니다** — 답변·답글 자체는 정상 저장되어 앱에서 보입니다.
DM은 전송 자체가 막힙니다.

## 6. 수신 설정

`Me.notificationPreferences`는 **항상 두 항목**을 돌려줍니다. 설정을 한 번도 바꾼 적 없는
회원도 `enabled: true`로 두 개가 옵니다 — 초기화 호출이 필요 없습니다.

**순서가 보장됩니다: `MESSAGE`, `SPOT_QA`.** DB 상태와 무관하게 이 순서입니다.

`updateNotificationPreference`는 바뀐 하나가 아니라 **두 카테고리 전부**를 돌려줍니다.
응답으로 캐시를 통째로 갈아 끼우면 재조회가 필요 없습니다. 같은 값으로 다시 불러도
성공합니다(멱등).

설정은 **회원 단위**라 재설치·기기 변경에도 유지됩니다. 기기 토큰(기기 단위)과 생명주기가
다릅니다.

**`enabled: true`가 알림 도착을 보장하지 않습니다.** OS 권한·채널 설정, 그리고 §5의
조건들이 모두 직렬로 걸립니다.

## 7. 오류

**`userErrors`에는 `INVALID_INPUT` 하나뿐입니다.** 그것도 `registerDeviceToken`에서
`deviceId`나 `fcmToken`이 비었을 때만 나옵니다. 나머지 두 뮤테이션은 `userErrors`가
채워지는 경로가 아예 없습니다.

**`UserError.message`는 한국어 원문이고 번역되지 않습니다.** `field`는 항상 `null`입니다.
그대로 화면에 띄우지 마세요 — 애초에 이 뮤테이션들의 실패는 사용자에게 보여 줄 것이
아니라 로그로 남길 것입니다(스펙 R12·AC12.3).

**최상위 `errors[]`로 오는 것:**

| 코드 | 언제 |
|---|---|
| `UNAUTHENTICATED` | 미인증 호출. 세 뮤테이션 모두 인증 필수 |
| `EMAIL_NOT_VERIFIED` | 이메일 미인증 회원 (아래) |
| (검증 오류) | `Locale`·`DevicePlatform`·`NotificationCategory`에 없는 값 |

### 이메일 인증 게이트에 걸립니다 ⚠️

**세 뮤테이션 모두 이메일 미인증 상태에서는 거부됩니다**(SPEC-0024의 게이트). 허용 목록에
없기 때문입니다.

그래서 **토큰 등록은 이메일 인증을 마친 뒤에 하세요.** `AuthGateState.ready` 이후가
맞습니다.

그리고 게이트는 **요청 안의 루트 필드를 전부** 검사합니다. `registerDeviceToken`을 `me`와
한 문서에 묶어 보내면, 미인증 회원에게는 **요청 전체가 실패합니다.** 배치하지 마세요.

## 8. 트리거는 3종뿐입니다

`NotificationCategory`가 `MESSAGE`·`SPOT_QA` 둘이라 넓어 보이지만, 실제로 알림이 나가는
경우는 셋입니다.

| 트리거 | 받는 사람 |
|---|---|
| DM 새 메시지 | 대화 상대 **한 명** |
| 내 질문에 답변 | **질문 작성자** |
| 내 답변에 답글 | **답변 작성자만** |

**답글 알림은 질문 작성자에게 가지 않습니다.** 답변 작성자에게만 갑니다. 같은 스레드의
다른 참여자에게도 가지 않습니다.

**알림이 없는 것들:** 댓글, 좋아요, 팔로우, 질문 등록, 대화 생성, 수정. 나중에 추가될 수
있지만 지금은 없습니다.

**한 사람의 모든 기기로 갑니다.** 기기 3대면 알림 3개입니다. `collapseKey`가 없으므로
기기 간 중복 제거는 서버가 하지 않습니다.

---

## 9. 발송은 비동기입니다

`sendMessage`가 성공했다고 푸시가 나갔다는 뜻이 아닙니다. 알림은 커밋 이후 별도 스레드에서
처리되며, 뮤테이션 응답은 그것을 기다리지 않습니다.

**연속 발송의 순서도 보장되지 않습니다.** 메시지 두 개를 빠르게 보내면 알림이 뒤바뀌어
도착할 수 있습니다. 알림 도착 순서로 대화 순서를 추론하지 마세요.

## 10. 정리 — 클라이언트가 해야 할 일

1. **Firebase 초기화** — 콘솔 설정과 `google-services.json`·`GoogleService-Info.plist`는
   준비되어 있습니다(패키지·번들 ID `kr.ieuri.ktripspot`)
2. **알림 권한 요청** — 거부돼도 앱이 막히지 않아야 하고, 재요청 다이얼로그도 띄우지 않음
3. **토큰 등록** — 인증 **완료 후**, 기동·포그라운드 복귀·`onTokenRefresh`마다
4. **언어 매핑** — OS 로케일 → 네 값 중 하나
5. **로그아웃 시 `deleteDeviceToken`**
6. **수신 처리** — 포그라운드에서는 배너 안 띄움, 백그라운드·종료에서는 탭 시 딥링크
7. **종료 상태 딥링크** — `PendingDestination`에 보관 후 `ready`에서 소비 (새 게이트
   만들지 말 것)
8. **알림 채널 2개**(Android) — 서버가 채널을 지정하지 않으므로 클라이언트가 만듦
9. **설정 화면 토글 2개** — `Me.notificationPreferences` 읽고
   `updateNotificationPreference` 쓰기
10. **OS 권한 꺼짐 안내** — 설정 화면에서 알리고 OS 설정으로 보내는 길 제공

---

## 확인이 필요한 것

- **실제 발송은 아직 검증되지 않았습니다.** 서버는 기기 토큰이 없어 보낼 대상이 없었고,
  포트 스텁 수준까지만 확인했습니다. 클라이언트가 토큰을 등록하면 그때 양쪽이 함께
  확인하게 됩니다.
- **FCM 자격증명 주입 여부는 환경마다 다릅니다.** 없으면 서버는 정상 기동하고 발송만
  건너뜁니다. 알림이 전혀 안 올 때 이 가능성을 먼저 의심하세요.
- **`DevicePlatform`으로 발송을 분기하지는 않습니다.** APNs 설정을 모든 메시지에 함께
  실어 보내고 iOS 기기만 그것을 씁니다. 저장하는 이유는 운영 진단(어느 플랫폼 기기였는지)
  입니다.
