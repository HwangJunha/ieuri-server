# SPEC-0019 클라이언트 대응 요청 — 장소 식별자가 언어 무관해집니다

## 무엇이 바뀌었나

TourAPI가 같은 장소를 언어마다 다른 id로 내려줍니다. 그래서 지금까지 **언어를 바꾸면
같은 장소가 다른 id**였고, 일본어로 누른 좋아요가 영어로 바꾸면 사라졌습니다.

서버가 언어별 행을 한 장소로 묶었습니다. **이제 `Spot.id`는 언어를 바꿔도 변하지
않습니다.**

부수적으로 일본어·영어·중국어 사용자가 보는 장소가 **21,000개에서 54,000개로** 늘어납니다.

## 인자 이름 변경 (Breaking)

`spotId` → `catalogId`. **값의 의미도 바뀌었으니 이름만 치환하면 안 됩니다** — 아래
"주의" 항목을 반드시 읽어주세요.

| 위치 | 변경 전 | 변경 후 |
|---|---|---|
| `Query.posts` | `spotId: ID` | `catalogId: ID` |
| `Mutation.createPost` 입력 | `spotId: ID` | `catalogId: ID` |
| `Mutation.updatePost` 입력 | `spotId: ID` | `catalogId: ID` |
| 피드 작성 입력 | `spotId: ID!` | `catalogId: ID!` |
| `Mutation.reactToSpot` | `spotId: ID!` | `catalogId: ID!` |

**바뀌지 않은 것:** `Query.spotDetail(id:)`은 인자 이름이 그대로 `id`입니다. 넘기는
값의 의미만 언어 무관 식별자로 바뀌었습니다.

**지도도 같습니다.** `mapViewport`가 돌려주는 `MapSpot.id`도 이제 언어 무관 식별자입니다.
이전 스키마 설명이 "언어별로 다르므로 언어를 바꾸면 다시 받아야 한다"고 되어 있었는데
**그 설명이 틀렸습니다** — 지금은 언어를 바꿔도 같은 마커가 같은 id입니다. 언어 전환 시
마커를 다시 받거나 언어별로 캐시를 나눌 필요가 없습니다.

`Spot.id`, `PostSpot.id`, `SpotDetail.id`도 필드 이름은 그대로이며 값의 성격만 바뀝니다.
이 값들은 서로 호환되므로 `Spot.id`를 `posts(catalogId:)`나 `reactToSpot(catalogId:)`에
그대로 넘길 수 있습니다.

## 주의 — 저장해 둔 id는 전부 무효입니다

**로컬에 캐시한 장소 id가 있다면 버려야 합니다.** 값 자체가 새로 발급된 것이라 옛 id로
조회하면 `SPOT_NOT_FOUND`가 납니다.

해당되는 것:
- 최근 본 장소 목록
- 즐겨찾기·북마크
- 딥링크에 박아둔 id
- 오프라인 캐시

**id 캐시를 비우는 마이그레이션이 필요합니다.**

## 동작 변화

**1. 언어 전환 시 목록을 다시 받지 않아도 됩니다.**
이전에는 "언어를 바꾸면 id가 달라지므로 목록을 다시 받아야 한다"는 제약이 있었습니다.
이제 같은 id로 언어만 바꿔 조회하면 됩니다.

**2. 좋아요가 언어를 넘어 유지됩니다.**
일본어로 누르고 영어로 봐도 눌린 상태입니다. 좋아요 **개수도 언어별 합산**이라 이전보다
커집니다 — 지금까지 실제보다 작게 보고하고 있었습니다.

**3. 일부 장소는 특정 언어의 이름이 없습니다.**
외국어에만 존재하는 장소가 4,196개 있습니다(TourAPI가 한국어를 안 준 경우). 서버가 없는
이름을 지어내지 않으므로, **그 장소는 한국어 목록·검색에 나오지 않습니다.**

다만 딥링크나 게시글 칩처럼 **id를 직접 들고 오는 경로에서는 다른 언어 이름으로라도
보여줍니다** — 한국어로 물었는데 KO 이름이 없으면 영어/일본어 이름이 나갈 수 있습니다.
빈 화면이나 오류보다 낫다는 판단입니다. 화면에 섞인 언어가 보일 수 있다는 뜻이니
참고해 주세요.

**4. 검색 카테고리 필터가 이제 실제로 걸립니다.**
`searchSpots(category:)`가 서버에서 무시되고 있었습니다 — "문화시설"로 걸러도 쇼핑·음식점이
그대로 나왔고 `totalCount`도 필터 이전 값이었습니다. 고쳤으니 **결과 건수가 줄어듭니다.**
이전 동작에 맞춰 클라이언트에서 후처리로 거르고 있었다면 그 코드를 빼야 이중 필터가 안 됩니다.
**6. 목록 정렬이 바뀝니다 — 원문이 있는 장소가 먼저 나옵니다.**
홈·지도·둘러보기(`spots`, `popularSpots`, `mapViewport`, `ongoingFestivals`)가 **그 언어로
쓰인 장소를 먼저** 보여주고, 번역으로 채운 장소는 그 뒤에 나옵니다. 일본어 사용자라면
일본어 원문 21,000건을 먼저 보고, 스크롤을 계속하면 번역된 33,000건을 만납니다.

거리·인기 정렬보다 **이 조건이 우선**입니다. 즉 가까운 번역 장소보다 먼 원문 장소가
앞에 올 수 있습니다.

**7. 저장해 둔 커서(`after`)는 무효입니다.**
`popularSpots`·`ongoingFestivals`의 커서 형식이 바뀌어 **기존 커서를 넘기면 오류**입니다.
정렬 키가 늘어나서 구버전 커서로는 위치를 특정할 수 없습니다 — 조용히 엉뚱한 페이지로
뛰는 것보다 거부가 낫다고 판단했습니다.

앱을 새로 켜면 첫 페이지부터 받으므로 대부분 문제없지만, **커서를 로컬에 저장했다가
복원하는 화면이 있다면** 그 값을 버려야 합니다.
**5. 검색 `totalCount`와 목록이 이제 일치합니다.**
이전에는 건수가 목록보다 컸고, 마지막 페이지 이후로도 `hasNext`가 참이라 **빈 페이지가
무한히 이어졌습니다.** 무한스크롤에 "빈 응답이면 멈춘다" 같은 방어를 넣어 두셨다면 그대로
두셔도 무해하지만, 이제 필요 없습니다.



## 확인 부탁

1. `spotId`를 쓰던 모든 쿼리·뮤테이션을 `catalogId`로 교체
2. 저장된 장소 id 캐시 무효화 (앱 업데이트 시 1회)
3. `SPOT_NOT_FOUND` 처리가 딥링크 경로에도 걸려 있는지
4. 좋아요 개수가 커지는 것을 전제로 한 UI가 있는지 (예: 인기 뱃지 기준선)
5. 지도 마커 id를 언어별로 나눠 캐시하고 있다면 통합
6. 검색 결과를 클라이언트에서 카테고리로 후처리하고 있다면 제거
7. `hasOrigin`으로 원문 우선 노출을 할지 결정 (안 쓰면 기존과 동일)
