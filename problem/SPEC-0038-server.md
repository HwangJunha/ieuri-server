# SPEC-0038 서버 설계

> spec: SPEC-0038 · source: `Specs/SPEC-0038/spec.md` (Obsidian) · 이슈: ieuri-server #157

## 근거 요구사항

FR-001 · FR-002 · FR-006 · QR-001 · QR-002 · QR-004 · BR-001 · VC-001 · VC-002 · VC-004

FR-003 · FR-004 · FR-005와 AC-001~AC-004는 **이미 충족돼 있다.** `recommendedSpots`는 요청마다
다시 계산하고 서버 상태를 갖지 않아(SPEC-0035) 반응은 즉시 반영되며, 반응한 장소는 DB 단계에서
제외되어 보충 조회가 새 장소를 준다. 이 SPEC은 그 성질을 **깨뜨리지 않는 것**이 요구사항이다.

## 규모 가정

spec.md가 `미정`으로 남긴 것 중 이 슬라이스가 채운 것:

- **추천 후보 상한 500**(사용자 판단·실측 아님, 확인 요청됨) → **실측 완료**. cap 350부터 FR-006을
  통과하며 500은 최다 카테고리 23%·7종. 다만 **1000 유지로 결정**(D-07)했으므로 spec.md에
  되쓸 값은 "500은 품질상 충분하나 처리량 개선 효과가 없어 1000을 유지한다"는 결론이다.
- **예상 DAU · 동시 사용자**는 여전히 미정이다 — 런칭 실사용 전까지 알 수 없고 이 SPEC이
  채울 수 없다.

## 설계

도메인은 `tourism`, 조회 전용이라 애그리거트를 거치지 않는다(CQRS 읽기 경로). 도메인 모델·커맨드·
GraphQL 스키마는 **바뀌지 않는다** — 계약과 정렬 보장이 그대로이므로 클라이언트 작업이 없고,
따라서 mock 공지 대상도 아니다.

### 무엇이 바뀌는가

`SpotSpatialQueryAdapter`의 SQL 한 벌만 바뀐다.

```
현재:  spot_catalog cat JOIN spot_catalog_translation t ON t.catalog_id = cat.id AND t.visible
       WHERE t.language = ? AND ST_DWithin(cat.location, …)
       ORDER BY ST_Distance(cat.location, …) LIMIT ?
       → 정렬 확정 전 8,925행을 조인

이후:  ① spot_catalog_translation 단독으로 필터·정렬·LIMIT  (조인 0회)
       ② 살아남은 LIMIT건에만 spot_catalog를 PK 조인해 thumbnail_image_url·copyright
```

`t.location`은 부모의 사본이며 기존 트리거가 유지한다. 새로 유지할 값이 없다.

### 영속성

마이그레이션 **V7** 하나, 인덱스 하나:

```sql
CREATE INDEX idx_spot_catalog_translation_location
    ON tour.spot_catalog_translation USING gist (location)
    WHERE visible;
```

`WHERE visible`로 부분 인덱스를 두는 이유는 조회가 항상 `visible`만 보기 때문이다 —
전체 인덱스보다 작고, 숨겨진 행의 갱신이 인덱스를 건드리지 않는다.

인덱스가 없어도(현 상태) 버퍼 1,695개로 이미 16배 개선이므로, 인덱스는 그 위에서 스캔 범위를
더 줄이는 역할이다. 효과 없는 인덱스는 넣지 않는 것이 이 저장소의 관행이라(선례: PERF-20260921이
커버링 인덱스를 만들어 재보고 효과 없음을 확인해 제거했다) **실제로 만들어 재봤다.**

**인덱스 실측**(2026-09-22, dev, 트랜잭션 안에서 생성 후 롤백 — DB는 그대로):

| | 계획 | 버퍼 | 시간 |
|---|---|---|---|
| 인덱스 없음 | `idx_..._visible`(btree) 비트맵 → `ST_DWithin` 필터 | 4,506 | **60.6ms** |
| 부분 GiST 있음 | `BitmapAnd`(**새 GiST** + `..._language_category`) | 4,506 | **22.8ms** |

계획이 실제로 바뀌어 새 인덱스를 쓴다(`Index Cond: location && _st_expand(...)`, 30,359행으로
선별). 버퍼 총량이 같은 것은 카탈로그 PK 재조인 3,000개가 지배하기 때문이고, 공간 스캔
단계가 1,490 → 399개로 줄어 시간이 **2.7배** 빨라진다.

빌드 176ms, 인덱스 크기 6,464kB. 82,051행 기준이라 운영에서도 부담이 아니다 —
`CONCURRENTLY`가 필요할 만큼 길지 않다.

선택도 실측(가산 좌표·KO): 현재 계획이 쓰는 btree(`visible, language`)는 40,786행으로 좁히고
그 뒤 `ST_DWithin`으로 8,414행까지 거른다. 공간 인덱스를 먼저 쓰면 24,180행에서 출발한다 —
공간 쪽이 더 선택적이라 GiST가 이득일 가능성이 높다.

**`language`를 인덱스에 포함시키지는 않는다.** GiST에 스칼라 컬럼을 넣으려면 `btree_gist`가
필요한데 설치돼 있지 않고, 확장 활성화는 매니페스트 소유(POL-034)라 이 SPEC이 정할 일이 아니다.
`language`는 인덱스 뒤 필터로 남는다. 부분 인덱스가 기대만큼 안 나오면 그때 별건으로 검토한다.

### 측정 (실측, 2026-09-22 dev · 가산 좌표 · 반경 20km · KO)

| 형태 | 인덱스 조회 | 버퍼 | 시간 |
|---|---|---|---|
| 현재 | 8,925 | 27,593 | 130ms |
| 번역 단독 정렬(인덱스 없이) | 0 | 1,695 | 67ms |
| 번역 단독 + 카탈로그 PK 재조인(최종 형태) | 1,000 | 4,626 | 56ms |
| 거리 랭킹만(이론상 천장) | 0 | 715 | 17ms |

30 RPS 환산으로 버퍼 트래픽이 약 6,467MB/s → 약 1,084MB/s.

### 결과 동일성 — 논리적 검증과 기계적 검증

둘을 따로 했고 **결론이 같다.**

- **논리적**: 조인이 1:1임이 스키마로 보장된다. 행이 늘지 않음은 `UNIQUE(catalog_id, language)`,
  줄지 않음은 `catalog_id`의 NOT NULL FK다(D-09). 정렬은 `ranked`가 거리·id로 전순서를 확정하고
  바깥이 같은 키로 재정렬하므로 조인이 순서를 흐트러뜨릴 수 없다. 좌표·분류는 번역의 사본을
  보는데 82,051행 전수 대조에서 불일치가 0건이다.
- **기계적**: 옛 쿼리와 새 쿼리를 **같은 커넥션에서 나란히 실행해 행마다 9개 필드를 전부 비교**했다
  (좌표 4곳 × 언어 4종 × 페이지 크기 3종 = 48쌍, 제외 id 179건 바인딩, 부분 GiST 있는 상태).
  **14,580행 비교, 불일치 0건.** 순서·거리값(1e-9 허용)·썸네일·저작권까지 포함한다.

논리적 검증만으로는 "사본이 어긋나 있었다면"을 잡지 못하고, 기계적 검증만으로는 "측정하지 않은
입력에서도 그런가"를 말하지 못한다. 그래서 둘 다 했다.
