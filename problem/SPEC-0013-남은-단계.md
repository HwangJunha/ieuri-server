### BM25 실동작 검증 (검색 노드에서 직접 실행)

```sql
CREATE TABLE _bm25_probe(id bigint primary key, title text);
INSERT INTO _bm25_probe VALUES (1,'경복궁 야간개장'),(2,'덕수궁 돌담길');
CREATE INDEX _probe_idx ON _bm25_probe
  USING bm25 (id, (title::pdb.lindera(korean))) WITH (key_field='id');
SELECT id, title, pdb.score(id) FROM _bm25_probe WHERE title @@@ '경복궁'::pdb.fuzzy(1);
--  id |      title      | score
--   1 | 경복궁 야간개장 |     1
```

**"경복궁"으로 "경복궁 야간개장"이 검색됐다.** 이 스펙이 pg_search를 택한 근거(R2, 한국어
형태소 분석)가 실측으로 확인된 것이며, 남은 것은 배관 작업이다.

## 남은 단계

### 1단계 — 복제 권한 (결정 필요)

**증상**: `permission denied to start WAL sender. Only roles with the REPLICATION attribute...`

논리 복제로 데이터를 보내려면 발행자에 WAL sender 프로세스가 떠야 하고, 그건 `REPLICATION`
속성을 가진 롤만 띄울 수 있다. 앱 롤 `ieuri`는 `rolreplication = false`다(실측).

**결정할 것**: 누구에게 권한을 주는가.

- **(A) 앱 롤 `ieuri`에 부여** — 매니페스트 수정 완료, 커밋만 하면 된다.
  간단하지만 앱 계정이 강한 권한을 갖는다. CNPG 문서도 "highly privileged"라고 경고한다.
- **(B) 복제 전용 롤 신설** — 권한 분리 원칙에 맞다. 대신 롤·시크릿을 새로 만들고
  검색 노드의 `externalClusters`를 그 롤로 바꿔야 한다.

앱이 침해돼도 복제 슬롯을 임의로 만들거나 지울 수 없게 하려면 (B)다. 로컬 검증이 목적이면
(A)로 진행하고 운영 전에 (B)로 바꾸는 것도 방법이다.

### 2단계 — 검색 노드 스키마 (결정 필요, 가장 중요)

**논리 복제는 행만 옮기고 테이블 구조는 옮기지 않는다.** 지금 검색 노드에는 `spot`이
없으므로, 권한이 풀려도 받을 그릇이 없어 데이터가 들어오지 않는다.

게다가 이건 일회성이 아니다 — 앞으로 `spot` 스키마가 바뀔 때마다(Flyway 마이그레이션)
**양쪽에 각각** 적용해야 한다. 이 스펙에서 가장 오래 남을 운영 부담이다.

**결정할 것**: 검색 노드의 스키마를 누가, 어떻게 관리하는가.

- **(A) Flyway가 두 데이터소스에 마이그레이션** — 서버 코드에 두 번째 `DataSource`와
  `Flyway` 빈을 둔다. 스키마가 자동으로 동기화되지만, 검색 노드에는 회원·인증 테이블까지
  전부 생긴다(필요 없는 것까지).
- **(B) 검색 노드 전용 마이그레이션 경로 분리** — 이미 옮겨 둔
  `db/search-node/V1__add_spot_search_bm25.sql`을 확장해, 필요한 테이블 DDL만 담은
  별도 마이그레이션 세트를 둔다. 검색 노드가 최소 스키마만 갖지만, `spot` 구조 변경 시
  양쪽 파일을 손으로 맞춰야 한다(드리프트 위험).
- **(C) CNPG `bootstrap.initdb.import`** — 클러스터 생성 시 메인에서 스키마를 가져온다.
  최초 1회는 편하지만 이후 변경은 여전히 수동이다.

**주의**: 어느 쪽이든 `spot.location`이 PostGIS `geography` 타입이라 검색 노드에도
postgis가 필요하다(이미 설치돼 있다).

### 3단계 — 구독 활성화 및 초기 동기화 (그냥 하면 됨)

1·2단계가 풀리면 CNPG가 자동으로 구독을 재시도한다.

- 최초 스냅샷으로 spot 117,726행이 복사된다. **시간이 걸리고**, 그동안 검색 결과가 비어 보인다.
- 확인: `kubectl get subscription -n ieuri-db` → `APPLIED=true`
- 검증: 검색 노드에서 `SELECT count(*) FROM spot` 이 메인과 일치하는지.

### 4단계 — BM25 인덱스 생성 (그냥 하면 됨, 단 위치 주의)

`db/search-node/V1__add_spot_search_bm25.sql`을 **검색 노드에만** 적용한다.

> **메인에 적용하면 안 된다.** 앞서 겪은 replica 크래시가 그대로 재현된다 — BM25 인덱스
> 생성이 WAL에 pg_search 레코드를 쓰고, replica가 그것을 재생하다 죽는다. 이미 한 번
> 발생해 PVC를 지우고 복구했다.

적용 방법은 2단계의 결정에 따라 달라진다.

### 5단계 — 앱의 데이터소스 분리 (서버 코드)

검색 어댑터 3종만 검색 노드를 보게 라우팅한다.

- 대상: `SpotSearchJdbcAdapter`, `FestivalQueryJdbcAdapter`, `PopularSpotQueryJdbcAdapter`
- 나머지 전부(쓰기·상세·좋아요 등)는 메인을 그대로 본다.
- 두 번째 `DataSource` 빈과 그것을 쓰는 `JdbcTemplate`을 만들어 세 어댑터에 주입한다.
- **읽기 전용이다** — 검색 노드에 쓰기가 가지 않게 해야 한다(구독자에 직접 쓰면 복제와 충돌).

### 6단계 — 검증 (그냥 하면 됨)

- 앱 부팅 → V42까지 정상(V43은 메인 경로에서 빠졌다)
- `searchSpots` 실호출 — "경복궁"으로 "경복궁 야간개장"이 나오는지
- `ongoingFestivals`·`popularSpots` 실호출
- 거리 가중 정렬이 AC-6.1~6.3을 만족하는지 실데이터로 확인
- 응답 시간 실측 → POL-029 승격 근거(§9.5)

## 스펙 범위에 대해

원래 설계(§6)는 "확장 하나 켜면 됨"이었다. 실제로는 **검색 전용 클러스터 + 논리 복제 +
스키마 이중 관리 + 앱 데이터소스 분리**가 됐다. 2·5단계는 명백히 SPEC-0013의 범위를 넘는다.

별도 스펙으로 뺄지 이번에 함께 처리할지 결정이 필요하며, 어느 쪽이든 스펙 문서에 이 구조
변경을 기록해야 한다(현재 §6은 "메인에 확장 활성화"로 되어 있어 사실과 다르다).

## 결정된 것 (사용자 확인)

- **1단계 = (A)** 앱 롤 `ieuri`에 `REPLICATION` 부여. 매니페스트 수정 완료(`managedRoles`).
- **2단계 = (B)** 검색 노드 전용 마이그레이션 경로. 형태는 **최종 스키마 압축**,
  실행 주체는 **앱의 두 번째 Flyway 빈**.

## 작성 완료 (커밋 대기)

| 파일 | 내용 |
|---|---|
| `db/search-node/V1__create_spot_tables.sql` | spot·spot_festival·spot_reaction 최종형 + 인덱스 |
| `db/search-node/V2__add_spot_search_bm25.sql` | BM25 언어별 부분 인덱스 4종 |
| `SearchDataSourceConfig.kt` | searchDataSource·searchFlyway·searchJdbcTemplate 빈 |
| `application.yaml` | `ieuri.search-datasource.*` |
| 검색 어댑터 3종 | `@Qualifier("searchJdbcTemplate")` 주입 |

설계 판단 셋:

- **조회 풀은 `readOnly`다.** 구독자에 실수로 쓰면 복제가 충돌한다. 대신 Flyway는 그 풀을
  쓰지 않고 접속 정보로 자체 커넥션을 연다 — read-only 세션에서는 DDL이 거부되기 때문이다.
- **빈을 조건부로 만들지 않는다.** 처음엔 url이 비면 끄도록 했으나, 그러면 어댑터·서비스·
  리졸버까지 `@ConditionalOnProperty`가 번진다. 접속 실패는 검색 쿼리에서 드러나는 편이 낫다.
- **`@Primary`를 붙이지 않는다.** 붙이면 JPA·배치·기존 어댑터가 전부 검색 노드를 본다.
