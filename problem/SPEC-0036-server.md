# SPEC-0036 서버 설계: 지도 뷰포트 추천

## 근거 요구사항

FR-001 · FR-002 · FR-004 · FR-007 · FR-009 · FR-010 · FR-011 · FR-013 · QR-001 · BR-001.

이 저장소가 책임지지 않는 것: FR-003·FR-005·FR-006·FR-008·FR-012는 클라이언트가 누적·세션·

## 규모 가정

spec.md가 `미정`으로 남긴 **T5(한 번에 점수를 계산하는 후보 수)** 를 채워 승인을 요청한다.

**제안값: `viewport-candidate-cap: 2000`.**

실측 근거(dev DB, 2026-09-18). EN 가시 번역 기준 뷰포트 안 후보 수:

| 화면 폭 | 명동 | 강남역 | 홍대 | 부산 서면 | 제주시청 | 전주 한옥마을 |
|---|---|---|---|---|---|---|
| ~3km | 722 | 127 | 291 | 160 | 62 | 66 |
| ~8km | 1,399 | 847 | 1,027 | 242 | 225 | 106 |
| ~20km | 4,054 | 3,734 | 3,444 | 827 | 257 | 120 |

- **300으로는 가짜 소진이 난다.** 명동 20km 폭이면 4,054건 중 300건만 보고 끝난다 — FR-009가
  명시적으로 금지한 상태다.
- **2,000이면 실사용 뷰포트를 덮는다.** 클라이언트가 조회하는 실제 크기는 화면 bbox의 1.2배이며
  (`MapTuning.viewportExpansion`), 20km 폭은 최대 축소에 가깝다. 그 구간에서도 서울 3대 밀집지만
  2,000을 넘는다.
- **성능이 상한을 제약하지 않는다.** 최악 조건(명동 20km 폭 · 후보 2,000건 · 제외 500건) 실측:
  후보 조달 **114ms** + 취향 유사도 2,000건 **55ms**. 병목은 후보 수가 아니라 정렬 방식이었고
  D-04가 그것을 제거했다(같은 bbox에서 `ST_Distance` 정렬 530ms → `<->` 45ms). 넓은 bbox에서는
  플래너가 GiST 인덱스 대신 `Seq Scan`을 고르는데, 선택도가 낮을 때의 정상 동작이며 카탈로그
  43,682행 규모에서 위 수치에 이미 포함돼 있다.
- **2,000을 넘는 구간은 소진이 실질적 문제가 아니다.** 한 번에 10개씩 더하므로 2,000건을 소진하려면
  같은 영역에서 200번을 눌러야 한다. 그 전에 사용자는 영역을 옮긴다.

승인되면 `spec.md`의 규모 가정 표와 변경 이력에 되쓰고 이슈에 한 줄 남긴다.

**T4(누적 마커 감당 한계)는 k-trip-spot 몫이라 여기서 채우지 않는다.**

## 이번 범위 아님

- **커서·`truncated` 플래그**. 추천은 묶음이며 소진은 "요청보다 적게 왔다"로 클라이언트가 안다(POL-037·FR-008).
- **문화행사·혼잡도 경로**(FR-012). 손대지 않는다.
- **누적 마커 상한**(T4). 클라이언트 결정 대기.

## 설계

**도메인**: `tourism`. 새 애그리거트가 없다 — 읽기 전용 질의이며 CQRS의 **쿼리 쪽만** 늘어난다.
커맨드·영속성 변경 없음, **마이그레이션 없음**(기존 `spot_catalog`·`spot_catalog_translation`·
`idx_spot_catalog_location` GiST 인덱스를 그대로 쓴다).

**애그리거트 경계**: 변화 없음. 후보는 QueryDSL이 아닌 PostGIS 생 SQL 경로이므로 읽기 모델 DTO로
직접 투영하고 애그리거트를 복원하지 않는다(CLAUDE.md의 읽기 규약).

**쿼리 흐름** — SPEC-0035의 파이프라인에서 **후보 조달 단계만** 갈린다:

1. bbox·묶음 크기 검증(면적 상한 4.0 제곱도는 `MapViewportPolicy` 승계, 초과는 `BBOX_TOO_LARGE`).
2. `LocationAccessed(memberId, <operation>)` 발행 — 서비스가, 좌표 없이(D-08).
3. 이 회원의 반응(좋아요·싫어요)을 활성 언어 단위로 읽어 **제외 집합이자 취향 재료**로 쓴다(FR-011).
4. 후보: **bbox 안** + 반응 제외 + **클라이언트가 보낸 이미 본 id 제외**, 뷰포트 중심 KNN 순 상한 N건(D-01·D-03·D-04·D-05).
5. 취향 유사도 → 점수(거리·취향·면세) → 카테고리 반복 감점 정렬 → 앞 `first`건. 전부 기존 순수 함수 재사용.

**결정성(QR-001·BR-001)**: 무작위가 개입할 자리가 없다 — 정렬은 점수 내림차순·동점 id 오름차순이고
(`CategoryDiversity`가 이미 그렇다), 서버에 시각·세션·난수 입력이 없다. 같은 bbox·같은 제외 목록·
같은 반응 상태면 같은 순서가 나온다. 클라이언트의 `shuffle()`은 제거 대상이며 그것이 이 스펙의 본문이다.

**포트 배치**: bbox + 중심 거리 + 배열 제외라는 조건이 기존 `SpotSpatialQueryPort.searchNearby`
(반경·`ST_DWithin`·`NOT IN`)와 다르므로 같은 메서드를 넓히지 않는다 — 반경과 bbox가 배타 인자로
공존하는 조건 객체는 "둘 중 하나" 분기를 어댑터 안에 만든다. 뷰포트 후보 조회는 **자기 메서드**를
갖고, 생 SQL은 기존 선례대로 공간 질의 어댑터 안에만 머문다.

**계약**: 새 루트 필드 하나(D-07). 인증 필수, bbox·이미 본 id 목록·묶음 크기·카테고리 필터를 받고
`Spot` 목록을 돌려준다. 정렬 보장과 절삭 동작을 설명에 적는다(POL-018·019). 최종 형태는 S1에서 정한다 —
이 문서는 필드 목록 앞에서 멈춘다.
