# SPEC-0016 — 메일 발송 OCI Email Delivery 전환 (서버 설계)

요구사항·수용 기준·계약은 원본 스펙에 있다. 이 문서는 **서버 구현 결정만** 담으며 요구사항은
번호로만 참조한다.

**GraphQL 계약 변경 없음.** 메일 전송은 `application.yaml`과 인프라 어댑터에만 존재하며 스키마에
노출된 적이 없다. 신규 에러 코드도 없다 — 발송은 `AFTER_COMMIT` 비동기라 결과가 응답에 도달하지
않는다.

## 변경 대상 계층

이 스펙이 건드리는 것은 **인프라 어댑터와 설정뿐이다.** 도메인·애플리케이션 계층은 변경되지
않는다. `EmailSenderPort`의 시그니처가 그대로이므로 포트를 쓰는 애플리케이션 서비스
(`EmailChangeService` 등)는 이 변경을 인지하지 못한다.

| 구성요소 | 위치 | 변경 |
|---|---|---|
| `EmailSenderPort` | `auth/application/port/out/client/ClientPorts.kt` | 변경 없음 — 포트 계약 유지 |
| `SmtpEmailSender` | `auth/infrastructure/adapter/out/client/` | 전송 대상 교체, 벤더 중립 명명 (R1·R5) |
| `VerificationEmailListener` | `auth/infrastructure/adapter/out/event/` | 변경 없음 — `AFTER_COMMIT` 경계 유지 |
| `maskEmail` | `common/logging/EmailMasking.kt` | 신규 — 로그 마스킹 유틸 (R6) |
| `application.yaml` | `src/main/resources/` | SMTP 호스트·포트·자격증명·발신 주소 (R1~R4) |

## 설계 결정

### 1. 어댑터 명명은 벤더 중립 (R5)

구현체는 `SmtpEmailSender`다. `OciEmailSender`가 아니다. 벤더 교체가 클래스명 변경을 요구하면
같은 작업을 다음 벤더에서 또 하게 된다. 이 스펙 자체가 Gmail→OCI 교체이므로, 그 교훈을 이름에
반영한다. 포트 인터페이스는 전송 수단을 모른다.

### 2. 자격증명 미주입 시 기동 허용 (R3·R4)

`username: ${OCI_SMTP_USER:}` / `password: ${OCI_SMTP_PASS:}` — 빈 문자열 기본값이다.
리터럴 자격증명은 어떤 프로파일에도 두지 않는다(R3).

빈 기본값은 의도적이다. 값이 없으면 **기동은 되고 발송만 실패한다**(R4). 암호화 키와 달리 실패
범위가 메일에 한정되므로, 로컬·CI에서 메일과 무관한 작업을 하려고 SMTP 자격증명을 요구하는 것은
비용만 크다. 발송 실패는 이미 삼켜지는 경로이므로 새로운 실패 양식을 만들지도 않는다.

### 3. STARTTLS는 `required`까지 켠다 (AC1-2)

`mail.smtp.starttls.enable`만으로는 서버가 STARTTLS를 제공하지 않을 때 **평문으로 강등된다.**
인증 코드가 평문으로 나가는 것은 발송 실패보다 나쁘다. `required: true`로 두어 강등 대신 실패를
택한다.

### 4. 발신 주소는 단일 설정 키 (R2)

`ieuri.mail.from`(`${MAIL_FROM:}`) 하나로 관리하고 코드에 리터럴로 쓰지 않는다. 가입 인증과
비밀번호 재설정 두 경로가 같은 키를 읽으므로 발신 주소가 갈라지지 않는다(AC2-2).

값이 비면 From 헤더를 설정하지 않고 발송을 시도한다(AC2-3). 잘못된 주소를 지어내지 않는다.

### 5. 마스킹은 실패해도 발송 경로를 깨뜨리지 않는다 (R6)

`maskEmail(value: String?): String` — `common/logging`에 둔다. auth 전용이 아니라 로그 공통 관심사이며,
POL-013의 연장이다(선례: `Coordinates.toString()`의 `"Coordinates(masked)"`).

규칙은 `로컬파트 앞 2자 + *** + @도메인`. 경계 처리 세 가지가 설계의 핵심이다:

- 로컬파트 2자 이하 → 앞 2자 규칙이 아무것도 가리지 못하므로 로컬파트 전체를 가린다(AC6-2).
  짧은 주소가 마스킹을 우회하지 못한다
- `@` 없음·빈 문자열·null → 예외 대신 `***` 반환(AC6-3). **마스킹이 예외를 던지면 로그를
  남기려다 로그를 잃는다**
- `@`가 여럿이면 마지막을 도메인 구분자로 본다

도메인을 남기는 것은 의도다 — 장애 분석에 필요한 정보가 대부분 도메인 단위다(수신 거부가 특정
도메인에 몰리는지 등).

### 6. 레이트 리밋은 별도 신호로 분류 (R7)

SMTP 거부 응답을 레이트 리밋과 그 외로 나눠 로깅한다. 자격증명 오류가 레이트 리밋 경고로
분류되면 두 원인이 뭉뚱그려져 로그의 값이 사라진다(AC7-2).

**재시도·아웃박스·DLQ는 도입하지 않는다.** 거부된 메일은 그대로 버려진다. R7이 바꾸는 것은
유실 여부가 아니라 **유실을 사후에 인지할 수 있는가**다. 이 경계를 넘지 않는다.

## 테스트

CLAUDE.md 테스트 범위표에 따라 **유닛테스트는 도메인·애플리케이션 계층만** 대상이다. 이 스펙의
변경 대상은 대부분 어댑터와 설정이라 상당수 기준이 유닛테스트로 검증되지 않는다. 이를 감추고
인프라 테스트 계획을 지어내지 않는다.

| 단위 | 검증 | 대상 |
|---|---|---|
| `maskEmail` (`common/logging`) | 유닛테스트 | R6 전체 — 정상·2자 이하·`@` 없음·null |
| 발송 실패 분류 로직 | 유닛테스트 | R7 — 레이트 리밋과 그 외 구분 |
| R1·R2·R5 | 설정 값 검토 / 실제 발송 확인 / 코드 리뷰 | 어댑터·설정 계층이라 유닛테스트 불가 |
| R3 | 설정 파일 검토 | 자격증명 리터럴 부재 |
| R4 | 기동 확인 | 자격증명 없이 컨텍스트 로딩 |

`maskEmail`은 순수 함수라 프레임워크 없이 검증된다. 발송 실패 분류도 SMTP 응답 해석 로직만
떼어내면 어댑터를 띄우지 않고 검증할 수 있다 — 그렇게 배치한다.

실제 SMTP 전송·컨텍스트 기동·DNS 레코드는 **테스트하지 않는다.** 인프라 계층이며 범위 밖이다.
